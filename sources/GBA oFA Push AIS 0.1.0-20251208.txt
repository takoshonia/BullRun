1დოკუმენტის შესახებ
ეს დოკუმენტი არის The Berlin Group openFinance API Framework განხორციელების სახელმძღვანელოთა პაკეტის ნაწილი, რომელიც შექმნილია საქართველოს კანონმდებლობასთან თავსებადი ღია ბანკინგისა და მისი გაფართოების, ღია ფინანსების დანერგვის მიზნით. დოკუმენტის მიზანია, სრულად თავსებადი იყოს შესაბამის ჩარჩოსთან [oFA-IG-Push] და მხოლოდ აზუსტებს მათ მოთხოვნებს, საქართველოს კანონმდებლობისა და ადგილობრივი კონტექსტის გათვალისწინებით.
დოკუმენტის მიზანია, მოახდინოს საქართველოში ღია ბანკინგის სერვისების მაქსიმალური ჰარმონიზაცია და ამ მიზნით, ის აწესებს ბევრ ისეთ შეზღუდვას, რომელთან დაკავშირებითაც The Berlin Group openFinance API Framework ჩარჩო მეტ არჩევანს იძლევა.
1.1გასაღები სიტყვების განმარტება
იმ გასაღები სიტყვების ქართული თარგმანების ინტერპრეტაცია, რომელიც მოცემულია ცხრილი 1-ში ("MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", და "OPTIONAL") უნდა მოხდეს [RFC2119] შესაბამისად. ტერმინებს ეს მნიშვნელობა აქვთ მხოლოდ იმ შემთხვევაში, როცა ისინი მსხვილი მხედრული ან/და ᲛᲗᲐᲕᲠᲣᲚᲘ (მთავრული) შრიფტით არიან გამოყენებული.

ორგანიზაცია, რომელიც ამსმპ-ში გახსნილ საკუთარ ანგარიშებს წვდება პირდაპირ, მმპ-ის გარეშე (მათ შორის ისეთ შემთხვევაში, როდესაც წვდომა ხორციელდება ტექნიკური ქვეკონტრაქტორის მეშვეობით)

ანგარიშის ინფორმაციის გადაწოდების მომსახურება წარმოადგენს ამსმპ-ის მიერ API კლიენტისთვის შეთავაზებულ სერვისს, რომლის საშუალებითაც API კლიენტი იღებს შეტყობინებებს ანგარიშის ინფორმაციის ცვლილებების შესახებ პროაქტიურად და ინფორმაციის მიწოდების ინიციატორი არის ამსმპ. ცვლილებები შეიძლება მოიცავდეს ანგარიშზე გატარებებს, ანგარიშის ნაშთის ცვლილებებს და სხვა შესაბამის ინფორმაციას, რომელიც განისაზღვრება ამ დოკუმენტის თავი 4.6, "გამოწერის მხარდაჭერილი ქვე-კატეგორიები" თავის შესაბამისად, მიუხედავად არხისა რომლითაც ეს ცვლილება მოხდა: ეს შეიძლება იყოს როგორც კლიენტის მომსახურების არხი (ფიზიკური მომსახურება, ინტერნეტ-ბანკი, მობილბანკი და ა.შ.) ისე თავად ამსმპ-ს სისტემაში შექმნილი ოპერაცია (მაგ. როდესაც ანაბარს გაუვა ვადა და თანხა და სარგებელი ჩაირიცხება მიმდინარე ანგარიშზე რომელზეც ანგარიშებზე გატარებების გამოწერა არსებობს და იგი აქტიურია, აუცილებელია ამ გამოწერას აღნიშნული ინფორმაციაც გადაეწოდოს, ამ დოკუმენტის მოთხოვნების დაცვით).
ანგარიშის ინფორმაციის გადაწოდების მომსახურების ფარგლებში API კლიენტი ახორციელებს ანგარიშის ინფორმაციის გამოწერას, რომლის დროსაც განსაზღვრავს იმ ანგარიშებსა და ინფორმაციას, რომლის ცვლილებებზეც სურს შეტყობინებების მიღება. გამოწერის მართვის პროცესის ტექნიკური საკითხები ამ დოკუმენტის თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები" თავის შესაბამისად.
4.2გამოწერაზე თანხმობის გამოხატვა
აუცილებელია ამსმპ-მა ანგარიშის ინფორმაცია გადააწოდოს მიმღებ მხარეს მხოლოდ იმ შემთხვევაში, თუ მიღებულია ანგარიშზე უფლებამოსილი პირის/პირების შესაბამისი თანხმობა და იგი აქტიურია. თანხმობის მართვის ტექნიკური მხარე რეგულირდება ამ დოკუმენტის თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები" თავის შესაბამისად.
აუცილებელია გამოწერის მაქსიმალური ხანგრძლივობა შეესაბამებოდეს მარეგულირებელი კანონმდებლობის მოთხოვნებს.
აუცილებელია გამოწერის ავტომატურად გაუქმება იმ შემთხვევაში, თუ მას ვადა გაუვა. გაუქმების ეს და სხვა საკითხები რეგულირდება ამ დოკუმენტის თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები" თავის შესაბამისად.
აუცილებელია ამსმპ-მა აქტიური გამოწერის არსებობის შემთხვევაში API კლიენტს პროაქტიურად (API კლიენტის მხრიდან დამატებითი მოთხოვნის საჭიროების გარეშე) გადააწოდოს ინფორმაცია ანგარიშის ინფორმაციის იმ კატეგორიებზე, რომელსაც გამოწერის ფარგლები მოიცავს. აღნიშნული რეგულირდება ამ დოკუმენტის თავი 9, "ანგარიშის ინფორმაციის გადაწოდების შეტყობინებები" თავის შესაბამისად.
4.3გამოწერის უნიკალურობა
აუცილებელია ამსმპ-მა უზრუნველყოს კონკრეტული API კლიენტის ფარგლებში გამოწერის უნიკალურობა:
API კლიენტის და სმმ-ის ჭრილში, თუ სმმ მოქმედებს როგორც ფიზიკური პირი ან ინდივიდუალური მეწარმე
API კლიენტის და იურიდიული პირის ჭრილში, თუ სმმ მოქმედებს როგორც იურიდიული პირი.
თუ API კლიენტმა უკვე შექმნა გამოწერა (მიუხედავად ამ გამოწერის შინაარსისა), მას არავითარ შემთხვევაში არ უნდა შეეძლოს იმავე ტიპის ახალი გამოწერის შექმნა, სანამ უკვე შექმნილი გამოწერა აქტიურია - ამის ნაცვლად API კლიენტმა არსებული გამოწერა უნდა შეცვალოს, ამ სტანდარტით განსაზღვრული ბოლოწერტილების გამოყენებით.
4.4ინფორმაციული და ჩახმახის ტიპის გამოწერები
ამ დოკუმენტით მხარდაჭერილია გამოწერის ორი ტიპი:
ინფორმაციული ტიპის გამოწერა: მას შემდეგ რაც ამსმპ-ში მოხდება რაიმე მოვლენა რომელიც API კლიენტს აქვს გამოწერილი, შესაბამის მისამართზე გაგზავნილ შეტყობინებაში გადაეწოდება შესაბამისი ინფორმაციაც: გატარებები ანგარიშზე, ანგარიშის ნაშთი და ა.შ.
ჩახმახის ტიპის გამოწერა: მას შემდეგ რაც ამსმპ-ში მოხდება რაიმე მოვლენა რომელიც API კლიენტს აქვს გამოწერილი, შესაბამის მისამართზე გაგზავნილ შეტყობინებაში გადაეწოდება მხოლოდ ზოგადი ინფორმაცია. დეტალების გამოსათხოვად API კლიენტმა ინფორმაცია უნდა გამოითხოვოს ამსმპ-დან, ანგარიშის ინფორმაციის მომსახურების ფარგლებში, როგორც ეს [GBA-oFA-IG-AIS] დოკუმენტითაა განსაზღვრული, [GBA-oFA-IG-CONS] დოკუმენტით განსაზღვრული თანხმობის ფარგლებში.
აუცილებელია ამსმპ მხარს უჭერდეს ორივე ტიპის გამოწერას.

4.7API კლიენტის ტიპები და მხარდაჭერა
4.7.1მესამე მხარის პროვაიდერების მხარდაჭერა
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ API კლიენტი, რომელიც არის მმპ და ლიცენზირებულია მოქმედი კანონმდებლობის შესაბამისად, იყოს მხარდაჭერილი ანგარიშის ინფორმაციის გადაწოდების მომსახურების ფარგლებში. აუცილებელია ამ სახის API კლიენტს ჰქონდეს ამ დოკუმენტის (მათ შორის თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები" თავის) შესაბამისად გამოწერის განხორციელების შესაძლებლობა ყველა იმ ანგარიშის ინფორმაციაზე, რომელზე უფლებამოსილიც არის სმმ, რომელსაც შესაბამისი თანხმობის გაცემა მოუწევს ამ დოკუმენტის შესაბამისად (რა). ანგარიშის ტიპები განისაზღვრება ამ დოკუმენტის თავი 4.5, "ანგარიშის მხარდაჭერილი ტიპები" თავის შესაბამისად.
აუცილებელია ამსმპ-მა თითოეული მმპ განიხილოს როგორც ერთი, უნიკალური API კლიენტი და ისე გაავრცელოს მასზე თავი 4.3, "გამოწერის უნიკალურობა" თავით განსაზღვრული მოთხოვნები.
API კლიენტის ავთენტიფიკაციისა და ავტორიზაციის პროცედურები რეგულირდება [GBA-oFA-IG-Common] დოკუმენტით.
4.7.2საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა
უმჯობესია ამსმპ-მა უზრუნველყოს, რომ მის API-ს იყენებდნენ არამარტო მმპ-ები, არამედ ის პირები, რომლებსაც ამსმპ-ში ანგარიში აქვთ გახსნილი და სურთ საკუთარ ანგარიშთან პირდაპირი პროგრამული (API-ზე დაფუძნებული) წვდომა მმპ-ზე დაყრდნობის გარეშე. თუ ამსმპ ამგვარ API კლიენტებს მხარს უჭერს, მოქმედებს შემდეგი მოთხოვნები:
აუცილებელია აღნიშნული მომსახურება გავრცელდეს კორპორატიულ მომხმარებლებზე
უმჯობესია აღნიშნული მომსახურება გავრცელდეს ინდივიდუალურ მეწარმეებზე
შესაძლოა აღნიშნული მომსახურება გავრცელდეს ფიზიკურ პირებზე, მიუხედვად მათი ინდმეწარმის სტატუსისა
აუცილებელია ყველა იმ მხარემ, ვისაც ამსმპ საკუთარ ანგარიშზე პირდაპირ წვდომას ამ თავის შესაბამისად გაუხსნის, ამ დოკუმენტის (მათ შორის თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები" თავის) შესაბამისად გამოწერა განახორციელოს საკუთარი ანგარიშების ინფორმაციისათვის. ანგარიშის ტიპები განისაზღვრება ამ დოკუმენტის თავი 4.5, "ანგარიშის მხარდაჭერილი ტიპები" თავის შესაბამისად.
აუცილებელია ამსმპ მხარს უჭერდეს კონკრეტული იურიდიულ პირის მიერ რამდენიმე API კლიენტის გამოყენებას, რათა მის ხელთ არსებული სხვადასხვა ელექტრონული სისტემისათვის სხვადასხვა გამოწერა ჰქონდეს შექმნილი, თავი 4.3, "გამოწერის უნიკალურობა" თავით განსაზღვრული მოთხოვნების დაკმაყოფილების მიზნით. აუცილებელია ამგვარი საკითხები რეგულირდებოდეს შესაბამისი სახელშეკრულებო ურთიერთობებით, როგორც თავი 4.8, "სახელშეკრულებო ურთიერთობები" თავით არის განსაზღვრული.
ამ სახეობის API კლიენტის ავთენტიფიკაციისა და ავტორიზაციის პროცედურები რეგულირდება [GBA-oFA-IG-Common] დოკუმენტით.
4.8სახელშეკრულებო ურთიერთობები
აუცილებელია ამსმპ-მა და API კლიენტმა შორის არსებობდეს შესაბამისი სახელშეკრულებო ურთიერთობა, რომელიც განსაზღვრავს ანგარიშის ინფორმაციის გადაწოდების მომსახურების პირობებს, მათ შორის უსაფრთხოების, კონფიდენციალურობისა და მონაცემთა დაცვის საკითხებს.
5პროტოკოლისა და უსაფრთხოების საკითხები
5.1API სტრუქტურა
როგორც [oFA-IG-Push] დოკუმენტშია განსაზღვრული, ანგარიშის ინფორმაციის გადაწოდების მომსახურება შედგება ორი ნაწილისაგან:
გამოწერის (Subscription) პროცესი, რომლის დროსაც API კლიენტი ამსმპ-ის სისტემაში იძახებს შესაბამის ბოლოწერტილებს, რათა გაააქტიუროს ანგარიშის ინფორმაციის გადაწოდების პროცესი, შეცვალოს პარამეტრები ან გაუქმოს იგი.
შეტყობინებების (Notification) პროცესი, რომლის დროსაც ამსმპ-ის სისტემა API კლიენტს უგზავნის შეტყობინებებს ანგარიშის ინფორმაციის ცვლილებების შესახებ.
ამ დოკუმენტში განისაზღვრება API რესურსების იდენტიფიკატორები გამოწერის პროცესისათვის (მაგ. /v2/subscriptions/push-account-entries). აუცილებელია, გამოქვეყნებულ API რესურსების მისამართებს ჰქონდეთ შემდეგი სახე: {პრეფიქსი}/{ამ დოკუმენტში განსაზღვრული მისამართი}, მაგალითად:
https://modelbank.openfinance.ge/latest/v2/subscriptions/push-account-entries
შესაძლოა ამსმპ-მა საკუთარი გადაწყვეტილებით API რესურსების პრეფიქსად განსაზღვროს ნებისმიერი რამ, რაც HTTP(S) პროტოკოლით ნებადართულია, მათ შორის მასში გაითვალისწინოს API ვერსიების იდენტიფიკატორიც.
5.2OAuth2 პროტოკოლის გამოყენება
აუცილებელია ამსმპ-მა და API კლიენტმა გამოიყენონ OAuth2 პროტოკოლი ყველა გამოძახებაში, რომელიც გამოწერის მართვას უკავშირდება (იხ. თავი 6, "ანგარიშის ინფორმაციის გამოწერის მართვის ბოლოწერტილები"). ამის საპირისპიროდ, ამსმპ-დან შეტყობინებების გადაწოდების პროცესში (თავი 9, "ანგარიშის ინფორმაციის გადაწოდების შეტყობინებები" თავის შესაბამისად) OAuth2 პროტოკოლის გამოყენება არავითარ შემთხვევაში არ ანდა გახდეს საჭირო.
5.3შეტყობინებზე ელექტრონული შტამპის დადება
აუცილებელია როგორც ამსმპ-მა, ისე API კლიენტმა გამოიყენოს ელექტრონული შტამპი შეტყობინებების ავთენტიფიცირებისა და მთლიანობის დასადასტურებლად. აუცილებელია ელექტრონული შტამპი დაიდოს როგორც მოთხოვნაზე, ისე პასუხზე, როგორც "გამოწერის" ისე "შეტყობინებების" პროცესის დროს. აუცილებელია ელექტრონული შტამპი შეესაბამებოდეს [GBA-oFA-IG-Common] დოკუმენტში აღწერილ მოთხოვნებს. HTTP(S)-ისგან განსხვავებული პროტოკოლების შემთხვევაში აუცილებელია შტამპის დადება მოხდეს თავი 10.3.1, "შეტყობინებების სერიალიზაცია" თავის შესაბამისად.
5.4API კლიენტის მიერ მისაღები შეტყობინებების URL-ების მოთხოვნები
5.4.1HTTP(S) პროტოკოლის მხარდაჭერა
აუცილებელია ამსმპ-მა მხარი დაუჭიროს URL-ებს, რომლებიც API კლიენტის მიერ არის მიწოდებული და იყენებს HTTPS პროტოკოლს (მაგალითად, https://push.apiclient.example.com/receive). აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები, რომლებიც გამოიყენება შეტყობინებების მისაღებად, იყოს საჯაროდ ხელმისაწვდომი და მუდმივი. აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები იყენებდნენ HTTPS პროტოკოლს უსაფრთხო კომუნიკაციის უზრუნველსაყოფად. აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები აკმაყოფილებდნენ [oFA-IG-Push] დოკუმენტის 2.2 თავში აღწერილ მოთხოვნებს. HTTP პროტოკოლი არავითარ შემთხვევაში არ უნდა იყოს მხარდაჭერილი რეალურ გარემოში, თუმცა შესაძლოა იგი მხარდაჭერილი იყოს სატესტო (Sandbox) გარემოში.
5.4.2სხვა პროტოკოლების მხარდაჭერა
შესაძლოა გარდა HTTP(S) პროტოკოლისა, ამსმპ-მა მხარი დაუჭიროს სხვა პროტოკოლებსაც. მაგალითად - მაღალი დატვირთვის მქონდე API კლიენტების უკეთესი მხარდაჭერისათვის. თუ ამსმპ მხარს უჭერს სხვა პროტოკოლებს, აუცილებელია ამსმპ-მა უზრუნველყოს, რომ API კლიენტის მიერ მიწოდებული URL-ები ისე იყოს შედგენილი რომ მასში კოდირებული იყოს ყველა სათანადო პარამეტრი, რითაც უნიკალურად დადგინდება შეტყობინებების გასაგზავნი/მისაღები ადგილმდებარეობა. მაგალითად, ყველა სერვერის მისამართი (DNS ან IP) და შესაბამისი პორტი, ასევე რიგი (Queue) ან თემა (Topic) და ა.შ..

Kafka პროტოკოლის მხარდაჭერა, სადაც მითითებულია სერვერების მისამართები, პორტი, თემა და უსაფრთხოების პარამეტრები.

შესაძლოა URL-ები არ აკმაყოფილებდნენ [oFA-IG-Push] დოკუმენტის 2.2 თავში აღწერილ მოთხოვნებს. მაგალითად, ისინი მოწოდებული და მართულნი იყონ ამსმპ-ის მიერ. აუცილებელია URL-ები გაიწეროს თავი 4.8, "სახელშეკრულებო ურთიერთობები" თავის შესაბამისად განსაზღვრული სახელშეკრულებო ურთიერთობის ფარგლებში. აუცილებელია URL-ით მითითებული მისამართები იყოს საჯაროდ ხელმისაწვდომი და მუდმივი. აუცილებელია გამოყენებული იყოს დაცული კომუნიკაციის მექანიზმები, რომლებიც უზრუნველყოფენ შეტყობინებების კონფიდენციალურობას, ავთენტიფიკაციას და მთლიანობას, არჩეული პროტოკოლის სტანდარტული შესაძლებლობების შესაბამისად, რათა API კლიენტს შეეძლოს დაეყრდნოს სტანდარტულ პროგრამულ ბიბლიოთეკებს.

8მომხმარებლის ავთენტიფიკაცია და ავტორიზაცია
ამ დოკუმენტის მიზნებისათვის API კლიენტი იყენებს OAuth2 ავტორიზაციის პროტოკოლს. გარდა იმისა რომ ყველა პროცესში, სადაც სმმ უშუალოდ არის ჩართული, გაიცემა OAuth2 ტოკენები (იხ. თავი 8.1, "ანგარიშის გამოწერის ავტორიზაცია" თავი) ყველა იმ პროცესში, სადაც სმმ პირდაპირ არაა ჩართული, მაინც გამოიყენება OAuth2 ტოკენები, რომლებიც სმმ-ის თანხმობით გაიცა API კლიენტზე.
8.1ანგარიშის გამოწერის ავტორიზაცია
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ ანგარიშის ინფორმაციის გამოწერის ავტორიზაცია განხორციელდეს შესაბამისი სმმ-ის მიერ, როგორც ეს რეგულირდება [GBA-oFA-IG-Common] დოკუმენტით. აუცილებელია აღნიშნული წესი ვრცელდებოდეს ყველა ტიპის API კლიენტზე (მათ შორის იმაზე, რომელიც არის იურიდიული პირი ან ინდმეწარმე და სარგებლობს საკუთარ ანგარიშებზე წვდომით, თუ მხარდაჭერილია ამსმპ-ს მიერ).
იმ შემთხვევაში თუ გამოიყენება "გადამისამართების" ტიპის OAuth2 ავტორიზაცია და გარკვეული ხარვეზის (მაგ. ქსელის გათიშვის) გამო API კლიენტმა ვერ მიიღო OAuth2 ტოკენი, აუცილებელია API კლიენტმა თავიდან დაიწყოს ავტორიზაციის პროცესი და გადაცეს scope პარამეტრში იგივე მნიშვნელობა, რაც გადაცემული ჰქონდა წინა მოთხოვნაში (ამ დოკუმენტისა და [GBA-oFA-IG-Common] დოკუმენტის შესაბამისად). ასეთ შემთხვევაში აუცილებელია ამსმპ-მა შეამოწმოს, უკვე ავტორიზებულია თუ არა ანგარიშის გამოწერა და თუ ეს ასეა, გასცეს ახალი OAuth2 ტოკენი მხოლოდ იმ მიზნით, რათა API კლიენტს შეეძლოს ინფორმაციის გამოთხოვა და სხვა ქმედებების გატარება, გამოწერის ავტორიზაციის გაუქმების ან ხელახალი ავტორიზაციის დაწყების გარეშე.
8.2მომხმარებლის წინასწარი ავთენტიფიკაცია და ავტორიზაცია პირდაპირი წვდომის შემთხვევაში
იმ შემთხვევაში, როდესაც ამსმპ-ში რეალიზებულია თავი 4.7.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა" თავში აღწერილი პირდაპირი წვდომის მექანიზმი, აუცილებელია API კლიენტმა უზრუნველყოს, რომ მომხმარებელმა წინასწარ მოახდინოს ავტორიზაცია ამსმპ-ში, როგორც ეს რეგულირდება [GBA-oFA-IG-Common] დოკუმენტით და მიიღოს OAuth2 ტოკენი (და ასევე, refresh_token, საჭიროებისამებრ).
აუცილებელია აღნიშნული წესით მიღებული ტოკენი გამოიყენებოდეს ანგარიშის ინფორმაციის გამოწერის მართვის ყველა პროცესში, სადაც სმმ უშუალოდ არის ჩართული (მაგალითად, ანგარიშის ინფორმაციის გამოწერის შექმნა, წაშლა, დეტალების მიღება და ა.შ.), აგრეთვე იმ პროცესებშიც რაც API კლიენტმა როგორც ავტონომიურად მოქმედმა ელექტრონულმა სისტემამ შესაძლოა გამოიყენოს (მაგ. ფონურ რეჟიმში აქტიური გამოწერების სიის პერიოდულად გამოსათხოვად და საკონტროლებლად).
აუცილებელია ამსმპ-მა [GBA-oFA-IG-Common] დოკუმენტით განსაზღვრული წესით უზრუნველყოს მრავლობითი ავტორიზაცია იმ შემთხვევაში, როდესაც სმმ არ არის უფლებამოსილი მარტომ ჩაატაროს ქმედება (მაგ. შექმნას ანგარიშის ინფორმაციის გამოწერა კორპორატიულ შემთხვევაში) და ამას ამსმპ-ში გაწერილი წესების შესაბამისად ესაჭიროება სხვა უფლებამოსილი პირების დასტური.

HTTP(S) პროტოკოლის შემთხვევაში (იხ. თავი 10.1, "გადაწოდება HTTP(S) პროტოკოლით") 2 მეგაბაიტზე მეტი ზომის შეტყობინებების გამოყენება არარეკომენდებულია. სხვა პროტოკოლების შემთხვევაში აუცილებელია ამსმპ-მა გაითვალისწინოს შესაბამისი პროტოკოლის გამოყენების სტანდარტებისა და რეალიზაციის შეზღუდვები და საუკეთესო პრაქტიკა.
10ანგარიშის ინფორმაციის გადაწოდების პროტოკოლი
10.1გადაწოდება HTTP(S) პროტოკოლით
გამოძახება:
POST <apiClientPrimaryPushURI>
აუცილებელია შეტყობინებები და პასუხები ფორმატირებული იყოს [oFA-IG-Push] დოკუმენტის 4.2 თავის შესაბამისად. დამატებითი მოთხოვნები რეგულირდება ამ დოკუმენტის თავი 9, "ანგარიშის ინფორმაციის გადაწოდების შეტყობინებები" თავის შესაბამისად.
თუ შეტყობინება მიღებულია და დამუშავებულია წარმატებით, აუცილებელია შეტყობინების მიმღებმა პასუხად დააბრუნოს HTTTP სტატუს კოდი 204 (No Content), როგორც ეს [oFA-IG-Push] დოკუმენტის 4.2 თავის შესაბამისად არის განსაზღვრული. სხვა სტატუს კოდებს შემთხვევაში რეაგირება რეგულირდება თავი 10.2, "შეტყობინების გამეორების მექანიზმი" თავის შესაბამისად.
10.2შეტყობინების გამეორების მექანიზმი
აუცილებელია ამსმპ-მა განმეორებით გაგზავნოს შეტყობინება იმ შემთხვევაში, თუ შეტყობინება ვერ მიეწოდება API კლიენტს (მაგალითად, ქსელის შეცდომის ან API კლიენტის დროებითი მიუწვდომლობის გამო). აუცილებელია დროებით ხელმიუწვდომლობად ჩაითვალოს მხოლოდ ის შემთხვევა თუ apiClientPrimaryPushURI-ზე გაგზავნილი მოთხოვნა პასუხს არ დააბრუნებს 30 წამის განმავლობაში, ან დასრულდება შემდეგი სტატუს კოდებით:
408 (Request Timeout)
429 (Too Many Requests)
500 (Internal Server Error)
502 (Bad Gateway)
503 (Service Unavailable)
504 (Gateway Timeout).
ამსმპ-მა არავითარ შემთხვევაში არ უნდა ჩათვალოს დროებით ხელმიუწვდომლობაში სხვა სტატუს კოდები, მათ შორის 4xx კლასის შეცდომები, რომლებიც მიუთითებენ API კლიენტის მხრიდან არასათანადო მოთხოვნაზე.
აუცილებელია შეტყობინების გამეორებისას ამსმპ-მა გამოიყენოს ერთიდაიგივე x-request-id, რომელიც გამოყენებულია თავდაპირველ შეტყობინებაში, რათა API კლიენტმა შეძლოს დადგინდეს, რომ ეს არის გამეორებული შეტყობინება.
თუ სხვაგვარად არ არის შეთანხმებული API კლიენტსა და ამსმპ-ს შორის, აუცილებელია შეტყობინების გამეორება განხორციელდეს შემდეგი წესების დაცვით:
გამეორების მაქსიმალური რაოდენობა იყოს 5 (ხუთი) ცალი.
გამეორების ინტერვალი იყოს მზარდი, კოეფიციენტით 1,5 დაწყებული 5 (ხუთი) წუთიდან. ანუ პირველი გამეორება მოხდება 5 წუთის შემდეგ, მეორე - 7.5 წუთის შემდეგ, მესამე - 11.25 წუთის შემდეგ, მეოთხე - 16.875 წუთის შემდეგ და მეხუთე - 25.3125 წუთის შემდეგ.
თუ შეტყობინების მიწოდება ვერ მოხერხდა ყველა 5 (ხუთი) მცდელობის მიუხედავად, ამსმპ-მა უნდა შეწყვიტოს შეტყობინების გამეორება და შეინახოს აღნიშნული ინფორმაცია ჟურნალში, შემდგომი გამოკვლევის მიზნით.
მკვდარი წერილების რიგი დოკუმენტის ამ ვერსიით მხარდაჭერილი არ არის. შესაძლოა ამსმპ და API კლიენტი შეთანხმდნენ მკვდარი წერილების რიგის გამოყენებაზე, როგორც დამატებით მექანიზმზე შეტყობინებების მიწოდების წარუმატებლობის შემთხვევაში. აღნიშნული რეგულირდება ამსმპ-სა და API კლიენტს შორის არსებულ სახელშეკრულებო ურთიერთობით.
10.3გადაწოდება სხვა პროტოკოლებით
10.3.1შეტყობინებების სერიალიზაცია
აუცილებელია შეტყობინებები სერიალიზებული იყოს JSON ფორმატში. შეტყობინებების სტრუქტურა რეგულირდება თავი 9, "ანგარიშის ინფორმაციის გადაწოდების შეტყობინებები" თავის შესაბამისად. შეტყობინებებზე ხელმოწერა ხორციელდება იგივე პრინციპით, რაც HTTP(S) პროტოკოლის შემთხვევაშია აღწერილი, შემდეგი დათქმებით:
სტანდარტული თავსართები (x-request-id, digest) გადაეცემა შესაბამისი პროტოკოლის მექანიზმების გამოყენებით (მაგალითად, Kafka Headers, AMQP Message Properties და ა.შ.).
თავსართი (request-target) კოდირებულია შემდეგი პრინციპით: POST callback-uri სადაც callback-uri არის შეტყობინების მისაღები URI, რომელიც არის მითითებული გამოწერის ელემენტში (apiClientPrimaryPushURI ატრიბუტად) და ფორმატირებულია თავი 5.4, "API კლიენტის მიერ მისაღები შეტყობინებების URL-ების მოთხოვნები" თავის შესაბამისად.
10.4შეტყობინების გამეორების მექანიზმი
აუცილებელია ამსმპ-მა განმეორებით გაგზავნოს შეტყობინება იმ შემთხვევაში, თუ შეტყობინება ვერ მიეწოდება API კლიენტს (მაგალითად, ქსელის შეცდომის ან API კლიენტის დროებითი მიუწვდომლობის გამო). აუცილებელია შეტყობინების მიწოდების წარუმატებლობა დადგინდეს შესაბამისი პროტოკოლის მექანიზმების გამოყენებით (მაგალითად, Kafka Delivery Reports, AMQP Acknowledgements და ა.შ.). აუცილებელია მკვდარი წერილების რიგის რეალიზება და იგი უნდა მოხდეს შესაბამისი პროტოკოლის მექანიზმების გამოყენებით.
თუ სხვაგვარად არ არის შეთანხმებული API კლიენტსა და ამსმპ-ს შორის, აუცილებელია შეტყობინების გამეორება განხორციელდეს თავი 10.2, "შეტყობინების გამეორების მექანიზმი" თავის შესაბამისად აღწერილი პრინციპით.
