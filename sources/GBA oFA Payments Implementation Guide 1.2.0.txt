1დოკუმენტის შესახებ
ეს დოკუმენტი წარმოადგენს The Berlin Group openFinance API Framework განხორციელების სახელმძღვანელოს, საქართველოს კანონმდებლობასთან თავსებადი ღია ბანკინგის დანერგვის მიზნით. დოკუმენტი სრულად თავსებადია შესაბამის ჩარჩოსთან [oFA-IG-Com] და [oFA-IG-EPIS], აზუსტებს მათ მოთხოვნებს, საქართველოს კანონმდებლობისა და ადგილობრივი კონტექსტის გათვალისწინებით.
დოკუმენტის მიზანია, მოახდინოს საქართველოში ღია ბანკინგის სერვისების მაქსიმალური ჰარმონიზაცია და ამ მიზნით, ის აწესებს ბევრ ისეთ შეზღუდვას, რომელთან დაკავშირებითაც The Berlin Group openFinance API Framework ჩარჩო მეტ არჩევანს იძლევა.
ასევე დოკუმენტით დარეგულირდა გარკვეული საკითხები, რომლებიც ჩაითვალა არასაკმარისად დარეგულირებულად (ან რეგულირების მიღმა დატოვებულად) ცალკეულ შემთხვევებში, როდესაც ამ დოკუმენტით გარკვეული საკითხები openFinance API Framework ჩარჩოსადმი შეუსაბამო მოთხოვნებს აწესებს, საკითხი მონიშნულია სქოლიოთი „გადახვევა openFinance API Framework ჩარჩოდან“.

3საოპერაციო წესები და მომსახურებაის საერთო საკითხები
3.1გადახდის ინიციირების მომსახურების აღწერა
ეს თავი განსაზღვრავს გადახდის ინიციირების მომსახურებას სხვადასხვა ტიპის საგადახდო სერვისებისა და პროდუქტებისათვის. საგადახდო სერვისების ჩამონათვალი სტანდარტულია და მიჰყვება [oFA-IG-Com]-სა და და [oFA-IG-EPIS]-ს, ხოლო პროდუქტები და მათი ინფორმაცია შედგენილია საქართველოს სპეციფიკის შესაბამისად.
გადახდის ინიციირების მომსახურებას უზრუნველყოფს გადახდის ინიციირების მომსახურე პროვაიდერი (გიმპ). ამ თავში განსაზღვრული სერვისები გადახდის ინიციირების მომსახურების პროვაიდერს აძლევენ საშუალებას, ღია ბანკინგის ანგარიშებიდან განახორციელონ გადახდის ოპერაციები, სმმ-ის დასტურის საფუძველზე. დასტურის მიღების მექანიზმები მოცემულია ამავე თავში და მის ქვეთავებში. დოკუუმენტში ასევე აღწერილია იმავე სერვისების გამოყენება საკუთარ ანგარიშებზე წვდომიმსათვის, რომელიც პოტენციურად შეიძლება გამოიყენოს არამარტო გიმპ-მა, არამედ სხვა მხარემაც.
ამ თავში მოცემული სერვისები ითვალისწინებენ იმ შესაძლებლობასაც, რომ გადახდის ინიციირებამდე მესამე მხარის პროვაიდერს (გადახდის ინიციირების მომსახურე პროვაიდერს) ასევე მოპოვებული ჰქონდეს საგადახდო მომსახურების მომხმარებლისგან გაცხადებული თანხმობა მის ანგარიშებზე წვდომაზე, თუმცა ასევე მხარდაჭერილია ის შემთხვევაც, როდესაც ამგვარი თანხმობა არ არსებობს.
ეს დოკუმენტი არ არეგულირებს მესამე მხარის პროვაიდერს (გადახდის ინიციირების მომსახურე პროვაიდერი) და სმმ-ს შორის არსებულ ურთიერთობებს და გულისხმობს, რომ აღნიშნული ურთიერთობა სხვა რაიმე ფორმით (ხელშეკრულება, კანონმდებლობა და ა.შ.) არის დარეგულირებული.
3.2გადახდის ინიციირების მომსახურების კლასები
ამ დოკუმენტის მიზნებისათვის, საგადახდო სერვისი (payment service) იყოფა სამ კლასად:
პირდაპირი გადახდები, რომლებიც საჭიროებენ მხოლოდ ერთჯერად ინიციირებას რაც ასევე გულისხმობს ავტორიზაციას
გადადებული გადახდები, რომლებიც საჭიროებენ ჯერ ავტორიზაციას და შემდეგ ინიციირებას
განმეორებადი გადახდები, რომლებიც საჭიროებენ ჯერ ავტორიზაციას და შემდეგ ინიციირებას.
3.2.1პირდაპირი გადახდის კლასი
პირდაპირი გადახდების მომსახურების ტიპებია:
payments - ერთეულოვანი გადახდები, განსაზღვრულია [oFA-IG-Com]-ის 3.4.1 თავის მიხედვით. მხარდაჭერა აუცილებელია.
bulk-payments - პაკეტური გადახდები, განსაზღვრულია [oFA-IG-Com]-ის 3.4.3 თავის მიხედვით. მხარდაჭერა აუცილებელია.
periodic-payments - მუდმივი საგადახდო დავალება, განსაზღვრულია [oFA-IG-Com]-ის 3.4.4 თავის მიხედვით. მხარდაჭერა არააუცილებელია.
secured-payments - გადახდები გარანტირებული შესრულებით, განსაზღვრულია [oFA-IG-EPIS]-ის 3.3 თავის მიხედვით. მხარდაჭერა აუცილებელია.
secured-payments ტიპის გადახდებში გადახდის ინიციირების გარანტირების მეთოდებზე იხილეთ თავი 3.2.5, "გარანტირებული გადახდის შესრულების უზრუნველყოფა".
3.2.2გადადებული გადახდების კლასი
გადადებული გადახდების მომსახურება გულისხმობს გადახდის ავტორიზაციისა და ინიციირების ფაზების გაყოფას.
ამ კლასში შემავალი ტიპებია:
deferred-payments - მარტივი გადადებული გადახდა, რომელიც არ გულისხმობს თანხის ბლოკირებას ან გადახდის სხვაგვარ გარანტირებას და დასაშვებია მხოლოდ ერთი ინიციირება.
secured-deferred-payments - გარანტირებული მარტივი გადადებული გადახდა, რომელიც გულისხმობს თანხის ბლოკირებას ან გადახდის სხვაგვარ გარანტირებას და დასაშვებია მხოლოდ ერთი ინიციირება.
multiple-deferred-payments - გადადებული გადახდა, რომელიც არ გულისხმობს თანხის ბლოკირებას ან გადახდის სხვაგვარ გარანტირებას და დასაშვებია ავტორიზებული თანხის ნაწილ-ნაწილ გადახდის ინიციირება.
secured-multiple-deferred-payments - გარანტირებული გადახდა, რომელიც გულისხმობს თანხის ბლოკირებას ან გადახდის სხვაგვარ გარანტირებას და დასაშვებია ავტორიზებული თანხის ნაწილ-ნაწილ გადახდის ინიციირება.
ყველას მხარდაჭერა აუცილებელია.
შესაძლოა API კლიენტმა გადმოსცეს requestedExpiryDateTime პარამეტრი, რაც მიუთითებს იმას თუ როდის უნდა გაუვიდეს დრო ავტორიზაციას/განიბლოკოს თანხა. ამსმპ-ს უფლება აქვს, არ გაითვალისწინოს აღნიშნული და დააწესოს ვადის გასვლის სხვა დრო, რომელიც აუცილებელია დაბრუნდეს expiryDateTime.
secured ტიპის გადახდებში გადახდის ინიციირების გარანტირების მეთოდებზე იხილეთ თავი 3.2.5, "გარანტირებული გადახდის შესრულების უზრუნველყოფა".

recurring-payments, , განსაზღვრულია [oFA-IG-EPIS]-ის 3.7 თავის მიხედვით. მხარდაჭერა აუცილებელია.
secured-recurring-payments, , განსაზღვრულია [oFA-IG-EPIS]-ის 3.7 თავის მიხედვით. მხარდაჭერა არააუცილებელია.
multiple-recurring-payments, , განსაზღვრულია [oFA-IG-EPIS]-ის 3.8 თავის მიხედვით. მხარდაჭერა აუცილებელია.
3.2.4ავტორიზაციისა და ინიციირების ფაზის გაყოფა გადადებული და განმეორებადი გადახდის კლასებისათვის
გადახდის ავტორიზაციის ფაზის დროს API კლიენტი განსაზღვრავს საგადახდო დავალების პარამეტრებს და ხდება მომხმარებლის ავთენტიფიკაცია (მათ შორის ძლიერი ავთენტიფიკაცია, თუ ეს საჭიროა მარეგულირებელი კანონმდებლობის მიხედვით) და საგადახდო დავალების დადასტურება. ზუსტად ისევე, როგორც ეს ხდება თავი 3.2.1, "პირდაპირი გადახდის კლასი" პირდაპირი გადახდის კლასის შემთხვევაში.
იმ შემთხვევაში, როდესაც გადახდის ტიპი არის secured, აუცილებელია ამსმპ-მა უზრუნველყოს რომ გადახდის ინიციირება მოხდეს. დეტალებისათვის იხილეთ თავი 3.2.5, "გარანტირებული გადახდის შესრულების უზრუნველყოფა".
გადახდის ინიციირების ფაზის დროს არ ხდება მომხმარებელთან არანაირი ურთიერთობა. API კლიენტი თავად უგზავნის ამსმპ-ს ყველა საჭირო ინფორმაციას.
3.2.5გარანტირებული გადახდის შესრულების უზრუნველყოფა
ეს დოკუმენტი არ ზღუდავს ამსმპ-ს, secured ტიპის პროდუქტებში დაეყრდნოს ექსკლუზიურად ანგარიშზე თანხის ბლოკირებას.
შესაძლოა ამსმპ-მა გამოიყენოს ნებისმიერი სხვა გზა, რათა API კლიენტს მისცეს რწმუნება რომ გადახდის ინიციირება შეცდომით არ დასრულდება ანგარიშზე არასაკმარისი თანხის არსებობის გამო. თუმცა აუცილებელია secured ტიპის პროდუქტზე გადახდის ავტორიზაცია დამთავრდეს წარუმატებლად, თუ ავტორიზაციის მომენტში ამსმპ-ს ამგვარი რწმუნების გაცემა არ შეუძლია.
შესაძლოა ამსმპ-მა დააბრუნოს securedBy ველი, სადაც მიუთითებს კონკრეტულად რა მეთოდით მოხდა ინიციირების წარმატების გარანტირება.

3.4API კლიენტის ტიპები და მხარდაჭერა
3.4.1მესამე მხარის პროვაიდერების მხარდაჭერა
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ API კლიენტი, რომელიც არის მმპ (ლიცენზირებულია მოქმედი კანონმდებლობის შესაბამისად), იყოს მხარდაჭერილი.
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ მმპ-სათვის სახელშეკრულებო ურთიერთობის (თავი 3.5, "სახელშეკრულებო ურთიერთობები" შესაბამისად) დამყარების გარეშეც შეეძლოს გამოიყენოს პირდაპირი გადახდის კლასები თავი 3.2.1, "პირდაპირი გადახდის კლასი" თავის შესაბამისად. აუცილებელია ამსმპ მხარს უუჭერდეს მონაცემთა მოდელს რომელიც თავი 4.1, "მონაცემთა სტანდარტული მოდელი გადახდის ინიციირების ყველა კლასისათვის" მიხედვით არის განსაზღვრული და რომლის შესაბამისი მონაცემების მიღება და დამუშავება მას აქვს რომელიმე მაინც ონლაინ არხში, რასაც საკუთარ მომხმარებლებს (ფიზიკურ ან იურიდიულ პირებს) სთავაზობს.
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ მმპ-სთვის სახელშეკრულებო ურთიერთობის დამყარების შემთხვევაში (თავი 3.5, "სახელშეკრულებო ურთიერთობები" შესაბამისად) შეეძლოს გამოიყენოს ყველა გადახდის ინიციირების კლასები და ტიპები, რომლებიც ამ დოკუმენტშია განსაზღვრული.
3.4.2საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა
უმჯობესია ამსმპ-მა უზრუნველყოს, რომ მის API-ს იყენებდნენ არამარტო მმპ-ები, არამედ ის პირები, რომლებსაც ამსმპ-ში ანგარიში აქვთ გახსნილი და სურთ საკუთარ ანგარიშთან პირდაპირი პროგრამული (API-ზე დაფუძნებული) წვდომა მმპ-ზე დაყრდნობის გარეშე. თუ ამსმპ ამგვარ API კლიენტებს მხარს უჭერს, მოქმედებს შემდეგი მოთხოვნები:
აუცილებელია აღნიშნული მომსახურება გავრცელდეს კორპორატიულ მომხმარებლებზე
უმჯობესია აღნიშნული მომსახურება გავრცელდეს ინდივიდუალურ მეწარმეებზე
შესაძლოა აღნიშნული მომსახურება გავრცელდეს ფიზიკურ პირებზე, მიუხედვად მათი ინდმეწარმის სტატუსისა
აუცილებელია ყველა იმ მხარემ, ვისაც ამსმპ საკუთარ ანგარიშზე პირდაპირ წვდომას ამ თავის შესაბამისად გაუხსნის, ამ დოკუმენტის შესაბამისად გადახდა განახორციელოს საკუთარი მფლობელობის ან მართვის ქვეშ მყოფი ანგარიშებიდან (და არა მესამე პირების ანგარიშებიდან).
აუცილებელია ამსმპ მხარს უჭერდეს კონკრეტული იურიდიულ პირის მიერ რამდენიმე API კლიენტის გამოყენებას, რათა მის ხელთ არსებული სხვადასხვა ელექტრონული სისტემისათვის სხვადასხვა გამოწერა ჰქონდეს შექმნილი. აუცილებელია ამგვარი საკითხები რეგულირდებოდეს შესაბამისი სახელშეკრულებო ურთიერთობებით, როგორც თავი 3.5, "სახელშეკრულებო ურთიერთობები" თავით არის განსაზღვრული.
ამ სახეობის API კლიენტის ავთენტიფიკაციისა და ავტორიზაციის პროცედურები რეგულირდება [GBA-oFA-IG-Common] დოკუმენტით.
3.5სახელშეკრულებო ურთიერთობები
შესაძლოა ამსმპ-მა და API კლიენტმა შორის არსებობდეს შესაბამისი სახელშეკრულებო ურთიერთობა, რომელიც განსაზღვრავს მომსახურების პირობებს, მათ შორის უსაფრთხოების, კონფიდენციალურობისა და მონაცემთა დაცვის საკითხებს.

თუ ცხრილში რომელიმე ელემენტის გასწვრივ მითითებულია „პირობითი“, მისი სავალდებულობა-არასავალდებულობა განისაზღვრება კონტექსტიდან გამომდინარე და მასზე ვრცელდება ამ თავით „სავალდებულო“ და „არასავალდებულო“ ველებზე დაწესებული მოთხოვნები.

აუცილებელია, ამსმპ-მა მიიღოს და დაამუშავოს გადახდის ინიციირების მოთხოვნები, როდესაც საგადახდო პროდუქტი არის ნებისმიერი ამ დოკუმენტში განსაზღვრული, მაგრამ გადარიცხვა ხდება არა სხვა ამსმპ-ში, არამედ თავად ამ ამსმპ-ში სხვა ანგარიშზე (ანუ creditorAccount და debtorAccount მიუთითებენ ანგარიშს ამავე ამსმპ-ში, creditorAgent იგივეა რაც debtorAgent, ცხადად ან არაცხადად და ა.შ.).
აუცილებელია ველების სავალდებულობა-არასავალდებულობა, მათში დასაშვები მნიშვნელობები და სხვა მოთხოვნები დადგინდეს იმ საგადახდო პროდუქტის აღწერის (ამ დოკუმენტის შესაბამისი დანართის) მიხედვით, რომელიც არის გამოყენებული გადახდის ინიციირებაში.

4.1.5გადამხდელის გამოტოვებული ანგარიშის და ვალუტის მითითების წესი გადახდის ავტორიზაციისას
ეს საკითხი რეგულირდება [GBA-oFA-IG-Common] 5.7. თავის (არასრულიად შევსებული API ტრანზაქციის შიგთავსის დაზუსტება ტრანზაქციის ავტორიზაციის პროცესში) მიხედვით. ამ თავში მოცემულია მხოლოდ ძირითადი ინფორმაცია და მოთხოვნები, დოკუმენტის აღქმადობის მიზნებისათვის.
აუცილებელია, ამსმპ მხარს უჭერდეს შემთხვევას, როდესაც API კლიენტის მხრიდან საგადახდო დავალების შექმნისას (თავი 6.1, "საგადახდო დავალების შექმნა (თანადროული ინიციირებით ან უამისოდ)" მიხედვით) მითითებული არ არის გადამხდელის და მისი ანგარიშის საიდენტიფიკაციო არანაირი ინფორმაცია.
მმპ-ის მხრიდან ასეთი გადახდის ინიციირებისას აუცილებელია ამსმპ-მა მისცეს საშუალება API კლიენტსა და იმ სმმ-ს, რომელიც პირველი ადასტურებს აღნიშნულ ოპერაციას, აირჩიოს IBAN-ის მიხედვით იდენტიფიცირებული სადებეტო ანგარიში ვალუტასთან ერთად. იმ შემთხვევაში. ამ მიზნით აუცილებელია ამსმპ-მა API კლიენტსა ან/და სმმ-ს წარუდგინოს ყველა ის საგადახდო ანგარიში, რომელიც ამსმპ-შია გახსნილი და რომელზეც API კლიენტს აქვს უფლებამოსილება (მაგ. მისი მფლობელობაა ან მართვის უფლება აქვს) და გადახდის ინიციირებისთვის.
აუცილებელია სიაში დაბრუნებულ ანგარიშებს ასევე მოჰყვებოდეს ნაშთის ინფორმაცია (balances ელემენტი).
თუ რომელიმე ანარიში მულტისავალუტოა, აუცილებელია სიაში დაბრუნდეს აღნიშნული ანგარიში IBAN იდენტიფიკატორისა და XXX ვალუტის მითითებით, ხოლო balances ელემენტში შევიდეს ყველა შესაბამისი ვალუტა და ნაშთი.
4.1.6ურთიერთმიმართება ელემენტებისათვის requestedExecutionDate და requestedExecutionDateTime
თუ მითითებულია ორივე ველი, აუცილებელია requestedExecutionDateTime-ში მითითებული თარიღი ემთხვეოდეს requestedExecutionDate-ში მითითებულს.
4.1.7ნაგულისხმევი მნიშვნელობა ელემენტისათვის chargeBearer
თუ ველი გადაცემული არ არის, აუცილებელია ნაგულისხმევი მნიშვნელობა იყოს OUR (საკომისიო, ასეთის არსებობის შემთხვევაში, ეკისრება დებიტორს).
4.1.8გადარიცხვა სხვა პირის სახელით
იმ შემთხვევაში, როდესაც გადარიცხვა მესამე პირის სახელით ხდება (მაგ. გადარიცხვა სახელმწიფო ბიუჯეტში სხვა პირის სასარგებლოდ), აუცილებელია გამოყენებული იქნას ველები ultimateDebtor → name და ultimateDebtor → identification, რომლებითაც გადაეცემა, შესაბამისად, მესამე პირის სახელი და საიდენტიფიკაციო მონაცემები.
თუ ამსმპ მხარს არ უჭერს ამგვარი ინფორმაციის გადაცემას არც ერთ საკუთარ ონლაინ არხში (ინტერნეტბანკი, მობილბანკი და ა.შ.), შესაძლოა ამსმპ-მა იგნორირება გაუკეთოს აღნიშნულ მონაცემებს.
4.1.9ელემენტი ultimateCreditor და თანხის საბოლოო მიმღების იდენტიფიკაცია
აუცილებელია ამსმპ მხარს უჭერდეს ველს ultimateCreditor ყველა საგადახდო პროდუქტში, მიუხედავად იმისა მხარდაჭერილია თუ არა იგი შესაბამისი ბანკთაშორისი გადარიცხვის სისტემით (ასეთ შემთხვევაში იხ. თავი 4.1.11, "მონაცემთა ელემენტები, რომლებიც ბანკთაშორისი გადარიცხვების სისტემებით არ არის მხარდაჭერილი").
ელემენტი ultimateCreditor არავითარ შემთხვევაში არ უნდა შეიცავდეს მითითებას იგივე პირზე რაზეც ელემენტი creditor (თუ იგი გადმოცემულია).
აუცილებელია მხარდაჭერილი იყოს, სულ მცირე, ultimateCreditor → name და ultimateCreditor → identification, რომლებითაც გადაეცემა, შესაბამისად, თანხის საბოლოო მიმღების სახელი და საიდენტიფიკაციო მონაცემები. საიდენტიფიკაციო მონაცემების ფორმატი განისაზღვრება [GBA-oFA-DOM]-ის მიხედვით.
თუ API კლიენტმა ამსმპ-ს გადასცა ultimateCreditor ელემენტი, ამსმპ-მა არავითარ შემთხვევაში არ უნდა შესთავაზოს სმმ-ს creditor ელემენტით მითითებული პირის ან/და creditorAccount ელემენტით მითითებული ანგარიშის დამატება სანდო ბენეფიციართა სიაში ამ საგადახდო დავალების ავტორიზაციის პროცესში.
ელემენტი ultimateCreditor გამოიყენება თავი 8.2, "გადახდების მიღება სავაჭრო ობიექტის (ე.წ. მერჩანტის) სასარგებლოდ" მიხედვით განხორციელებული ოპერაციების მხარდასაჭერად.
4.1.10ველი riskSignals და რისკის სიგნალების დამუშავება
აუცილებელია ამსმპ-მა მიიღოს და დაამუშაოს საგადახდო დავალების შექმნის მოთხოვნა თავი 6.1, "საგადახდო დავალების შექმნა (თანადროული ინიციირებით ან უამისოდ)" მიხედვით, როდესაც გადახდის ინიციირების მოთხოვნის ტანში ან/და სმმ-ის კონტექსტის აღმწერ PSU-* თავსართებში მითითებულია გადახდის რისკის სიგნალები.
რისკის სიგნალების მიზანია, გიმპ-ამსმპ არხში არსებობდეს იმგვარი ინფორმაციის გადაცემის მექანიზმი, რომელიც ამსმპ-ს მისცემს საშუალებას განსაზღვროს, გაათავისუფლოს თუ არა სმმ ძლიერი ავთენტიფიკაციის ვალდებულებისაგან.
ეს თავი განსაზღვრავს მხოლოდ მონაცემთა გადაცემის წესს და არ ავალდებულებს ამსმპ-ს რომ მისმა ტრანზაქციების რისკის მონიტორინგის სისტემამ დაამუშავოს ყველა მათგანი ან/და მიიღოს შესაბამისი გადაწყვეტილება მომხმარებლის ძლიერი ავთენტიიკაციის განხორციელების, გამონაკლისით სარგებლობის, ტრანზაქციის ავტომატური დამოწმების ან სხვა ქმედების თაობაზე. აღნიშნული უნდა გადაწყდეს მოქმედი კანონმდებლობის, ამსმპ-ის შიდა პროცედურების, თავი 3.5, "სახელშეკრულებო ურთიერთობები" მიხედვით მხარეებს შორის გაფორმებული ხელშეკრულების (ასეთის არსებობის შემთხვევაში) ან/და სხვა რაიმე დადგენილი წესის შესაბამისად.
GBARiskSignals არის გიმპ-ის მიერ მოწოდებული რისკის სიგნალების ნაკრები A2A გადახდის ინიციირებისას. [ISO20022] მიხედვით აგებულ pain.001 ტიპის შეტყობინებაში მსგავსი ინფორმაცია გადაიცემა `supplementaryData[]`ელემენტში, თუმცა JSON შეტყობინების შემთხვევაში იგი უბრალოდ ზედა დონის ელემენტად გამოიყენება. ამგვარი ინფორმაციის კოდირების წესი შესაძლოა დაემატოს დოკუმენტის სამომომავლო ვერსიებში.
ძირითადი პრინციპი: გიმპ არის სენსორი, და არა მსაჯული. თითოეული ველი წარმოადგენს ან გიმპ-ის მიერ დაფიქსირებულ დაკვირვებას, ან ვაჭრისგან გადმოცემულ ფაქტს. აქ არაფერი ითხოვს, აცხადებს ან ითვლის SCA-სგან გათავისუფლებას, ვერდიქტს ან ქმედებას. ძლიერი ავთენტიფიკაციისგან სმმ-ის გათავისუფლების გადაწყვეტილებას იღებს მხოლოდ ამსმპ (იხ. EBA Q&A 2021_5845: გადამხდელის მიერ ინიცირებული საკრედიტო გადარიცხვისთვის გათავისუფლების გამოყენება შეუძლია მხოლოდ გადამხდელის საგადახდო მომსახუურების პროვაიდერს).
პასუხისმგებლობა: გიმპ ვალდებულია უზრუნველყოს მთლიანი riskSignals შიგთავსის ან/და PSU-* თავსართების სიზუსტე, მათ შორის მესამე მხარეებისგან (მაგ. ვაჭრისგან) მიღებულ მონაცემებზე. ამ დოკუმენტით არ განისაზღვრება გიმპ-ის ვალდებულებების წარმოშობის მექანიზმები (ხელშეკრულებით განსაზღვრული რეგრესის წესი, კანონმდებლობის მოთხოვნა და სხვა). ასევე ეს დოკუმენტი არ ადგენს მექანიზმებს, როგორ უნდა უზრუნველყოს გიმპ-მა სხვა მხარისგან (მაგ. სავაჭრო ობიექტისგან) მიღებული მონაცემების სარწმუნოობის რაიმე დონე.

6.1საგადახდო დავალების შექმნა (თანადროული ინიციირებით ან უამისოდ)

მოთხოვნის პარამეტრები და დასაბრუნებელი მნიშვნელობები რეგულირდება [oFA-IG-Com] -ის მიხედვით, დამატებითი მოთხოვნები მოცემულია წინამდებარე თავში და მის ქვეთავებში. აუცილებელია, სულ მცირე, JSON ვარიანტების მხარდაჭერა. XML ვარიანტების მხარდაჭერა არააუცილებელია.
აუცილებელია, ამსმპ-მა დაამუშავოს Client-Rejection-NoFunds-Preferred თავსართი (იგნორირება არ გაუკეთოს მას), თუ აღნიშნული თავსართი შესაბამისი სერვისისათვის მხარდაჭერილია [oFA-IG-Com]-ით ან [oFA-IG-EPIS]-ით. დამუშავების წესი განისაზღვრება შესაბამისი სტანდარტით. კერძოდ, თუ ამ თავსართში გადმოცემულია true ან თავსართი გადმოცემული არ არის, აუცილებელია ამსმპ-მა შეამოწმოს ანგარიშზე ხელმისაწვდომი ნაშთის არსებობა და უარყოს გადახდა ინიციირების ეტაპზევე, თუ თანხა არასაკმარისია. თუ აღნიშნული თავსართის მნიშვნელობა არის false, შესაძლოა ამსმპ-მა შეაჩეროს გადახდის დავალება ანგარიშზე თანხის ჩარიცხვამდე (მოლოდონის პერიოდში გადახდას ექნება ACCP სტატუსი, და fundsavailable იქნება false).
აუცილებელია გამოძახებისას მხარდაჭერილი იყოს რესურსის სტატუსის გადაწოდების მოთხოვნის დაფიქსირება [GBA-oFA-IG-Common]-ის მე-6 თავის შესაბამისად.
გამოძახებისას Authorization სათაურის გამოყენების წესი და გამოსადეგი ტოკენის ტიპები განისაზღვრება თავი 5.2, "OAuth2 პროტოკოლის გამოყენება API ფუნქციებში" მიხედვით.

ამ ფუნქციის მხარდაჭერა აუცილებელია ყველა იმ შემთხვევისათვის, რომელიც მხარდაჭერილია თავი 6.1.4, "გადახდა გადადებული და განმეორებადი კლასებისათვის" მიხედვით.
მოთხოვნის პარამეტრები და დასაბრუნებელი მნიშვნელობები რეგულირდება [oFA-IG-EPIS]-ის 3.5 თავის (Initiation for Deferred Payments), 3.7 თავის (Initiation for Recurring Payments) ან 3.8 თავის (Initiation for Multiple Recurring Payments) მიხედვით.
აუცილებელია ამსმპ-ს ჰქონდეს multiple-recurring-payments პროდუქტისათვის ერთბიჯიან (one-step) ინიციირების პროცესს [oFA-IG-EPIS]-ის 3.8 თავის (Initiation for Multiple Recurring Payments) მიხედვით.
უმჯობესია ამსმპ მხარს უჭერდედეს ამავე თავით განსაზღვრულ ორბიჯიან ავტორიზაციასაც და განახორციელოს იგი როდესაც API კლიენტი ცხადად გადმოსცემს Client-ExplicitConfirmationRequested თავსართში მნიშვნელობას true. ამ შემთხვევაში აუცილებელია თავი 6.4, "გადახდის ინიციირების დადასტურება მრავლობითი განმეორებადი გადახდის კლასისათვის" და თავი 6.5, "გადახდის ინიციირების უარყოფა მრავლობითი განმეორებადი გადახდის კლასისათვის" მიხედვით განსაზღვრული ფუნქციათა მხარდაჭერაც.
აუცილებელია გამოძახებისას მხარდაჭერილი იყოს რესურსის სტატუსის გადაწოდების მოთხოვნის დაფიქსირება [GBA-oFA-IG-Common]-ის მე-6 თავის შესაბამისად. შენიშვნა ეს არის დამოუკიდებელი მოთხოვნა და მიემართება კონკრეტულ ინიციირებას რომელიც შეიქმნება ამ მოთხოვნის შესაბამისად. ამდენად, იგი დამუშავდეს თავი 6.1, "საგადახდო დავალების შექმნა (თანადროული ინიციირებით ან უამისოდ)" მიხედვით შექმნილი რესურსის სტატუსისგან განცალკევებით.
გამოძახებისას Authorization სათაურის გამოყენება აუცილებელია და გამოსადეგი ტოკენის ტიპები განისაზღვრება თავი 5.2, "OAuth2 პროტოკოლის გამოყენება API ფუნქციებში" მიხედვით.

7საგადახდო დავალების სასიცოცხლო ციკლი
მას შემდეგ, რაც მმპ მიაწვდის ამსმპ-ს საგადახდო დავალებას და ეს უკანასკნელი დაარეგისტრირებს მას, ამ დოკუმენტის თავი 6.1, "საგადახდო დავალების შექმნა (თანადროული ინიციირებით ან უამისოდ)" მიხედვით განსაზღვრული წესით, საგადახდო დავალება იწყებს საკუთარ სასიცოცხლო ციკლს ამსმპ-ს ელექტრონულ სისტემაში, რაც გამოიხატება, მათ შორის, დავალების სტატუსის ცვლილებით. დავალების სტატუსის გამოთხოვა შესაძლებელია თავი 6.7, "გადახდის სტატუსი" მიხედვით განსაზღვრული წესით.

ACFC, როდესაც შესაბამისი შემოწმებებიც გავლილია).
PART
PartiallyAcceptedგამოიყენება მხოლოდ მრავლობით გადახდებში (იხ. თავი 6.1.2, "მრავლობითი (პაკეტური) გადახდა" ) პაკეტის იმგვარი სტატუსის მისათითებლად, როდესაც ტრანზაქციების ნაწილი უკვე მიღებულია (რომელიმე „Accepted” სტატუსი), ნაწილი კი ჯერ არ დამუშავებულა

აუცილებელია გადადებული და განმეორებადი გადახდების სტატუსების გადაყვანის პროცესი სრულად თავსებადი იყოს [oFA-IG-EPIS]-თან.
8გადახდის ინიციირების ტიპური შემთხვევები
8.1კონვერტაციის ოპერაციები
8.1.1კონვერტაცია მულტისავალუტო ანგარიშის „ქვეანგარიშებს“ შორის
თუ მომხმარებელს აქვს მულტისავალუტო ანგარიში, რომელზეც მიბმულია ორი ვალუტა (პირობითად ლარი და ევრო) და ხდება თანხის კონვერტირება პირველი ვალუტიდან (პირობითად, ლარიდან) მეორე ვალუტაში (პირობითად, დოლარში), მოქმედებს შემდეგი წესი:
აუცილებელია ამსმპ-მა instructedAmount-ით მითითებული თანხა და ვალუტა განიხილოს creditorAccount ანგარიშზე ჩასარიცხ ოდენობად.
თუ creditorAccount-ში ვალუტა მითითებული არ არის, აუცილებელია ამსმპ-მა იგულისხმოს ის ვალუტა, რომელიც მითითებულია instructedAmount-ით. თუ მულტისავალუტო ანგარიშზე ეს ვალუტა განსაზღვრული არ არის, აუცილებელია ამსმპ-მა დააბრუნოს შეცდომა PAYMENT_FAILED
თუ debtorAccount-ში ვალუტა მითითებული არ არის, აუცილებელია ამსმპ-მა მომხმარებელს ვალუტა აარჩევინოს გადახდის ინიციირების ავტორიზაციის ეკრანზე. თუმცა ამსმპ-მა არავითარ შემთხვევაში არ უნდა მისცეს მომხმარებელს საშუალება, შეცვალოს მმპ-ს მიერ გადმოცემული ანგარიშის ნომერი. თუ ამსმპ აღნიშნულ ოპერაციაზე საკომისიოს ისე აწესებს რომ საკომისიოები განსხვავებულია ვალუტების მიხედვით, შესაძლოა მან არ დააბრუნოს ინფორმაცია საკომისიოს ოდენობის შესახებ გადახდის ინიციირების ოპერაციის პასუხად, თუმცა ვალუტის დაზუსტების შემდეგ აუცილებელია მომხმარებელმა დაინახოს აღნიშნული ინფორმაცია მანამ, სანამ გადახდაზე თანხმობას გამოხატავდეს.
8.1.2კონვერტაცია საკუთარ ანგარიშებს შორის
აუცილებელია ამსმპ-მა instructedAmount-ით მითითებული თანხა და ვალუტა განიხილოს creditorAccount ანგარიშზე ჩასარიცხ ოდენობად.
თუ creditorAccount-ში ვალუტა მითითებული არ არის, აუცილებელია ამსმპ-მა იგულისხმოს ის ვალუტა, რომელიც მითითებულია instructedAmount-ით. თუ მულტისავალუტო ანგარიშზე ეს ვალუტა განსაზღვრული არ არის, აუცილებელია ამსმპ-მა დააბრუნოს შეცდომა PAYMENT_FAILED
8.2გადახდების მიღება სავაჭრო ობიექტის (ე.წ. მერჩანტის) სასარგებლოდ
გადახდის ინიციირების მომსახურების ერთ-ერთი ტიპური სცენარია გიმპ-ის მიერ სავაჭრო ობიექტების (ე.წ. მერჩანტის) სასარგებლოდ. ამ დროს ტრანზაქციის ინიციირება ხდება თავი 3.4.1, "მესამე მხარის პროვაიდერების მხარდაჭერა" მიხედვით განსაზღვრული არხითთ. არსებობს ორი შესაძლო სქემა:
პირდაპირი ოპერაცია - creditor/creditorAccount კი სავაჭრო ობიექტს/მის ანგარიშს. ამ შემთხვევაში ამ დოკუმენტით განსაზღვრულაია რომ ველი ultimateCreditor (იხ. თავი 4.1.9, "ელემენტი ultimateCreditor და თანხის საბოლოო მიმღების იდენტიფიკაცია") წარმოდგენილი არ არის. სავაჭრო ობიექტი იღებს ოპერაციის სრულ თანხას (instructedAmount), ხოლო გიმმპ-ის მიერ სავაჭრო ობიექტისგან მომსახურების საკომისიო, როგორც წესი, დაითვლება ცალკე რაიმე მეთოდით (მაგ. სავაჭრო ობიექტი თვის ბოლოს რიცხავს მომსახურების თანხას, ინვოისის საფუძველზე)
ოპერაცია შუამავლით - გიმმპ-ის მიერ წარდგენილ საგადახდო დავალების ველ instructedAmount -ში გადაცემული თანხა ასევე შეიცავს საკომისიოს, რომელიც უნდა დააკლდეს სავაჭრო ობიექტისთვის ჩასარიცხ თანხას იმთავითვე უნდა დააკლდეს საკომისიო და რაღაც მეთოდით განაწილდეს ამა თუ იმ მხარეებს შორის (მათ შორის გიმპ-ს ერგოს თავისი წილი). ამ დროს ოპერაციაში მონაწილეობს შუამავალი ანგარიში, რომელიც წარმოდგენილია creditorAccount ველში, ხოლო სავაჭრო ობიექტის საიდენტიფიკაციო ინფორმაცია ultimateCreditor ველში (იხ. თავი 4.1.9, "ელემენტი ultimateCreditor და თანხის საბოლოო მიმღების იდენტიფიკაცია") ეთითება. ამ დროს გადახდის ინიციირების მომსახურება სრულდება მაშინ, როდესაც დასრულდება თანხის შუამავალ ანგარიშზე ჩარიცხვის ოპერაცია.
ამ დოკუმენტით არ რეგულირდება ის თუ ვის ეკუთვნის შუამავალი ანგარიში და თუ მისი მფლობელია გიმმპ, რამდენად კანონშესაბამისია მისი გამოყენება ღია ბანკინგის კონტექსტში. გთხოვთ გაითვალისწინოთ რომ „საგადახდო სისტემისა და საგადახდო მომსახურების შესახებ“ საქართველოს კანონის 222 მუხლის მე-3 პუნქტის „ა“ ქვეპუნქტის მიხედვით, „გადახდის ინიციირების მომსახურების პროვაიდერს არ აქვს უფლება, ნებისმიერ დროს ფლობდეს გადახდის ინიციირების მომსახურებასთან დაკავშირებულ მომხმარებლის თანხას“. ამდენად, თუ ორგანიზაციას მხოლოდ გადახდის ინიციირების პროვაიდერის ლიცენზია აქვს მოპოვებული (და არა დამატებით რაიმე სხვა ტიპის ლიცენზია), მაშინ ამ დოკუმენტით რეგულირებული ოპერაციის განხორციელება შესაძლოა არ იყოს კანონშესაბამისი.
როდესაც ტარდება ოპერაცია შუამავლით, ამ შემთხვევაში შუამავალი ანგარიშიდან თანხის განაწილებას, ეს შეიძლება მოხდეს ცალკე ოპერაციით, რომელიც ინიციირდება გიმპ-ის მიერ ინიციირებული საწყისი ოპერაციისთანავე ან მოგვიანებით. აქ არსებობს სხვადასხვა ვარიანტი:
თანხის გადარიცხვა ხელით - უფლებამოსილი პირი შუამავალი ანგარიშიდან გადარიცხვას ახორციელებს ამსმპ-ის ინტერნეტ ან მობილბანკით
თანხის გადარიცხვა ამსმპ-ის რაიმე API-ს საშუალებით. უფლებამოსილი პირი შუამავალი ანგარიშიდან გადარიხვისთვის სარგებლობს ამსმპ-ის მოწოდებული რაიმე API-ს მეშვეობით (მათ შორის შესაძლოა ეს იყოს დოკუმენტით განსაზღვრული API, როდესაც API კლიეენტი არის უფლებამოსილი პირი და API-ს იყენებს თავი 3.4.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა" მიხედვით განსაზღვრული წესით და არა თავი 3.4.1, "მესამე მხარის პროვაიდერების მხარდაჭერა" მიხედვით).
რაიმე სხვა მეთოდი, მაგალითად - მუდმივი საგადასახადო დავალება

აუცილებელია remittanceInformationUnstructured-სგან აიწყოს მთლიანი სტრიქონი და მოიჭრას პირველი 140 სიმბოლო MT შეტყობინებაში ჩასაწერად.
RTGS MT-ს შემთხვევაში აუცილებელია remittanceInformationUnstructured-სგან დარჩენილი ინფორმაცია ჩაიწეროს 77T ველში. შესაძლოა მნიშვნელობა მოიჭრას, შესაბამისი ველების სიგრძიდან გამომდინარე.
RTGS MT-ს შემთხვევაში აუცილებელია additionalInformation ჩაიწეროს 77T ველში, remittanceInformationUnstructured-ს დარჩენილი ფრაგმენტის შემდეგ. შესაძლოა მნიშვნელობა მოიჭრას, შესაბამისი ველების სიგრძიდან გამომდინარე.
თუ გადმოცემულია purposeCode და არ არის გადმოცემული additionalInformation, აუცილებელია შეტყობინებაში ეს კოდი იყოს განხილული additionalInformation-ის დატვირთვის მატარებლად, ხოლო თუ გადმოცემულია ორივე მათგანი, აუცილებელია purposeCode მიეწეროს ბოლოში (საჭიროებისამებრ, additionalInformation-ის მოჭრის ხარჯზე).

სხვა საგადახდო მომსახურების პროვაიდერი (მათ შორის კომერციული ბანკი) რომელიც ლიცენზირებულია საქართველოში და გადასარიცხი ვალუტა (instructedAmount → currency) არ არის ლარი - ველების გადაყვანა საგადახდო სისტემის შეტყობინებაში ხდება თავი 16, "appendix_title" მიხედვით განსაზღვრული წესით და გადარიცხვისთვის გამოიყენება საქართველოს ეროვნული ბანკის RTGS სისტემა.

16.1.5remittanceInformationUnstructured, additionalInformation და purposeCode
აუცილებელია RTGS MT და SWIFT MT შეტყობინებაში თარგმნისას გამოყენებული იქნას ველი ‘70’(Remittance Information).
აუცილებელია remittanceInformationUnstructured-სგან აიწყოს მთლიანი სტრიქონი და მოიჭრას პირველი 140 სიმბოლო MT შეტყობინებაში ჩასაწერად.
RTGS MT-ს შემთხვევაში აუცილებელია remittanceInformationUnstructured-სგან დარჩენილი ინფორმაცია ჩაიწეროს 77T ველში, ხოლო SWIFT MT-ს შემთხვევაში 72-ე ველში. შესაძლოა მნიშვნელობა მოიჭრას, შესაბამისი ველების სიგრძიდან გამომდინარე.
RTGS MT-ს შემთხვევაში აუცილებელია additionalInformation ჩაიწეროს 77T ველში, remittanceInformationUnstructured-ს დარჩენილი ფრაგმენტის შემდეგ, ხოლო SWIFT MT-ს შემთხვევაში - 72-ე ველში. შესაძლოა მნიშვნელობა მოიჭრას, შესაბამისი ველების სიგრძიდან გამომდინარე.
თუ გადმოცემულია purposeCode და არ არის გადმოცემული additionalInformation, აუცილებელია შეტყობინებაში ეს კოდი იყოს განხილული additionalInformation-ის დატვირთვის მატარებლად, ხოლო თუ გადმოცემულია ორივე მათგანი, აუცილებელია purposeCode მიეწეროს ბოლოში (საჭიროებისამებრ, additionalInformation-ის მოჭრის ხარჯზე).

16.1.9გადარიცხვა სხვა პირის სახელით
იმ შემთხვევაში, როდესაც გადარიცხვა მესამე პირის სახელით ხდება (მაგ. გადარიცხვა სახელმწიფო ბიუჯეტში სხვა პირის სასარგებლოდ), აუცილებელია გამოყენებული იქნას ველები ultimateDebtor → name და ultimateDebtor → identification, რომლებითაც გადაეცემა, შესაბამისად, მესამე პირის სახელი და საიდენტიფიკაციო მონაცემები.
თუ ამსმპ მხარს არ უჭერს ამგვარი ინფორმაციის გადაცემას არც ერთ საკუთარ ონლაინ არხში (ინტერნეტბანკი, მობილბანკი და ა.შ.), შესაძლოა ამსმპ-მა იგნორირება გაუკეთოს აღნიშნულ მონაცემებს.
