ეს დოკუმენტი არის The Berlin Group openFinance API Framework განხორციელების სახელმძღვანელოთა პაკეტის ნაწილი, რომელიც შექმნილია საქართველოს კანონმდებლობასთან თავსებადი ღია ბანკინგისა და მისი გაფართოების, ღია ფინანსების დანერგვის მიზნით. დოკუმენტის მიზანია, სრულად თავსებადი იყოს შესაბამის ჩარჩოსთან (1) და (2) და მხოლოდ აზუსტებდეს მათ მოთხოვნებს, საქართველოს კანონმდებლობისა და ადგილობრივი კონტექსტის გათვალისწინებით.
დოკუმენტის მიზანია, მოახდინოს საქართველოში ღია ბანკინგის სერვისების მაქსიმალური ჰარმონიზაცია და ამ მიზნით, ის აწესებს ბევრ ისეთ შეზღუდვას, რომელთან დაკავშირებითაც The Berlin Group openFinance API Framework ჩარჩო მეტ არჩევანს იძლევა. 
იმ გასაღები სიტყვების ქართული თარგმანების ინტერპრეტაცია, რომელიც მოცემულია ცხრილი 1-ში ("MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", და "OPTIONAL") უნდა მოხდეს (3) შესაბამისად. ტერმინებს ეს მნიშვნელობა აქვთ მხოლოდ იმ შემთხვევაში, როცა ისინი მსხვილი მხედრული  ან/და ᲛᲗᲐᲕᲠᲣᲚᲘ (მთავრული) შრიფტით არიან გამოყენებული.

თუ ამსმპ-ის გადაწყვეტილება ავტომატური თანხმობაა, API კლიენტს შეუძლია თანხმობის ობიექტის იდენტიფიკატორი (რომელსაც ამსმპ-სგან მიიღებს) გამოიყენოს ანგარიშის ინფორმაციის გაზიარების სერვისებში. 
თუ ამსმპ-ის გადაწყვეტილება მომხმარებლის ავთენტიფიკაციის და თანხმობის გამოხატვის მოთხოვნაა, იგი უბრუნებს მმპს-ს პასუხს. მმპ-ს ესაჭიროება თანხმობის სტატუსის სერვისის გამოძახება რათა შეიტყოს, როგორ დასრულდა მომხმარებლის ავთენტიფიკაციის პროცესი.
თუ საგადახდო მომსახურების მომხმარებელს მოთხოვნილი ჰქონდა ამსმპ-ში გამოხატული თანხმობა, API კლიენტმა დამატებით უნდა გამოიძახოს თანხმობის შესახებ დეტალური ინფორმაციის მიწოდების სერვისი, რათა შეიტყოს თუ კონკრეტულად რაზე გამოხატა თანხმობა სმმ-მა. სხვა შემთხვევაში ამ სერვისის გამოძახება საჭირო არ არის, ვინაიდან ამსმპ-ს როლი მხოლოდ მმპ-ის მიერ წარდგენილი თანხმობის დოკუმენტზე სმმ-ის თანხმობის მიღებით შემოიფარგლება.

შენიშვნა: balances და transactions უფლებები ასევე გულისხმობენ accountDetails უფლებას (2)-ის თანახმად. 
აუცილებელია accountList ტიპის თანხმობისათვის მხარდაჭერილი იყოს accountDetails, ownerName და balance უფლებები.

API მოთხოვნების დასაშვები რაოდენობების გამოთვლის წესი 
აუცილებელია, frequencyPerDay გაგებული იქნას, როგორც „გამოთხოვათა რაოდენობა ნებისმიერ 24 საათიან შუალედში“. 
აუცილებელია თითოეული თანხმობა, მიუხედავად იმისა, ის ერთჯერადია თუ განმეორებადი, API კლიენტს უფლებას  აძლევდეს, სრულად მისწვდეს ამსმპ-ში დაცულ ყველა ინფორმაციას, რასაც მოიცავს თანხმობა - მიუხედავად იმისა, თუ რამდენი ტექნიკური (API) გამოძახება იქნება საჭირო ამისათვის. 
მაგალითად, თუ ერთჯერადი თანხმობა გამოხატულია რამდენიმე ანგარიშის ნაშთების გაზიარებაზე, მმპ-ს უნდა შეეძლოს გამოითხოვოს ორივეს ნაშთი, მიუხედავად იმისა, რომ მას ამისთვის სულ მცირე 2 მოთხოვნა დასჭირდება. 
განმეორებადი თანხმობის შემთხვევაში დამუშავება განსხვავდება იმის მიხედვით, თუ როგორ ხდება ინფორმაციის მოთხოვნა:
სმმ ინფორმაციას ითხოვს აქტიურად (ანუ სმმ უშუალოდ ურთიერთქმედებს API კლიენტთან, რომელიც მოქმედებს მისი დავალებით);
ინფორმაციას მოითხოვს უშუალოდ API კლიენტი, მოქმედებს რა სმმ-ის მიერ გაცემული თანხმობის ფარგლებში, თუმცა API გამოძახება არ ხდება სმმ-ის უშუალო მონაწილეობით.
აუცილებელია, ამსმპ-მა frequencyPerDay ტიპის შეზღუდვა გაავრცელოს მხოლოდ ისეთ მოთხოვნებზე, რომლებიც მმპ-ის ინიცირებულია. მან არავითარ შემთხვევაში არ უნდა გაავრცელოს აღნიშნული შეზღუდვა სმმ-ის მიერ ინფორმაციის აქტიურ მოთხოვნაზე.
შენიშვნა: ინფორმაციის მოთხოვნასთან დაკავშირებულ ყველა API გამოძახებისას (ანუ /accounts, /card-accounts, /cards და ა.შ.) შესაბამისი სტანდარტით განსაზღვრულია PSU-IP-Address თავსართი, რომელშიც IP მისამართი გადაეცემა მაშინ და მხოლოდ მაშინ, როდესაც სმმ ინფორმაციას ითხოვს აქტიურად. თუ ინფორმაციას ითხოვს უშუალოდ მმპ, აღნიშნული ველი ცარიელი რჩება. აღნიშნული პრინციპი განსაზღვრულია, მაგალითად, (1)-ით. რაც შეეხება თანხმობის გამოხატვის სერვისს, აქ (2)-ის მიხედვით PSU-IP-Address სათაური სავალდებულო პარამეტრია.
შესაძლოა, ამსმპ-მა დააწესოს რაიმე მექანიზმები, რომლითაც მოხდება მმპ-ების მხრიდან აღნიშნული შესაძლებლობის ბოროტად გამოყენების ფაქტების გამოვლენა, რომელიც გადაეგზავნება მარეგულირებელ ორგანოებს, შემდგომი რეაგირებისათვის. აღნიშნული არავითარ შემთხვევაში არ უნდა მოხდეს იმ ფორმით, რომელიც API გამოძახებებს (1)-ის ან (7)-ის მოთხოვნებთან არათავსებადს გახდის.
აუცილებელია თანხმობის ლიმიტი გამოთვლილი იყოს კონკრეტული თანხმობის ჭრილში (ანუ იმის მიხედვით თუ რომელი თანხმობის იდენტიფიკატორს გადმოსცემს მმპ Consent-ID თავსართში).

მულტისავალუტო ანგარიშებზე გამოხატული თანხმობა
მულტისავალუტო ანგარიშები
საქართველოს კანონმდებლობის მიხედვით, მულტისავალუტო ანგარიში განიმარტება შემდეგნაირად:
ანგარიში, რომელზეც აღრიცხულია ფულადი სახსრები რამდენიმე ვალუტაში ცალ-ცალკე და რომელიც რაოდენობრივად წარმოადგენს ერთ ანგარიშს;
ამ დოკუმენტის მიზნებისათვის აუცილებელია ამსმპ-მა მულტისავალუტო ანგარიშად მიიჩნიოს მომხმარებლის ანგარიშების ნებისმიერი ისეთი ერთობლიობა, რომლებსაც ეს ამსმპ სულ მცირე ერთ შემთხვევაში აერთიანებს და გაერთიანებული ფორმით წარუდგენს მოხმარებელს მის მიერ მომხმარებლისთვის სულ მცირე ერთ არხში (ინტერნეტ-ბანკი, მობილ ბანკი და სხვა). 
საერთო ანგარიშის ფორმით წარდგენის არაამომწურავი სია შემდეგია:
ანგარიშების სიაში საერთო სახით ჩვენება (იმ შემთხვევაში, თუ საუბარია ანარიშების სიაზე და არა, მაგალითად, „ჯამური აქტივების“ და „ჯამური ვალდებულებების“ მსგავს ჯამურ ინფორმაციაზე)
დაჯამებული ნაშთის გამოტანა
დაჯამებული ნაშთის გამოტანა (იმ შემთხვევაში, თუ საუბარია ანარიშების კონკრეტულ ჯგუფზე და არა, მაგალითად, „ჯამური აქტივების“ და „ჯამური ვალდებულებების“ მსგავს ჯამურ ინფორმაციაზე)
გაერთიანებული ამონაწერის მიღების შესაძლებლობა
ნებისმიერი ტიპის ოპერაციის გატარებისას გაერთიანებაში შემავალი ანგარიშის ამორჩევა ხდება ავტომატურად, წინასწარ გაწერილი სცენარით (მაგ. პრიორიტეტებით) ან მის გარეშე. აღნიშნული არ ვრცელდება იმ შემთხვევაზე, როდესაც სხვადასხვა ტიპის ოპერაციებზე (მაგ. თანხის გამოტანაზე და თანხის შეტანაზე) ანგარიშების სხვადასხვა სიმრავლეა წინასწარ დადგენილი.
შენიშვნა: მიუხედავად იმისა რომ დამკვიდრებული პრაქტიკით მულტისავალუტო ანგარიშებში შემავალ ანგარიშებს, როგორც წესი, ერთიდაიგივე IBAN გააჩნიათ, ამ თავის მიზნებისათვის IBAN-ების იგივეობა ავტომატურად არ ნიშნავს რომ ანგარიშები მულტისავალუტო ანგარიშს მიეკუთვნება. მეტიც, ზოგიერთ შემთხვევაში მულტისავალუტო ანგარიშში ერთიანდებიან ისეთი ანგარიშებიც, რომლებსაც IBAN განსხვავებული აქვთ.
თანხმობის გამოხატვის წესი
აუცილებელია, მულტისავალუტო ანგარიშზე გამოხატული თანხმობა ვრცელდებოდეს მასზე, როგორც ერთიან ანგარიშზე. მათ შორის აუცილებელია, მულტისავალუტო ანგარიშზე ახალი ვალუტის დამატების შემთხვევაში თანხმობა ვრცელდებოდეს ახალ ვალუტაზეც. 
შესაძლოა, ამსმპ-მა მხარი დაუჭიროს მულტისავალუტო ანგარიშის „დანაწევრებას“ ისე, რომ საშუალება მისცეს მმპ-ს, მიიღოს სმმ-ის თანხმობა მულტისავალუტო ანგარიშთან დაკავშირებულ კონკრეტულ  ვალუტასთან მიმართებაში. აღნიშნული გულისხმობს, მაგალითად, ანგარიშზე დეტალური თანხმობის მოთხოვნისას ვალუტის კოდის მითითებასაც. თუმცა ამ შემთხვევაში აუცილებელია, მხარდაჭერილი იყოს მთლიან მულტისავალუტო ანგარიშზე თანხმობის გაცემაც (ვალუტის მითითების გარეშე).
თუ ამსმპ მხარს უჭერს მულტისავალუტო ანგარიშის „დანაწევრებას“, ერთ ვალუტასთან მიმართებაში გაცემული თანხმობა არავითარ შემთხვევაში არ უნდა გულისხმობდეს თანხმობას სხვა ვალუტასთან მიმართებაში.
თუ ამსმპ მხარს არ უჭერს მულტისავალუტო ანგარიშის „დანაწევრებას“, აუცილებელია ანგარიშზე დეტალური თანხმობის მოთხოვნისას მან სმმ-ს თანხმობა გამოახატინოს იმის მიუხედავად, გადმოეცა თუ არა ანგარიშის ნომერთან ერთად ანგარიშის ვალუტა.
ბარათების (და არა საბარათე ანგარიშების) შემთხვევაში, თუ ისინი მულტისავალუტოა, კონკრეტულ ვალუტაზე თანხმობის გამოხატვა არავითარ შემთხვევაში არ უნდა იყოს მხარდაჭერილი - მულტისავალუტო ბარათზე თანხმობა ყოველთვის ხდება „აგრეგირებულ“ დონეზე.

განმეორებადი თანხმობების ურთიერთქმედება
თუ API კლიენტს მიერ უკვე დარეგისტრირებულია recurringIndicator=true თანხმობა და მმპ არეგისტრირებს მეორე recurringIndicator=true თანხმობას, აუცილებელია პროცესი წარიმართოს ერთი-ერთი შემდეგი სცენარით:
ამსმპ მხარს უჭერს მრავლობითი თანხმობების (Multiple Consents) გამოხატვას (2)-ის მიხედვით და არ აუქმებს წინა recurringIndicator=true თანხმობებს
ამსმპ მხარს არ უჭერს მრავლობითი თანხმობების გამოხატვას (2)-ის მიხედვით და აუქმებს ყველა წინა recurringIndicator=true თანხმობას, მიუხედავად იმისა, რა ტიპისაა ესა თუ ის თანხმობა (მაგ. დეტალური თანხმობით შეიძლება ამსმპ-ში გამოხატული თანხმობის ჩანაცვლება). აუცილებელია ჩანაცვლებული თანხმობის სტატუსი გახდეს replacedByTpp როგორც ეს განსაზღვრულია (6)-ით.

ავთენტიფიკაციისა და შესაბამისი თავსართის გამოყენების საკითხი
ამ თავით რეგულირდება მხოლოდ ავთენტიფიკაციისა და, შესაბამისად, Authorization თავსართის გამოყენების საკითხები, ანგარიშზე თანხმობის გამოცხადების სერვისებში.
თანხმობის მოთხოვნის რეგისტრაციის სერვისი
შესაძლოა გამოძახებისას Authorization თავსართის გამოყენება, რომელშიც გადაეცემა OAuth2 ტოკენი. აუცილებელია, ამსმპ-მა მხარი დაუჭიროს შემთხვევას, როდესაც API კლიენტი არ გადასცემს Authorization სათაურს. 
თუ მმპ გადასცემს Authorization თავსართს, აუცილებელია მასში მითითებული ტოკენი გაცემული იყოს მომხმარებლის ავთენტიფიკაციის საფუძველზე, მხოლოდ ერთ-ერთ შემდეგ შემთხვევაში:
ავთენტიფიკაციის ტოკენი გაიცა სმმ-ის ამ ამსმპ-ში რაიმე წინა ავთენტიფიკაციის შედეგად (თუ ამგვარი ავთენტიფიკაცია მოხდა და ტოკენი აქტიურია). ტოკენის გადაცემის ფაქტი არ ავალდებულებს ამსმპ-ს, დაეყდნოს მას. შესაბამისად, აუცილებელია ამსმპ-მა იმოქმედოს ერთ-ერთი შესაძლო სცენარით:
ყურადღება არ მიაქციოს ამ ტოკენის არსებობას და იმოქმედოს ისევე, როგორც იმოქმედებდა ცარიელი Authorization თავსართის გადმოცემისას;
გაითვალისწინოს ტოკენის არსებობა და, თუ მარეგულირებელი კანონმდებლობა საშუალებას აძლევს, სმმ-ს შესთავაზოს ავთენტიფიკაცია შემცირებული რაოდენობის ფაქტორებით. აღნიშნული განიხილება როგორც OAuth2 წინარე ავტორიზაცია.  
სმმ-მა ავთენტიფიკაცია გაიარა მმპ-სთან ან სხვა პირთან და აღნიშნული ავთენტიფიკაციის სანდოობა განსაზღვრულია ამსმპ-სა და API კლიენტს შორის დადებული ორმხრივი ან მრავალმხრივი ხელშეკრულების საფუძველზე. აღნიშნული განიხილება როგორც OAuth2 წინარე ავტორიზაცია (4)-ის მიხედვით  (OAuth2 Pre-Step).
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს ისეთი ტოკენის გამოყენება, რომელიც არ არის გაცემული მომხმარებლის ავთენტიფიკაციის საფუძველზე.
აუცილებელია, ამსმპ-მა მოითხოვოს მომხმარებლის ძლიერი ავთენტიფიკაცია aspspManaged ტიპის თანხმობის შემთხვევაში.
აუცილებელია, ამსმპ-მა მოითხოვოს მომხმარებლის ძლიერი ავთენტიფიკაცია, როცა მოთხოვნილია ანგარიშის ნაშთები ან/და ტრანზაქციები.
შესაძლოა, ამსმპ-მა არ მოითხოვოს მომხმარებლის ძლიერი ავთენტიფიკაცია, როცა accountList ტიპის თანხმობის შემთხვევაში, თუ აღნიშნული ნებადართულია მარეგულირებელი კანონმდებლობით და მოთხოვნილი არ არის ანგარიშის ნაშთები.

თანხმობის სტატუსის სერვისი
თუ თანხმობის მოთხოვნის რეგისტრაციისას გამოყენებული იქნა Authorization სათაური ან მომხმარებელმა გაიარა ავთენტიფიკაცია ამ თანხმობის ფარგლებში, გამოძახებისას Authorization სათაურის გამოყენება აუცილებელია.

თანხმობის შესახებ დეტალური ინფორმაციის მიწოდების სერვისი
გამოძახებისას Authorization სათაურის გამოყენება აუცილებელია. აუცილებელია, ტოკენი გაცემული იყოს მომხმარებლის ავთენტიფიკაციის საფუძველზე. თუ მმპ-მა მოითხოვა ამსმპ-ში გამოხატული თანხმობა, ტოკენი ვალუდურია მაგრამ მაგრამ თანხმობის გამოხატვის პროცესი დასრულებული არ არის, აუცილებელია ამსმპ-მა დააბრუნოს შეცდომა CONSENT_INVALID.

თანხმობის გაუქმების სერვისი
თუ თანხმობის მოთხოვნის რეგისტრაციისას გამოყენებული იქნა Authorization სათაური ან მომხმარებელმა გაიარა ავთენტიფიკაცია ამ თანხმობის ფარგლებში, გამოძახებისას Authorization სათაურის გამოყენება აუცილებელია.


სახელშეკრულებო და არასახელშეკრულებო მოდელი
აუცილებელია payments და cards ტიპის ანგარიშებზე მხარდაჭერილი იყოს არასახელშეკრულებო მოდელი, ანუ როდესაც თანხმობის რეგისტრაციის ბოლოწერტილს (POST /v2/consents/account-access) არ გადაეცემა API-Contract-ID თავსართი. 
აუცილებელია არასახელშეკრულებო მოდელით სარგებლობისას მმპ-ს (API კლიენტს) შეეძლოს ისარგებლოს იმ ლიმიტებით, რომლებიც დადგენილია საქართველოს კანონმდებლობის შესაბამისად და აქ მოყვანილია მხოლოდ ინფორმაციისათვის:
24 საათის განმავლობაში გამოითხოვოს მონაცემები სულ მცირე 4-ჯერ, როდესაც მომხმარებელი აქტიურად არ ითხოვს ინფორმაციას (ველი frequencyPerDay)
თანხმობის მაქსიმალური ხანგრძლივობა იყოს სულ მცირე 90 დღე მიმდინარე თარიღიდან (ველი validTo)
თუ API კლიენტი სარგებლობს არასახელშეკრულებო მოდელით, შესაძლოა ამსმპ-მა საკუთარი გადაწყვეტილებით დაადგინოს კანონმდებლობაზე მაღალი ლიმიტები payments და cards ტიპის ანგარიშებზე. 
შესაძლოა payments და cards ტიპის ანგარიშებზე მხარდაჭერილი იყოს სახელშეკრულებო მოდელი, რომლის დროსაც რეგისტრაციის ბოლოწერტილს გადმოეცემა API-Contract-ID თავსართი. 
იმ API კლიენტებისათვის, რომლებიც არიან მმპ-ები, აუცილებელია ამსმპ-მა სახელშეკრულებო მოდელში (ასეთის არსებობის შემთხვევაში) გაითვალისწინოს ან იგულისხმოს ლიმიტები payments და cards ტიპის ანგარიშებზე, რომლებიც არ უნდა იყოს არასახელშეკრულებო ლიმიტებზე ნაკლები. 
შესაძლოა სხვა ტიპის ანგარიშებზე მხარდაჭერილი იყოს მხოლოდ სახელშეკრულებო მოდელი. ამ შემთხვევაში, თუ თანხმობის რეგისტრაციის ბოლოწერტილს არ გადმოეცემა API-Contract-ID თავსართი, უნდა მოხდეს შეცდომა CONSENT_INVALID.
API კლიენტის მიერ ლიმიტების გადაჭარბების შემთხვევაში აუცილებელია თანხმობის რეგისტრაცის მცდელობა უნდა დასრულდეს შეცდომით CONSENT_INVALID

NextGenPSD2 XS2A და openFinance API Framework-თანხმობების თანაარსებობა
თუ ამსმპ მხარს უჭერს payments და cards ტიპის ანგარიშებზე თანხმობის გამოხატვას და ამავდროულად დანერგილი აქვს NextGenPSD2 XS2A 1.3.x თავსებადი თანხმობების მოდელი, აუცილებელია NextGenPSD2 XS2A 1.3.x თავსებადი ინტერფეისით მიღებული თანხმობები ავტომატურად კონვერტირდეს ამ დოკუმენტით მხარდაჭერილ თანხმობის მოდელში.
თუ ამსმპ-ის გადაწყვეტილებით (ან/და მარეგულირებელი კანონმდებლობის მოთხოვნით) payments და cards ტიპის ანგარიშებზე თანხმობის გამოხატვის დანერგვასთან ერთად არ გამოირთვება NextGenPSD2 XS2A 1.3.x თავსებადი ინტერფეისი, აუცილებელია ერთიდაიგივე თანხმობა, ერთიდაიგივე იდენტიფიკატორით (Consent Token) ხელმისაწვდომი იყოს ორივე ინტერფეისში, შესაბამისი ინტერფეისისათვის განსაზღვრული ფორმატის მიხედვით, გარდა იმ შემთხვევისა, როდესაც თანხმობა მიღებულია ამ დოკუმენტის მიხედვით და მასში არ არის არც payments არც cards ტიპის ანგარიშები. აუცილებელია ყველა ფუნქცია (სტატუსის გამოთხოვა, დეტალების გამოთხოვა, გაუქმება) ხელმისაწვდომი იყოს ორივე ინტერფეისიდან. 
თუ ამსმპ მხარს უჭერს ორივე ინტერფეისს ერთდროულად, აუცილებელია მან ორივე ინტერფეისში დანერგოს მრავლობითი თანხმობის (Multiple Consents), როგორც ეს განსაზღვრულია (2)-ით და (8)-ით, ანუ განმეორებითი თანხმობის რეგისტრაციისას დააბრუნოს  ASPSP-Multiple-Consent-Support=true თავსართი.

NextGenPSD2 XS2A თანხმობის გადაყვანა openFinance API Framework ფორმატში (ინფორმაციული)
ამ თავით განსაზღვრულია ის მაგალითები როგორ უნდა მოხდეს NextGenPSD2 XS2A თანხმობის გადაყვანა openFinance API Framework ფორმატში, სხვადასხვა ტიპებისათვის.

combinedServiceIndicator ატრიბუტის საკითხი
NextGenPSD2 XS2A სტანდარტის დოკუმენტში ასევე იყო ატრიბუტი combinedServiceIndicator, რომელიც ეთითებოდა დოკუმენტის (და არა ანგარიშის) დონეზე. აღნიშნული ატრიბუტი (2)-ით უკვე აღარ არის განსაზღვრული და გადაყვანისას შესაბამის ანგარიშებს rights ატრიბუტში უნდა ჩაემატოთ უფლება paymentInitiations.

ამსმპ-ში გამოხატული თანხმობა
ამსმპ-ში გამოხატული თანხმობა, რომელიც ინიციირდება NextGenPSD2 XS2A სტანდარტის მიხედვით, საბოლოოდ იღებს დეტალური თანხმობის მსგავს სახეს (და შემდგომში ამ ფორმით ბრუნდება GET /v1/consents/{consentId} გამოძახებისას). ამდენად, გადაყვანის წესები სრულად იდენტურია დეტალური თანხმობის გადაყვანის წესებით, რომელიც 10.2.1 თავით არის განსაზღვრული, განსხვავებული იქნება მხოლოდ consentType ატრიბუტი, რომელშიც ეწერება aspspManaged.
