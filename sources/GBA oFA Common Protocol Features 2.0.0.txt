1დოკუმენტის შესახებ
ეს დოკუმენტი წარმოადგენს The Berlin Group openFinance API Framework განხორციელების სახელმძღვანელოს, საქართველოს კანონმდებლობასთან თავსებადი ღია ბანკინგის დანერგვის მიზნით. დოკუმენტი სრულად თავსებადია შესაბამის ჩარჩოსთან [oFA-PFSM] და სხვა, აზუსტებს მათ მოთხოვნებს, საქართველოს კანონმდებლობისა და ადგილობრივი კონტექსტის გათვალისწინებით.
დოკუმენტის მიზანია, მოახდინოს საქართველოში ღია ბანკინგის სერვისების მაქსიმალური ჰარმონიზაცია და ამ მიზნით, ის აწესებს ბევრ ისეთ შეზღუდვას, რომელთან დაკავშირებითაც The Berlin Group openFinance API Framework ჩარჩო მეტ არჩევანს იძლევა.
1.1გასაღები სიტყვების განმარტება

საკითხებს, რომლებიც მონიშნულია როგორც „უმჯობესია“ „რეკომენდებულია“, „არარეკომენდებულია“, „არასავალდებულო“, „პირობითი“ ასევე მოჰყვება დამაზუსტებელი მითითება იმის თაობაზე, თუ რატომაა რეკომენდებული (ან არარეკომენდებული) აღნიშნული საკითხის გადაწყვეტა ამ დოკუმენტის დანაწესის მიხედვით.
ქართულენოვან ტერმინებს ამ თავით განსაზღვრული მნიშვნელობა აქვთ მხოლოდ იმ შემთხვევაში, როცა ისინი მსხვილი მხედრული ან/და ᲛᲗᲐᲕᲠᲣᲚᲘ (მთავრული) შრიფტით არიან მითითებული.

3პროტოკოლისა და უსაფრთხოების საკითხები
3.1API კლიენტი და მისი კავშირი ამსმპ-სთან
ამ დოკუმენტის მიზნებისათვის API კლიენტი შეიძლება იყოს როგორც მმპ (ღია ბანკინგის მიზნებისათვის), ისე კორპორატიული ელექტრონული სისტემა (საკუთარ ანგარიშებზე წვდომის სერვისის მიზნებისათვის, იხ. თავი 3.2.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა"). ტერმინი API კლიენტი გამოიყენება openFinance API Framework-თან სრული თავსებადობის მიზნებისათვის.
აუცილებელია, API კლიენტი და ამსმპ ერთმანეთს უკავშირდებოდნენ დაცული არხით, რომელიც ამავდროულად უზრუნველყოფს ორივე მხარის საიმედო ავთენტიფიკაციას ერთმანეთის მიმართ. აუცილებელია, აღნიშნული განხორციელდეს [oFA-PFSM]-ის და ამ დოკუმენტის მიხედვით როგორც საკომუნიკაციო არხის, ისე გამოყენებითი პროგრამული უზრუნველყოფის დონეზე.
3.2API კლიენტის ტიპები და მხარდაჭერა
3.2.1მესამე მხარის პროვაიდერების მხარდაჭერა
აუცილებელია ამსმპ-მა უზრუნველყოს, რომ API კლიენტი, რომელიც არის მმპ და ლიცენზირებულია მოქმედი კანონმდებლობის შესაბამისად, იყოს მხარდაჭერილი ამ დოკუმენტთან თავსებადობის მიზნებისათვის.
აუცილებელია ამსმპ-მა თითოეული მმპ განიხილოს როგორც ერთი, უნიკალური API კლიენტი. აუცილებელია უნიკალურობა განისაზღვრებოდეს თავი 3.3.1, "ღია ბანკინგში ჩართული მხარეების უნიკალური იდენტიფიკატორები" თავის შესაბამისად განსაზღვრული იდენტიფიკატორით.
3.2.2საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა
უმჯობესია ამსმპ-მა უზრუნველყოს, რომ მის API-ს იყენებდნენ არამარტო მმპ-ები, არამედ ის პირები, რომლებსაც ამსმპ-ში ანგარიში აქვთ გახსნილი და სურთ საკუთარ ანგარიშთან პირდაპირი პროგრამული (API-ზე დაფუძნებული) წვდომა მმპ-ზე დაყრდნობის გარეშე. თუ ამსმპ ამგვარ API კლიენტებს მხარს უჭერს, მოქმედებს შემდეგი მოთხოვნები:
აუცილებელია აღნიშნული მომსახურება გავრცელდეს კორპორატიულ მომხმარებლებზე
უმჯობესია აღნიშნული მომსახურება გავრცელდეს ინდივიდუალურ მეწარმეებზე
შესაძლოა აღნიშნული მომსახურება გავრცელდეს ფიზიკურ პირებზე, მიუხედვად მათი ინდმეწარმის სტატუსისა
აუცილებელია ამსმპ მხარს უჭერდეს მომხმარებლის თითოეული მხარაჭერილი ტიპის შემთხვევაში რამდენიმე API კლიენტის გამოყენებას, რათა მათ სხვადასხვა ელექტრონული სისტემისათვის გამოიყენონ პირდაპირი წვდომის არხხი. აუცილებელია ამგვარი საკითხები რეგულირდებოდეს შესაბამისი სახელშეკრულებო ურთიერთობებით, როგორც თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" თავით არის განსაზღვრული.
3.3API კლიენტის უნიკალური იდენტიფიკატორი
3.3.1ღია ბანკინგში ჩართული მხარეების უნიკალური იდენტიფიკატორები
აუცილებელია, ღია ბანკინგში ჩართული მხარეები (როგორც მმპ, ისე ამსმპ) ერთმანეთის საიდენტიფიკაციოდ იყენებდნენ უნიკალურ ნომრებს, რომლებიც შედგენილია შემდეგი პრინციპით:
PSDGE-NBG-სუფიქსი
სადაც „სუფიქსი“ განისაზღვრება შემდეგნაირად:
თუ საგადახდო მომსახურების პროვაიდერი (ამსმპ, მმპ) საგადახდო მომსახურების დაწყების მომენტისათვის ჩართულია საქართველოს ეროვნული ბანკის დროის რეალურ რეჟიმში ანგარიშსწორების (RTGS) სისტემაში, მაშინ მის იდენტიფიკატორში სუფიქსი ავტომატურად (საქართველოს ეროვნულ ბანკთან შეთანხმების საჭიროების გარეშე) იქნება RTGS სისტემაში მონაწილის იდენტიფიკატორი (ამრიგად, სუფიქსები იქნება PSDGE-NBG-BAGAGE22, PSDGE-NBG-CBASGE22, PSDGE-NBG-DISNGE22 და ა.შ.).
თუ საგადახდო მომსახურების პროვაიდერი მოგვიანებით დაკარგავს RTGS სისტემის მონაწილის სტატუსს, მას უფლება ექნება გამოიყენოს აღნიშნული იდენტიფიკატორი სტატუსის დაკარგვიდან 2 წლის განმავლობაში.
თუ საგადახდო მომსახურების პროვაიდერი შეიცვლის RTGS სისტემაში მონაწილის იდენტიფიკატორს, მას უფლება ექნება გამოიყენოს ძველი იდენტიფიკატორი ცვლილებიდან 2 წლის განმავლობაში.
სხვა შემთხვევაში სუფიქსი არის საგადახდო მომსახურების პროვაიდერისათვის საქართველოს ეროვნული ბანკის მიერ მინიჭებული უნიკალური იდენტიფიკატორი. წინამდებარე დოკუმენტი არ არეგულირებს ეროვნული ბანკის მიერ აღნიშნული იდენტიფიკატორების მინიჭების წესს. თუ ასეთი საგადახდო მომსახურების პროვაიდერი, რომელსაც უკვე მინიჭებული აქვს იდენტიფიკატორი მე-2 პუნქტის შესაბამისად, მოგვიანებით ჩაერთვება RTGS სისტემაშიც, მას უფლება ექნება გამოიყენოს თავდაპირველი იდენტიფიკატორი RTGS სისტემაში ჩართვიდან 2 წლის განმავლობაში
თუ საგადახდო მომსახურების პროვაიდერი იცვლის იდენტიფიკატორს წინა პუნქტებით განსაზღვრულ რომელიმე შემთხვევაში, მან არავითარ შემთხვევაში აღარ უნდა გამოიყენოს ძველი იდენტიფიკატორი, მიუხედავად იმისა, დარჩენილი აქვს თუ არა მას ზემოთაღნიშნული პუნქტებით განსაზღვრული 2-წლიანი ვადა
3.3.2სხვა API კლიენტების უნიკალური იდენტიფიკატორები
იმ API კლიენტების უნიკალური იდენტიფიკატორის მინიჭება, რომელიც არ არის ღია ბანკინგში ჩართული მხარე, რეგულირდება ამსმპ-ის მიერ.
ამ დოკუმენტთან თავსებადობის მიზნებისათვის აუცილებელია ამსმპ იყენებდეს იმავე იდენტიფიკატორს ამ API კლიენტებთან ურთიერთობაშიც, რასაც ღია ბანკინგში გამოიყენებდა, თავი 3.3.1, "ღია ბანკინგში ჩართული მხარეების უნიკალური იდენტიფიკატორები" მიხედვით განსაზღვრულ წესით.
თუ API კლიენტი არის ლიცენზირებული მმპ და გააჩნია თავი 3.3.1, "ღია ბანკინგში ჩართული მხარეების უნიკალური იდენტიფიკატორები" მიხედვით განსაზღვრული იდენტიფიკატორი, შესაძლოა მას მიენიჭოს განსხვავებული უნიკალური იდენტიფიკატორი თავი 3.2.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა" მიხედვით განსაზღვრული მიზნით ამსმპ-სთან ურთიერთობისათვის.
3.4დაცული საკომუნიკაციო არხის მოთხოვნები
აუცილებელია, API კლიენტსა და ამსმპ-ს შორის კავშირის არხი დამყარდეს TLS პროტოკოლის მიხედვით, TLS 1.2 ან უფრო მაღალის მიხედვით.
აუცილებელია, კავშირის დამყარებისას ორივე მხარემ ერთმანეთს წარუდგინოს X.509 სერტიფიკატები.
აუცილებელია, თითოეული მხარის X.509 სერტიფიკატი შეიცავდეს თავი 3.3, "API კლიენტის უნიკალური იდენტიფიკატორი" მიხედვით განსაზღვრულ იდენტიფიკატორს და აკმაყოფილებდეს თავი 3.6, "ზოგადი მოთხოვნები სერტიფიკატების შემოწმების პროცესის მიმართ" მიხედვით დაწესებულ მოთხოვნებს.
აუცილებელია, OAuth2 პროტოკოლის რეალიზაციისას დაყრდნობილი მხარის (API კლიენტის) ავთენტიფიკაცია და ტოკენების გაცემა ხორციელდებოდეს [RFC8705]-ის მოთხოვნების შესაბამისად და ამ პროცესში გამოიყენებოდეს წინამდებარე თავით განსაზღვრული სერტიფიკატები.
აუცილებელია, OAuth2 პროტოკოლში გამოყენებული client_id პარამეტრი მკაცრად (მათ შორის სიმბოლოების რეგისტრების გათვალისწინებით) უდრიდეს თავი 3.3, "API კლიენტის უნიკალური იდენტიფიკატორი" მიხედვით განსაზღვრულ იდენტიფიკატორს.
აუცილებელია, ამსმპ-მა და API კლიენტმა სერტიფიკატებით დაიცვან ყველა ის ჰიპერბმული, რომელსაც ისინი ერთმანეთს გადასცემენ ამ დოკუმენტით განსაზღვრული კომუნიკაციის პროცესში (მაგ. ამსმპ უბრუნებს ჰიპერბმულს API კლიენტს _links სექციით).
3.5OAuth2 კლიენტების დინამიკური რეგისტრაციის დამატებითი მოთხოვნები
შესაძლოა, ამსმპ მხარს უჭერდეს კლიენტების დინამიკურ რეგისტრაციას [RFC7591]-ის და ასევე [OpenID-DR]-ის შესაბამისად და დინამიკური რეგისტრაციის მართვას [RFC7592]-ის შესაბამისად.
აუცილებელია, დინამიკური რეგისტრაციისას (თუ იგი მხარდაჭერილია) ამსმპ-მა API კლიენტს მიანიჭოს იგივე იდენტიფიკატორი (client_id) რაც მკაცრად ემთხვევა თავი 3.3, "API კლიენტის უნიკალური იდენტიფიკატორი" მიხედვით განსაზღვრულ იდენტიფიკატორს.
თუ API კლიენტი არის მმპ (თავი 3.2.1, "მესამე მხარის პროვაიდერების მხარდაჭერა" მიხედვით) და არ არსებობს წინასწარი შეთანხმება ამსმპ-სა და API კლიენტს შორის თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" შესაბამისად, დინამიკური რეგისტრაცია არავითარ შემთხვევაში არ უნდა იქნას დადგენილი რაიმე პროცესის წინაპირობად API კლიენტებისათვის.
3.6ზოგადი მოთხოვნები სერტიფიკატების შემოწმების პროცესის მიმართ
აუცილებელია, კავშირის პროცესში გამოყენებული სერტიფიკატის შემოწმება ყველა შემდგომი კრიტერიუმით:
ამსმპ-ის სერტიფიკატი გაცემულია ისეთი გამცემი ორგანოს მიერ, საქართველოს კანონმდებლობის შესაბამისად უფლებამოსილია გასცეს ღია ბანკინგის სერტიფიკატი, ხოლო სერტიფიკატი სრულად აკმაყოფილებს [ETSI TS 119 495]-ის მოთხოვნებს, მათ შორის შეიცავდეს ჩანაწერს ამსმპ-ის როლის თაობაზე. თუ API კლიენტი არის მმპ (იხ. თავი 3.2.1, "მესამე მხარის პროვაიდერების მხარდაჭერა") სერტიფიკატი გაცემულია ისეთი გამცემი ორგანოს მიერ, რომელიც აღიარებულია საქართველოში ღია ბანკინგის სერტიფიკატის სანდო გამცემად და სერტიფიკატი სრულად აკმაყოფილებს [ETSI TS 119 495]-ის მოთხოვნებს, მათ შორის შეიცავდეს სათანადო როლ(ებ)ს. თუ API კლიენტი მმპ არ არის, გამცემის საკითხი რეგულირდება შესაბამისი სახელშეკრულებო ურთიერთობებით, როგორც თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" თავით არის განსაზღვრული.
სერტიფიკატის მოქმედება არ არის შეჩერებული ან გაუქმებული, რაც დადასტურებულია სერტიფიკატების ონლაინ სტატუსის პროტოკოლის (სოსპ, Online Certificate Status Protocol, OCSP) მიხედვით [RFC6960]-ის შესაბამისად ან გაუქმებული სერტიფიკატების სიით, [RFC5280]-ის შესაბამისად.
უმჯობესია, დაცული საკომუნიკაციო არხის დამყარებისას (იხ. თავი 3.4, "დაცული საკომუნიკაციო არხის მოთხოვნები") კავშირის მონაწილე თითოეულ მხარეს (როგორც ამსმპ, ისე API კლიენტი) გააჩნდეს OCSP Stapling-ის გამოყენების საშუალება. იმ შემთხვევაში, თუ კავშირის მონაწილე ერთი მხარე კავშირის დამყარების პროცესში მიუთითებს, რომ გააჩნია აღნიშნულის მხარდაჭერა, უმჯობესია, მეორე მხარემ დააბრუნოს სოსპ ყველა საჭირო პასუხი.
აუცილებელია, დაცული იყოს სერტიფიკატების მოქმედების შემოწმების ყველა სათანადო მექანიზმი, მათ შორის სოსპ სერტიფიკატების (თუ გამოიყენება) მოქმედების შემოწმების წესი, რაც საერთაშორისო სტანდარტებითა და საუკეთესო პრაქტიკითაა განსაზღვრული.
3.7ზოგადი მოთხოვნები ჰიპერბმულების შემოწმების მიმართ
აუცილებელია, API კლიენტმა ამსმპ-ის სერვისების გამოძახების პროცესში შეამოწმოს ყველა ჰიპერბმული, რომელსაც ამსმპ მას დაუბრუნებს და დარწმუნდეს, რომ ის ნამდვილად ამ ამსმპ-ს ეკონტაქტება. კერძოდ:
აუცილებელია, API-სთან დაკავშირებული ჰიპერბმულების შემოწმება განხორციელდეს სერტიფიკატებში შესაბამისი ჩანაწერების (Common Name, Subject Alternate Name) შემოწმებისა და ამსმპ-ს ჰიპერბმულების შედარებით გზით
აუცილებელია, მომხმარებლის ავთენტიფიკაციის პროცესში OAuth2 სერვერის მეტაინფორმაციის (იხ. [RFC8414]) სისწორე დადასტურდეს ამსმპ-ს API პასუხების ავთენტურობის შემოწმების გზით თავი 4.3, "ელექტრონული შტამპის განხორციელება მოთხოვნასა და პასუხზე"-ის შესაბამისად
აუცილებელია, OAuth2 ავტორიზაციის პროცესში გამოყენებული ჰიპერბმულების შემოწმება განხორციელდეს [RFC6749] და სხვა შესაბამისი პროტოკოლების უსაფრთხოების საუკეთესო პრაქტიკების შესაბამისად
აუცილებელია, ამსმპ-მა შეამოწმოს API კლიენტის მიერ გადაცემული ყველა ჰიპერბმული და დარწმუნდეს, რომ ის ნამდვილად ამ API კლიენტთან ცვლის ინფორმაციას.
აუცილებელია, შემოწმება ემყარებოდეს შემდეგ ძირითად პრინციპს:
აუცილებელია ამსმპ-მა API ტრანზაქციის შექმნის პროცესში შეამოწმოს, გადმოსცა თუ არა API კლიენტმა Client-Redirect-URI სანამ ავთენტიფიკაციის განხორციელების მითითებას მისცემდეს API კლიენტს [oFA-PFSM] შესაბამისად. თუ Client-Redirect-URI გადმოცემული არ არის და არც API კლიენტს აქვს წინასწარ შეთანხმებული ამსმპ-სთან გადამისამართების ნაგულისხმევი მისამართი რაიმე ფორმით (მაგ. თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" მიხედვით), ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოახდინოს გადამისამართების ტიპის ავთენტიფიკაცია. ხოლო თუ API კლიენტს ცხადად აქვს მითითებული რომ მას გადამისამართების ტიპის ავთენტიფიკაცია სურს (თავსართი Client-SCA-Approach-Preference მეშვეობით), აუცილებელია ამსმპ-მა API კლიენტს შეცდომა დაუბრუნოს.
თუ Client-Nok-Redirect-URI გადმოცემული არ არის, აუცილებელია ამსმპ-მა იგულისხმოს რომ მის მოვალეობას Client-Redirect-URI ასრულებს (Client-Redirect-URI-ს გადმოცემა-არგადმოცემის საკითხი იხილეთ წინა პუნქტში)
გადამისამართებისგან განსვავებით, ამსმპ-მა არავითარ შემთხვევაში არ უნდა უარჰყოს განცალკევებული ტიპის ავთენტიფიკაცია იმ მიზეზითთ რომ Client-Redirect-URI ან/და Client-Nok-Redirect-URI არ იქნა გადაცემული.
აუცილებელია, ამსმპ-მა შეამოწმოს Client-Redirect-URI და Client-Nok-Redirect-URI (თუ ეს უკანასკნელი გადაცემულია API კლიენტის მხრიდან), კერძოდ შეადაროს იგი API კლიენტის სერტიფიკატში არსებულ ჩანაწერებს (Common Name, Subject Alternate Name)
3.8კონტრაქტი API კლიენტსა და ამსმპ-ს შორის
შესაძლოა ამსმპ-სა და API კლიენტს შორის გაფორმდეს ხელშეკრულება, რომელიც განსაზღვრავს მომსახურების პირობებს, მათ შორის უსაფრთხოების, კონფიდენციალურობისა და მონაცემთა დაცვის საკითხებს. ეს დოკუმენტი არ არეგულირებს ამგვარი ხელშეკრულების გაფორმების აუცილებლობის რაიმე წესს.
საკუთარ ანგარიშებზე პირდაპირი წვდომისათვის (იხ. თავი 3.2.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა") სავარაუდოდ ამგვარი ორმხრივი ან მრავალმხრივი ხელშეკრულების გაფორმება სავალდებულო იქნება. აღნიშნული საკითხი ამ დოკუმენტის რეგულირების მიღმაა.
შესაძლოა ამსმპ-სა და მმპ-ს შორისაც გაფორმდეს რაიმე ხელშეკრულების გაფორმებას ამ დოკუმენტით განსაზღვრულ საკითხებზე.
შესაძლოა სახელშეკრულებო ურთიერთობა სავალდებულოდ გამოაცხადოს სხვა დოკუმენტმა, რომელიც ამ დოკუმენტს ეყრდნობა (მაგ. [GBA-oFA-IG-Push])
ყველა იმ შემთხვევაში, როდესაც openFinance API Framework-ის შესაბამისი დოკუმენტი (რომელიც ამ დოკუმენტიდან არის მითითებული) სავალდებულოდ (mandatory) განსაზღვრავს HTTP თავსართ API-Contract-ID -ს, მისი გამოყენება აუცილებელია, მიუხედავად იმისა API ფუნქცია (და შესაბამისი ფუნქციონალი) ხელმისაწვდომია თუ არა უსასყიდლოდ.
თუ API კლიენტი უფლებამოსილია გამოიყენოს ესა თუ ის ფუნქცია ხელშეკრულების გარეშე, აუცილებელია მან API-Contract-ID თავსართში გადასცეს 00000000-0000-0000-0000-000000000000 მნიშვნელობა, რომელიც არის ე.წ. „ცარიელი UUID” [RFC9562]-ის მიხედვით.
4API-ს საერთო სტრუქტურა და მოთხოვნები
4.1API ბოლოწერტილების URL ფორმატირება
ამ დოკუმენტით არ განისაზღვრება API რესურსების URL-ების ფორმატირების რაიმე სპეციალური წესი, გარდა იმისა რომ აუცილებელია URL-ების ფორმატირება მოხდეს [oFA-PFSM]-ის მიხედვით. კერძოდ, აუცილებელია, გამოქვეყნებულ API რესურსების მისამართებს ჰქონდეთ შემდეგი სახე: {პრეფიქსი}/{შესაბამისი-სტანდარტით-განსაზღვრული-მისამართი}
მაგალითად, თუ ამსმპ განსაზღვრავს რომ API რესურსების URL-ების პრეფიქსია https://api.testbank.ge/latest ხოლო API რესურსის იდენტიფიკატორი არის /v2/payments/domestic/{paymentId}, საბოლოო URL იქნება ასეთი სახის: https://api.testbank.ge/latest/v2/payments/domestic/bc524d40-cc4a-44ae-93ce-fe9c267d12df
შესაძლოა ამსმპ-მა საკუთარი გადაწყვეტილებით API რესურსების პრეფიქსებში მიუთითოს ნებისმიერი რამ, მათ შორის API ვერსიების იდენტიფიკატორი, ან რაიმე სხვა მნიშვნელობა.
4.2API მოთხოვნისა და პასუხის ფორმატი
ამ დოკუმენტთან თავსებადობის მიზნებისათვის აუცილებელია, მხარდაჭერილი იყოს მოთხოვნისა და პასუხის JSON ფორმატი.
შესაძლოა, ამავე ინტერფეისის ფარგლებში ამსმპ-მ მხარი დამატებით ასევე დაუჭიროს openFinance API Framework-ით განსაზღვრულ სხვა ფორმატებსაც (მაგ. XML).
იმ შემთხვევაში, როდესაც გამოიყენება JSON ფორმატი და API პასუხი აღნიშნავს შეცდომას, აუცილებელია იგი დაბრუნდეს [RFC7807] შესაბამისად, [oFA-PFSM]-თან სრულ შესაბამისობაში. იმ შეცდომებისთვის, რომლებიც განსაზღვრულია [oFA-PFSM]-ით, აუცილებელია HTTP პასუხის კოდების მკაცრი შესაბამისობა.
მაგალითად, [oFA-PFSM]-ის მიხედვით:

აუცილებელია პროგრამული დამუშავებისას API კლიენტი დაეყრდნოს არა type არამედ code ველ(ებ)ის მნიშვნელობებს, რათა ამსმპ-ს ჰქონდეს საშუალება, შეხედულებისამებრ შეცვალოს type-ში დაბრუნებული მისამართები (მათ შორის დააბრუნოს ისინი კონტექსტის მიხედვით სხვადასხვა ენაზე).
4.3ელექტრონული შტამპის განხორციელება მოთხოვნასა და პასუხზე
აუცილებელია, მოთხოვნაზე API კლიენტმა გამოიყენოს ელექტრონული შტამპი [oFA-PFSM]-ის შესაბამისად.
აუცილებელია, მოთხოვნაზე გაცემულ პასუხზე ამსმპ-მა გამოიყენოს ელექტრონული შტამპი, რომელიც იქნება ფორმატირებული ზუსტად იმ წესის შესაბამისად, რომელიც განსაზღვრულია მოთხოვნებზე [oFA-PFSM]-ის მიხედვით, შემდეგი დამატებითი მოთხოვნების გათვალისწინებით:
JWT ტოკენში aud მტკიცების (claim) სავალდებულობა, რომელიც მოთხოვნაზე სავალდებულოა [oFA-PFSM]-ისმიხედვით, ამ დოკუმენტის ამ ვერსიასთან თავსებადობის მიზნით განსხვავებულად რეგულირდება: aud მტკიცება არავითარ შემთხვევაში არ უნდა იქნას გამოყენებული.
შესაძლოა მოთხოვნაზე გაცემულ პასუხში ამსმპ-მა ხელმოწერილი თავსართების სიაში დაამატოს ვირტუალური თავსართი (response-status) და ისე დასვას შტამპი პასუხზე. ამ შემთხვევაში აუცილებელია აღნიშნული ვირტუალური თავსართის მნიშვნელობად იგულისხმებოდეს [RFC7231]-ით განსაზღვრული HTTP პასუხის კოდი (Response Code).
აუცილებელია, სისტემის ყველა მონაწილე (ამსმპ და API კლიენტი) ახდენდეს დროის სინქრონიზაციას საერთაშორისო კოორდინირებულ დროსთან (UTC).
აუცილებელია, სისტემის ყველა მონაწილემ (ამსმპ-მა და API კლიენტმა) შეამოწმოს მიღებულ შეტყობინებებში არსებული თარიღის ველის მნიშვნელობა შეტყობინების დამუშავებამდე და შეადაროს საკუთარ სისტემაში დაფიქსირებულ დროს. იმ შემთხვევაში, თუ მიღებულ შეტყობინებაში დაფიქსირებული დრო უფრო მეტია, ვიდრე თავად მონაწილის სისტემაში დაფიქსირებული დრო და აღნიშნული სხვაობა 2 (ორ) წამს აღემატება, მოქმედებს შემდეგი წესი, შეტყობინება არავითარ შემთხვევაში არ უნდა დამუშავდეს, თუ საქართველოს ეროვნული ბანკის მიერ სხვა რამ არ არის დადგენილი.
აუცილებელია ელექტრონული შტაპის შემოწმების პროცესში შემოწდეს [ETSI EN 319 102-1]-ით განსაზღვრული ყველა კრიტერიუმი. აუცილებელლია სერტიფიკატების დასაშვებობა განისაზღვრებოდეს თავი 3.6, "ზოგადი მოთხოვნები სერტიფიკატების შემოწმების პროცესის მიმართ" მიხედვით.
4.4ენებისა და რეგიონების გამოყენება და მხარდაჭერა
აუცილებელია ამსმპ-მა ამ თავით განსაზღვრული წესები გაავრცელოს ამსმპ-სა და სმმ-ს შორის უშუალო ურთიერთობაზე ამ დოკუმენტით განსაზღვრული პირდაპირი კავშირის ფარგლებში, მაგალითად, ავთენტიფიკაციაში თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში" მიხედვით.
აუცილებელია ეს წესები ასევე ნაგულისხმევად ვრცელდებოდეს ამსმპ-სა და API კლიენტს შორის გასაცვლელ შეტყობინებებზე (რაც არ არის სმმ-ისთვის ხელმისაწვდომი), გარდა იმ შემთხვევისა როდესაც სხვაგვარად არის დარეგულირებული მათ შორის თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" შესაბამისად გაფორმებული ხელშეკრულებით, ასეთის არსებობის შემთხვევაში.
უმჯობესია, API კლიენტმა ამსმპ-ს გადასცეს Accept-Language თავსართი, რომელიც თითოეული მოთხოვნის შემთხვევაში მიუთითებს იმას, რომელ ენებს ანიჭებს უპირატესობას სმმ.
შესაძლოა ამსმპ საშუალებას აძლევდეს სმმ-ს აირჩიოს სასურველი ენა ამსმპ-ის არხში (მაგ. ინტერნეტ ან მობილბანკში) და ამ არჩევანის გათვალისწინებით წარმართოს კომუნიკაცია სმმ-სთან, მიუხედავად იმისა Accept-Language თავსართი გადმოცემულია თუ არა API მოთხოვნაში.
როდესაც Accept-Language თავსართი გადმოცემულია, თავსართი PSU-Accept-Language არავითარ შემთხვევაში არ უნდა იქნას გამოყენებული ამგვარი უპირატესობის დასადგენად ამსმპ-ს მიერ. თუმცა, თავის მხრივ, API კლიენტმა შესაძლოა API კლიენტმა მხედველობაში მიიღოს მომხმარებლის ენა Accept-Language მნიშვნელობების დასადგენად.
ეს დოკუმენტი არ აწესებს რაიმე დამატებით შეზღუდვას Accept-Language-ში გადმოცემულ მნიშვნელობებზე. ძალაშია მხოლოდ ის დათქმები და შეზღუდვები, რომლებიც HTTP პროტოკოლის განმსაზღვრელი სტანდარტებითაა დადგენილი. აუცილებელია, ამსმპ-მა დაამუშავოს Accept-Language თავსართი აღნიშნული წესების შესაბამისად.
თუ Accept-Language მითითებული არ არის, არც სმმ-ის სასურველი ენაა ცალსახად ცნობილი, მაგრამ ამსმპ-სათვის ცნობილია სმმ-ის სასურველი ენის შესახებ (მაგ. თავსართი PSU-Accept-Language მითითებულია, მომხმარებელმა ცხადად გადართო ენა მომხმარებლის ძლიერი ავთენტიფიკაციის ეკრანზე, ამსმპ-სათვის ცნობილია რომელ ენაზე იყენებს ინტერნეტ-ბანკს სმმ და ა.შ.) უმჯობესია ამსმპ დაეყრდნოს აღნიშნულ ცოდნას იმის დასადგენად, რა ენაზე სურს კომუნიკაცია სმმ-ს. სხვა შემთხვევაში აუცილებელია, ამსმპ-მა იგულისხმოს ქართული ენა, რეგიონი - საქართველო.
უმჯობესია, ამსმპ-მა დააბრუნოს Content-Language თავსართი. თუ აღნიშნული თავსართი არ დაბრუნდება, აუცილებელია API კლიენტმა იგულისხმოს ქართული ენა, რეგიონი - საქართველო.
4.5მოთხოვნების უნიკალურობა და იდემპოტენტურობა
ყველა API მოთხოვნას, რომელიც აღწერილია ამ დოკუმენტით, აუცილებელია მიჰყვებოდეს HTTP თავსართი X-Request-ID, რომელიც არის UUID ტიპის. აღნიშნული თავსართის დანიშნულებაა, ამსმპ-მა გაარჩიოს, მოთხოვნა განმეორებადია თუ არა. აუცილებელია აღნიშნული თავსართის დამუშავება მოხდეს [oFA-PFSM]-ის შესაბამისად.
4.6API რესურსები და ტრანზაქციის ცნება
ამ დოკუმენტის მიზნებისათვის API რესურსი იქმნება HTTP POST მოთხოვნის შედეგად, რომელიც მიმართულია ამსმპ-ის API-ს კონკრეტულ ბოლოწერტილზე და შექმნილია ახალი ობიექტი (მაგ. გადახდის ინიციირება [GBA-oFA-IG-PIS] -ის შესაბამისად, ანგარიშის ინფორმაციის გამოთხოვაზე თანხმობის მოთხოვნა [GBA-oFA-IG-AIS] შესაბამისად, და ა.შ.). აღნიშნულ რესურსს ამსმპ ანიჭებს უნიკალურ იდენტიფიკატორს, რომელიც შემდგომში გამოიყენება რესურსზე წვდომისათვის, მათ შორის მისი სტატუსის გამოსათხოვად. რესურსებისა და მისი იდენტიფიკატორების შექმნის პროცესი და მათი გამოყენების წესები სრულად თავსებადია [oFA-PFSM]-ის მოთხოვნებთან, მის 2.2.6 თავში მოცემული საკითხების ჩათვლით.
API რესურსების შექმნა ხდება API ტრანზაქციის ფარგლებში. ტრანზაქცია იწყება იმ მომენტში, როდესაც API კლიენტი ამსმპ-ს მიმართავს შესაბამის API ბოლოწერტილს ახალი რესურსის შექმნის მიზნით. აღნიშნული საკითხი სრულად თავსებადია [oFA-PFSM]-ის მოთხოვნებთან, მის 2.2.5 თავში მოცემული საკითხების ჩათვლით.
API ტრანზაქცია არ უნდა გაიგივდეს ფინანსურ ტრანზაქციასთან, რომელიც შეიძლება წარმოიშვას API რესურსის გამოყენების შედეგად (მაგ. გადახდის ინიციირების შემთხვევაში).
5მომხმარებლის იდენტიფიკაცია, ავთენტიფიკაცია და ავტორიზაცია
5.1მომხმარებლის იდენტიფიკაციის, ავთენტიფიკაციის და ავტორიზაციის ძირითადი პრინციპები
API ტრანზაქციების განხორციელება დაიშვება მხოლოდ საამისოდ უფლებამოსილი პირ(ებ)ის თანხმობით. აუცილებელია ყველა პირმა გაიაროს ავთენტიფიკაცია იმ მეთოდით, რომელიც ამსმპ-ის მიერ არის განსაზღვრული. მიუხედავად იმისა რომ ავთენტიფიკაციის მეთოდი შეიძლება ტექნიკურად მიწოდებული იყოს სხვა პირის მიერ, ამ დოკუმენტის მიზნებისათვის ეს მაინც ჩაითვლება ამსმპ-ის მიერ სმმ-ისათვის მინიჭებულ, დასაშვებ ავთენტიფიკაციის მეთოდად.
ავთენტიფიკაციის პროცესის წარმართვა ხდება იმის მიხედვით, თუ ვინ უნდა დაადასტუროს ესა თუ ის API ტრანზაქცია. ამსმპ განსაზღვრავს, დადასტურებას ესაჭიროება ერთი, ორი თუ მეტი პირის თანხმობა. აღნიშნულის წარმართვა ხდება ავტორიზაციის რესურსების მეშვეობით. ამ დოკუმენტით მხარდაჭერილია დეტალებისათვის იხ. თავი 5.3, "ავტორიზაციის რესურსების მართვა".
აუცილებელია თითოეულ ავტორიზაციის რესურსს, რომელიც შეიქმნება API ტრანზაქციაზე თანხმობის გამოსახატად, ადასტურებდეს ერთადერთი პირი და აღნიშნული პროცესი იყოს სინქრონული. გამონაკლისს შეადგენს ამსმპ-ის არხით განხორციელებული ავთენტიფიკაცია (იხ. თავი 5.4.5, "ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)"), რომელიც API კლიენტისა და ამსმპ-ის ურთიერთობის თვალსაზრისით გამოიხატება ერთი ავტორიზაციის რესურსით, თუმცა შესაძლოა ამსმპ-ის არხში (მაგ. ინტერნეტ ან მობილბანკში) დადასტურებას ახორციელებს ერთი ან მეტი პირი, თუმცა ეს ფაქტი API კლიენტისათვის სრულიად უხილავი, გამჭვირვალე და ასინქრონულია, ანუ API კლიენტს არ აქვს არანაირი გარანტია იმისა, კონკრეტულად როდის მოხდება დადასტურება შესაბამის ავტორიზაციის რესურსზე.
აუცილებელია ავთენტიფიკაციისა და ავტორიზაციის პროცესი საბოლოოდ დაიყვანებოდეს OAuth2-ის ტოკენებზე და API-სთან ურთიერთობისას გამოიყენებოდეს აღნიშნული ტოკენები. აღნიშნული რეგულირდება ამ თავით და მისი ქვე-თავებით, კერძოდ თავი 5.4.7, "API ტრანზაქციის რესურსის ტოკენების მიღება და გამოყენება" მიხედვით.
*შესაძლოა* API კლიენტმა გარკვეულ წინარე ეტაპზე მიღებული ტოკენი გადასცეს API ტრანზაქციის შექმნის ოპერაციას, რაც *შესაძლოა* გამოყენებული იქნას მომხმარებლის იდენტიფიკაციისთვის (იხ. <<CH_PSU_Identification>>), ასევე გარკვეული წინაპირობების შემთხვევაში - ავთენტიფიკაციისთვის (იხ. <<CH_ID_Auth_Chaining>>)
შესაძლოა API კლიენტმა ამსმპ-ს ტრანზაქციის ინიციირებასთან ერთად გადასცეს სმმ-ის კონტექსტის აღმწერი ინფორმაცია თავი 5.9, "სმმ-ის კონტექსტის წარმოდგენა PSU-* თავსართების სახით" მიხედვით ან სერვისის შესაბამის დოკუმენტში (მაგ. [GBA-oFA-IG-PIS]) განსაზღვრული წესით, რათა ამსმპ-ის ტრანზაქციების რისკის მონიტორინგის სისტემამ მიიღოს შესაბამისი გადაწყვეტილება მომხმარებლის ძლიერი ავთენტიიკაციის განხორციელების, გამონაკლისით სარგებლობის, ტრანზაქციის ავტომატური დამოწმების ან სხვა ქმედების თაობაზე, მოქმედი კანონმდებლობის, ამსმპ-ის შიდა პროცედურების, თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" მიხედვით მხარეებს შორის გაფორმებული ხელშეკრულების (ასეთის არსებობის შემთხვევაში) ან/და სხვა საფუძვლით.
5.2მომხმარებლის იდენტიფიკაცია
შესაძლოა ავტორიზაციის რესურსის დასადასტურებლად ავთენტიფიკაციის პროცესს წინ უძღოდეს სმმ-ის იდენტიფიკაცია, რაც გულისხმობს API კლიენტის მიერ იმგვარი ინფორმაციის გადაცემას ამსმპ-ისათვის, რომლითაც ხდება სმმ-ის ვინაობის უნიკალური დადგენა. ამგვარი ინფორმაციის გადაცემის გარეშე ჩაშენებული (იხ. თავი 5.4.3, "ჩაშენებული ტიპის ავთენტიფიკაცია (Embedded SCA Approach)"), განცალკევებული (იხ. თავი 5.4.4, "განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)") და ამსმპ-ის არხით (იხ. თავი 5.4.5, "ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)") ვერ განხორციელდება.
საიდენტიფიკაციო ინფორმაციის არაამომწურავი სია შემდეგია:
PSU_ID თავსართი რომელიც გადაეცემა ავტორიზაციის რესურსის შექმნის ტრანზაქციას
Authorization თავსართი, რომელიც გადაეცემა ავტორიზაციის რესურსის შექმნის ტრანზაქციას და მიუთითებს სმმ-ზე, თავი 5.4.8, "მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში"-ის შესაბამისად.
ანგარიშის იდენტიფიკატორი, რომელიც გადაეცემა API რესურსის შექმნას - ავტორიზაციის პირველი რესურსის შემთხვევაში
დებიტორის (debtor) იდენტიფიკატორი, რომელიც გადაეცემა API რესურსის შექმნას - ავტორიზაციის პირველი რესურსის შემთხვევაში
5.3ავტორიზაციის რესურსების მართვა
5.3.1თანხმობის გამოხატვის პროცესის აბსტრაქცია ავტორიზაციის რესურსებით
API ტრანზაქცია, [oFA-PFSM]-ის მიხედვით იწყება იწყება "ტრანზაქციის ინიციირების მოთხოვნით" (მაგალითად, გადახდის ინიციირების მოთხოვნა) და მის შედეგად იქმნება API რესურსი. ეს რესურსი შეიძლება ასევე შეიცვალოს [oFA-PFSM]-ით განსაზღვრული წესით. როგორც წესი, API რესურსის შექმნას და ცვლილებას (ხანდახან-გაუქმებასაც) ესაჭიროება ავტორიზაცია სმმ-ის მხრიდან.
გამომდინარე იქიდან რომ API ტრანზაქცია შეიძლება გარკვეულ შემთხვევებში მოითხოვდეს 2 ან მეტი პირის მიერ დადასტურებას (ე.წ. 4 თვალის პრინციპი), ერთ API რესურსს შეიძლება შეესაბამებოდეს ერთი ან რამდენიმე ავტორიზაციის რესურსი.
აუცილებელია ავტორიზაციის პირველი რესურსის შესაქმნელად ამსმპ მხარს უჭერდეს [oFA-PFSM] განსაზღვრავს ავტორიზაციის რესურსის შექმნის სულ მცირე ვარიანტს:
ავტორიზაციის რესურსი იქმნება API რესურსთან ერთად, იხ. თავი 5.3.2, "ავტორიზაციის რესურსის შექმნა არაცხადად";
ავტორიზაციის რესურსი იქმნება ცალკე API გამოძახებით, იხ. თავი 5.3.3, "ავტორიზაციის რესურსების ცხადად შექმნისა და დამატებითი ინფორმაციის მიწოდების მოთხოვნა ამსმპ-ის მხრიდან".
თუ ამსმპ-ს საკუთარ ელექტრონულ არხებში საკუთარ მომხმარებლებს სთავაზობს ტრანზაქციების დადასტურებას 2 ან მეტი პირის მიერ, აუცილებელია იგი ავტორიზაციის მეორე რესურსის შესაქმნელად მხარს უჭერდეს რესურსის ცხად შექმნას, იხ. თავი 5.3.3, "ავტორიზაციის რესურსების ცხადად შექმნისა და დამატებითი ინფორმაციის მიწოდების მოთხოვნა ამსმპ-ის მხრიდან", რაც არ გამორიცხავს მის მიერ პირველი რესურსის შექმნას არაცხადად, თავი 5.3.2, "ავტორიზაციის რესურსის შექმნა არაცხადად" მიხედვით.
3 ან მეტი პირის მიერ ტრანზაქციის დადასტურების მხარდაჭერის წესი და შესაბამისი ავტორიზაციის რესურსების მართვის მოდელი განისაზღვრება ამ დოკუმენტით.
დოკუმენტის ამ ვერსიის მიზნებისათვის აუცილებელია ავტორიზაციის რესურსები დადასტურდნენ მიმდევრობით და ამსმპ-მა არავითარ შემთხვევაში არ უნდა შეაქმნევინოს API კლიენტს ავტორიზაციის ახალი რესურსი, თუ ძველი რესურსის ავტორიზაცია ჯერ არ დასრულებულა
5.3.2ავტორიზაციის რესურსის შექმნა არაცხადად
ავტორიზაციის რესურსების არაცხადად შექმნას წარმოადგენს ოპტიმიზაციას ისეთი შემთხვევებისათვის, როდესაც ამსმპ-ს აქვს ყველა სათანადო ინფორმაცია მომხმარებლის ავთენტიფიკაციის დასაწყებად და იგი ამჯობინებს, API კლიენტისაგან მიიღოს ნაკლები მოთხოვნა. ამ დროს ამსმპ ავტომატურად ქმნის ავტორიზაციის რესურსს მაშინვე, როგორც კი ხდება API ტრანზაქციის შექმნა ამსმპ-ს სისტემაში (მაგ. გადახდის ინიციირების).
უმჯობესია ამსმპ-მა არაცხადად შექმნილ ავტორიზაციის რესურსს მიანიჭოს API რესურსისგან განსხვავებული იდენტიფიკატორი.
აუცილებელია, ამსმპ-მა აღნიშნული რესურსი დააბრუნოს API ტრანზაქციის შექმნის მოთხოვნის პასუხად, _links სექციაში, როგორც scaStatus ტიპის ჰიპერბმული.
აუცილებელია scaStatus ჰიპერბმული ფორმატირებული იყოს [oFA-PFSM]-ის შესაბამისად, როგორც ავტორიზაციის ქვე-რესურსის სტატუსის მოთხოვნა (GET Authorisation Status Request).

5.4მომხმარებლის ავთენტიფიკაციაის პროცესის წარმართვა
5.4.1ავთენტიფიკაციის დასაშვები ტიპები, რომელიც შეიძლება მოითხოვოს ამსმპ-მა
ავტორიზაციის რესურსის როგორც ცხადი, ისე არაცხადი შექმნისას აუცილებელია ამსმპ-მა მმპ-ს დაუბრუნოს ინფორმაცია იმის თაობაზე, რა ტიპის ავთენტიფიკაციის პროცედურა უნდა დაიწყოს API კლიენტმა. შესაძლოა ამსმპ-მა მხარი დაუჭიროს [oFA-PFSM]-ით განსაზღვრულ ნებისმიერ მეთოდს, თუმცა თუ API კლიენტი არის მმპ, ამსმპ-მა არავითარ შემთხვევაში არ უნდა აიძულოს იგი, გემოიყენოს ავტორიზაციის მეთოდები გარდა ამ თავით განსაზღვრულისა. გამონაკლისს შეადგენს მხოლოდ ის შემთხვევა, როდესაც ამსმპ-სა და API კლიენტს შორის გაფორმებულია რაიმე ხელშეკრულება, რომელიც სხვა მეთოდების გამოყენებასაც ითვალისწინებს.
გადამისამართება OAuth2-ით (OAuth2 SCA Approach) - იხ. თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში"
ჩაშენებული (Embedded SCA Approach) - იხ. თავი 5.4.3, "ჩაშენებული ტიპის ავთენტიფიკაცია (Embedded SCA Approach)"
განცალკევებული (Decoupled SCA Approach) - იხ. თავი 5.4.4, "განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)"
ამსმპ-ის არხის (ASPSP Channel SCA Approach) - იხ. თავი 5.4.5, "ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)"
ხელმოწერის (Signature SCA Approach) - იხ. თავი 5.4.6, "ავთენტიფიკაცია ციფრული ხელმოწერით"
აუცილებელია, აღნიშნული მეთოდების გამოყენებისას ამსმპ-მა დაიცვას ამ დოკუმენტის მოთხოვნები.
აუცილებელია მხარდაჭერილი იყოს გადამისამართება OAuth2-ით (OAuth2 SCA Approach). აუცილებელია იგი მხარდაჭერილი იყოს მხოლოდ პირველი ან ერთადერთი ავტორიზაციისათვის. ამსმპ-მა არავითარ შემთხვევაში არ უნდა დაუშვას გადამისამართება OAuth2-ით (OAuth2 SCA Approach) მეორე და შემდგომი ავტორიზაციის რესურსებისათვის.
შესაძლოა მხარდაჭერილი იყოს ჩაშენებული ავთენტიფიკაცია (Embedded SCA Approach). როდესაც იგი მხარდაჭერილია, ამსმპ-მა არავითარ შემთხვევაში არ უნდა დაუშვას მისი გამოყენება მეორე და შემდგომი ავტორიზაციისთვის (ანუ გამოყენება შემოიფარგლოს მხოლოდ პირველი ან ერთადერთი ავტორიზაციის შემთხვევაში).
შესაძლოა მხარდაჭერილი იყოს განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach) პირველი ან ერთადერთი ავტორიზაციისათვის.
შესაძლოა მხარდაჭერილი იყოს განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach) შეუზღუდავად, მიუხედავად იმისა ეს პირველი ავტორიზაციის შემთხვევაში ხდება თუ შემდგომის.
შესაძლოა მხარდაჭერილი იყოს ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach). შეუზღუდავად, მიუხედავად იმისა ეს პირველი ავტორიზაციის შემთხვევაში ხდება თუ შემდგომში.
ისეთი API ტრანზაქციებისათვის, რომელსაც ესაჭიროებათ მეორე ან/და შემდგომი დადასტურება, აუცილებელია ამსმპ-მა გამოიყენოს ან განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach) ან ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach). უმჯობესია მეორე და შემდგომი დადასტურებისათვის ამსმპ-მა გამოიყენოს ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach). აუცილებელია ამსმპ-ის არხით ავთენტიფიკაცია მოხდეს ერთი ავტორიზაციის რესურსის ფარგლებში, ვინაიდან ამგვარი პროცესი უზრუნველყოფს შემდგომი დადასტურების პროცესის სრულად გადატანას ამსმპ-ის არხში, რასაც შესაბამისი პასუხისმგებელი პირები უკვე შეჩვეულები არიან ოპერაციების ამსმპ-ის არხებით განხორციელების შემთხვევაში.
5.4.2OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში
აუცილებელია, ამსმპ მხარს უჭერდეს OAuth2 პროტოკოლის გადამისამართების ტიპის ავთენტიფიკაციისას (OAuth2 SCA Approach) [oFA-PFSM]-ის მოთხოვნების შესაბამისად. გადამისამართების არა-OAuth2 მეთოდი მხარდაჭერილი არ არის ამ დოკუმენტით. ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს [oFA-PFSM]-ით განსაზღვრული გადამისამართების ტიპის ავტორიზაცია oAuth2-ის გარეშე, გარდა იმ შემთხვევისა, როდესაც ამსმპ-სა და API კლიენტს შორის გაფორმებულია რაიმე ხელშეკრულება (იხ. თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის"), რომელიც ამ მეთოდს ითვალისწინებს.
აუცილებელია OAuth2 რეალიზებული იყოს [FAPI-RO] მოთხოვნების შესაბამისად.
აუცილებელია, მომხმარებლის ძლიერი ავთენტიფიკაცია ეყრდნობოდეს Authorization Code Grant -ს [RFC6749] მიხედვით.
აუცილებელია ამსმპ-მა OAuth2 ავტორიზაციის პროცესის (როგორც ცხადის, ისე არაცხადის) დაწყების მოთხოვნის პასუხად დააბრუნოს oAuthAdditionalParameters ელემენტი [oFA-PFSM] მიხედვით. აუცილებელია API კლიენტმა იხელმძღვანელოს აღნიშნულ ელემენტში დაბრუნებული ინსტრუქციებით.
შესაძლოა ამსმპ მხარს უჭერდეს [oFA-PFSM]-ით განსაზღვრულ "ავტორიზაციის მიმდევრობას დადასტურებით" (Authorisation Process with Confirmation) რომელიც გულისხმობს API კლიენტის მიერ OAuth2 ავტორიზაციის შედეგად მიღებული ტოკენის გადაცემას ამსმპ-ში (მაგ. იმისთვის, რათა ეს უკანასკნელი დარწმუნდეს რომ ავტორიზაცია წარმატებით დასრულდა). ამ შემთხვევაში მოქმედებს შემდეგი წესი:
თუ API კლიენტმა ამსმპ-ს არ გადასცა Client-Confirmation-Request-Preferred თავსართი ავტორიზაციის დაწყებისას ან ამ თავსართში გადასცა false, ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს API კლიენტისგან ტოკენის მიღების დადასტურება
თუ API კლიენტმა ამსმპ-ს Client-Confirmation-Request-Preferred თავსართში გადასცა true, შესაძლოა ამსმპ-მა მოითხოვოს API კლიენტისგან ტოკენის მიღების დადასტურება
აუცილებელია ამსმპ მხარს უჭერდეს განმეორებით ავტორიზაციას, სულ მცირე, პირველი მცდელობიდან 5 წუთის განმავლობაში, რაც გულისხმობს იმას რომ API კლიენტი OAuth2-ის scopes პარამეტრში გადმოსცემს იგივე მნიშვნელობებს, რაც წინა ჯერზე გადმოსცა და კვლავ გადაამისამართებს სმმ-ს ამსმპ-ში. ასეთ შემთხვევაში აუცილებელია ამსმპ-მა კვლავ გაატაროს ავთენტიფიკაცია სმმ-ს, მიაწოდოს მას ინფორმაცია რომ ავტორიზაცია უკვე განხორციელებულია და გადაამისამართოს კვლავ კლიენტთან OAuth2 Authorization Code Flow წესების დაცვით. აუცილებელია ამ პროცესის შედეგად API კლიენტმა მიიღოს ახალი ავტორიზაციის კოდი და ახალი ტოკენი. API კლიენტმა არავითარ შემთხვევაში არ უნდა გამოიყენოს აღნიშნული შესაძლებლობა გადახდის ინიციირების ისეთი ტიპებისათვის, რომლებიც დადასტურების შემდეგ თანხის პირდაპირ გადარიცხვას ითვალისწინებენ (ე.წ. "პირდაპირი გადახდები" [GBA-oFA-IG-PIS] მიხედვით), გარდა იმ შემთხვევისა, როდესაც API კლიენტმა API კლიენტმა ამსმპ-ს Client-Confirmation-Request-Preferred თავსართში გადასცა true და ამსპმ-მა თავის მხრივ დაადასტურა [oFA-PFSM] მიხედვით რომ მას ესაჭიროება ტოკენის მიღების დადასტურება.
აუცილებელია დადასტურების ეკრანზე ამსმპ-მა სმმ-ს მისცეს არამარტო ტრანზაქციაზე დათანხმების, ისე უარყოფის საშუალებაც.
5.4.3ჩაშენებული ტიპის ავთენტიფიკაცია (Embedded SCA Approach)
ამ დოკუმენტთან თავსებადობის მიზნებისათვის აუცილებელია, ჩაშენებული ტიპის ავთენტიფიკაცია ხორციელდებოდეს მხოლოდ ერთი ფაქტორით. ამ ავთენტიფიკაციის პროცესში ამსმპ-მა მმპ-სგან არავითარ შემთხვევაში არ უნდა მოითხოვოს ან/და მიიღოს:
ცოდნაზე დამყარებული ფაქტორი (სტატიკური პაროლი ან PIN კოდი)
სტატიკური ბიომეტრიული მონაცემი (მაგ. თითის ანაბეჭდის გამოსახულება)
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოსთხოვოს API კლიენტს ჩაშენებული ავთენტიფიკაცია, თუ სმმ-ის უნიკალური იდენტიფიკაცია (იხ. თავი 5.2, "მომხმარებლის იდენტიფიკაცია") შეუძლებელია.
თუ ამსმპ მხარს უჭერს ჩაშენებული ტიპის ავთენტიფიკაციას, აუცილებელია მან მოითხოვოს და მიიღოს მხოლოდ დინამიკურად შექმნილი ავთენტიფიკაციის მონაცემები (მაგალითად, ერთჯერადი SMS კოდი, ერთჯერადი კოდების გენერატორის მიერ გენერირებული ტოკენი, ბარათის მიერ შექმნილი კრიპტოგრამა და ა.შ.), რომელთა წარმოდგენაზე მმპ-ს დაუწესდება დროითი ლიმიტი, არაუმეტეს 5 (ხუთი) წუთისა.
შესაძლოა ამსმპ მხარს უჭერდეს მომხმარებლის ძლიერ ავთენტიფიკაციაში ჩაშენებული ტიპის ავთენტიფიკაციას. ამ შემთხვევაში აუცილებელია ჩაშენებული ავთენტიფიკაცია გამოიყენებოდეს მეორე ან შემდგომ ფაქტორად სმმ-ის ავთენტიფიკაციის პროცესში და წინა ფაქტორებით ამ სმმ-ის ავთენტიფიკაციის მტკიცებულებისთვის ამსმპ ეყრდნობოდეს Autorization თავსართში გამოყენებულ ტოკენს (იხ. თავი 5.4.8, "მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში")
ჩაშენებული ავთენტიფიკაციის მოთხოვნით ამსმპ-მა არავითარ შემთხვევაში არ უნდა გამოიწვიოს ჩიხური სიტუაცია, ანუ მან არ უნდა მოითხოვოს ჩაშენებული ავთენტიფიკაცია, როდესაც Authorization თავსართში გამოყენებული ტოკენი გამოუსადეგარია პირველი ფაქტორით ავთენტიფიკაციის დასადასტურებლად.
5.4.4განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოსთხოვოს API კლიენტს განცალკევებული ავთენტიფიკაცია, თუ სმმ-ის უნიკალური იდენტიფიკაცია (იხ. თავი 5.2, "მომხმარებლის იდენტიფიკაცია") შეუძლებელია.
აუცილებელია ამსმპ-მა იდენტიფიცირებულ მომხმარებელს გაუგზავნოს ე.წ. Push Notification იმ აპლიკაციაში, რომელსაც სმმ ჩვეულებრივ იყენებს ამსმპ-ში საკუთარ ანგარიშების წვდომისათვის. აპლიკაციის მიმართ მოთხოვნები განისაზღვრება თავი 5.8.2, "ამსმპ-ის ვალდებულებები მობილურ გარემოში განცალკევებული ავთენტიფიკაციის მხარდასაჭერად" მიხედვით.
აუცილებელია ამსმპ-მა დაადგინოს რაიმე ვადა, რა დროის განმავლობაში სმმ-მა უნდა დაადასტუროს ან უარყოს ტრანზაქცია. ამ ვადის გასვლის შემდეგ აუცილებელია ავტორიზაციის ტაიმაუტი მოხდეს და შესაბამის რესურსს მიენმიენიჭოს scaStatus=failed
5.4.5ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)
აღნიშნული ავთენტიფიკაციის მეთოდი გულისხმობს API კლიენტს ამსმპ-სთან აქვს ერთი ავტორიზაციის რესურსი, თუმცა ამსმპ-ის მხარეს შეიძლება წარიმართებოდეს საკმაოდ რთული პროცესიც, მათ შორის ორი ან მეტი პირის მიერ თანხმობების გამოხატვა, დროის განუსაზღვრელ შუალედში, და ეს სრულიად ასინქრონულად მიმდინარეობდეს.
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოსთხოვოს API კლიენტს ამსმპ-ის არხით ავთენტიფიკაცია, თუ სმმ-ის უნიკალური იდენტიფიკაცია (იხ. თავი 5.2, "მომხმარებლის იდენტიფიკაცია") შეუძლებელია.
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს ეს მეთოდი, როდესაც API კლიენტი არის მმპ და ხორციელდება პირველი ან ერთადერთი ავტორიზაცია და API კლიენტს ცხადად არ აქვს მითითებული ამ მეთოდის უპირატესობა Client-SCA-Approach-Preference თავსართით, სხვა მეთოდებთან შედარებით.
აუცილებელია, ამსმპ-მა პროცესი განაგრძოს იმ სისტემაში, რომელსაც სთავაზობს საკუთარ კლიენტურას ანგარიშების სამართავად (ინტერნეტ ან/და მობილბანკში). API კლიენტს დადასტურების ან უარყოფის სტატუსი დაუბრუნდება მას შემდეგ, რაც ავტორიზაციის პროცესი დასრულდება (ყველა პასუხისმგებელი პირი დაამოწმებს ოპერაციას ან მოხდება მისი უარყოფა). მიუხედავად იმისა, თუ რამდენი დასტური ესაჭიროება კონკრეტულ ავტორიზაციის რესურსს სინამდვილეში ამსმპ-ს თვალთახედვით, აუცილებელია რომ API კლიენტის თვალთახედვით ეს იყოს ჯამურად ერთი ავტორიზაციის რესურსი. მეტიც, API კლიენტის მხრიდან ახალი ავტორიზაციის რესურსის მოთხოვნის შემთხვევაშიც კი, ამსმპ-მა არავითარ შემთხვევაში არ უნდა შექმნას შემდგომი ავტორიზაციის რესურსი და აუცილებელია მან API კლიენტს დაუბრუნოს შესაბამისი შეცდომა.
აუცილებელია, ამსმპ-ს იმ სისტემათაგან, რომლითაც იგი საკუთარ კლიენტურას (ინტერნეტ ბანკი, მობილბანკი და სხვა) სთავაზობს ანგარიშების სამართავად, სულ მცირე ერთი იყოს აღჭურვილი იმ შესაძლებლობით, რომ დაამუშავოს ამ ტიპის ავტორიზაციის მოთხოვნები, მარეგულირებელ კანონმდებლობასთან სრულ შესაბამისობაში.
5.4.6ავთენტიფიკაცია ციფრული ხელმოწერით
ამ დოკუმენტის ამ ვერსიის მიზნებისათვის, ხელმოწერით ავთენტიფიკაცია (იხ. [oFA-PFSM]) მხარდაჭერილი არ არის.

შესაძლოა ამსმპ-მა უზრუნველყოს რომ სერვისის გამოძახების შედეგად დაბრუნებული ტოკენი იყოს "ზოგადი გამოყენებისა", ანუ მისი საშუალებით შესაძლებელია იყოს სხვა API ტრანზაქციის შესაბამისი მონაცემების დაბრუნება, თუმცა ასეთ შემთხვევაშიც კი აუცილებელია ამსმპ-მა ყოველ ჯერზე დააბრუნოს tokenExchange ჰიპერბმული, რათა API კლიენტმა შეძლოს ამ ტოკენის აღება კონკრეტული ტრანზაქციის ჭრილში და გამოყენება. ამ შემთხვევაში ამსმპ-მა არავითარ შემთხვევაში არ უნდა იქონიოს ტრანზაქციის ან/და ავტორიზაციის რესურსთან დაკავშირებული ჩანაწერები scope პარამეტრში - არც თავად ტოკენში (თუ JWT ფორმატის ტოკენია) და არც [RFC7662]-ის introspection endpoint-ის პასუხში. ამსმპ-მა არავითარ შემთხვევაში არ უნდა მისცეს ერთიდაიგივე ტოკენი ორ სხვადასხვა API კლიენტს. API კლიენტმა არავითარ შემთხვევაში არ უნდა გააკეთოს დაშვება ტოკენის კეშირების თაობაზე.
აუცილებელია ამსმპ-მ უზრუნველყოს, რომ ამ სერვისის გამოძახების შედეგად დაბრუნებული ტოკენი იყოს აქტიური და მოქმედი, სანამ მისი ვადა არ ამოიწურება. აუცილებელია ამსმპ-მ უზრუნველყოს ტოკენის მრავალჯერადად გამოყენების საშუალება. შესაძლოა ამსმპ-მა უარი განაცხადოს ტოკენის გაცემაზე და დააბრუნოს HTTP 429 შეცდომის კოდი, თუ წინა ტოკენი აქტიურია და მისი ვადის ამოწურვამდე საკმარისზე მეტი დროა დარჩენილი.
აუცილებელია ტოკენი [RFC8705]-ის შესაბამისად მიბმული იყოს API კლიენტის სერტიფიკატზე რომლითაც API კლიენტი თავი 3.4, "დაცული საკომუნიკაციო არხის მოთხოვნები" მიხედვით ავთენტიფიკაციას გაივლის ამ სერვისის გამოძახებისას.

გადახდის ინიციირების მიმდევრობის დიაგრამა
ამ გზით მიღებული ტოკენი არავითარ შემთხვევაში არ უნდა ჩაითვალოს გამოსადეგად თავი 5.4.8, "მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში"-ის ფარგლებში, ანუ მისი გამოყენება არ უნდა იყოს საკმარისი იმისთვის, რომ ამსმპ-მ მმპ-სთვის მოითხოვოს მხოლოდ მეორე ფაქტორის ავთენტიფიკაცია.
5.4.8მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში
API ტრანზაქციის შექმნის პროცესში (მაგ. ახალი გადახდის ინიციირებისას) შესაძლოა API კლიენტმა Authorization თავსართში გადასცეს მის ხელთ არსებული Bearer ტიპის ტოკენი, რათა ამსმპ-მ გამოიყენოს იგი მომხმარებლის ავთენტიფიკაციის პროცესში. ეს შეიძლება იყოს:
ავთენტიფიკაციის ტოკენი, რომელიც გაიცა თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში" შესაბამისად, იმავე API კლიენტზე, რაიმე სხვა API ტრანზაქციის ავტორიზაციისას
ავთენტიფიკაციის ტოკენი, რომელიც გაიცა [GBA-oFA-IG-eKYC] შესაბამისად
რაიმე სხვა ტოკენი, თუ ამსმპ და API კლიენტი მოქმედებენ სახელშეკრულებო ურთიერთობებით, როგორც თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" თავით არის განსაზღვრული და ამ ტოკენის გამოყენება ამ თავით განსაზღვრული მიზნებისათვის არის დაშვებული.
ამსმპ-მა არავითარ შემთხვევაში არ უნდა უარჰყოს API ტრანზაქციის შექმნა მხოლოდ იმ მიზეზით, რომ მან ვერ ამოიკითხა API კლიენტის მიერ გაცემული ტოკენი, დაადგინა რომ აღნიშნული ტოკენი მისთვის უცნობი გამცემის მიერაა გაცემული, გაცემულია მის მიერ მაგრამ გაუქმებულია სხვადასხვა მიზეზით, ის მხარს არ უჭერს ძველი ტოკენების საფუძველზე გამარტივებულ ავტორიზაციას და სხვა. ამ შემთხვევაში აუცილებელია, ამსმპ მოიქცეს ზუსტად ისე, როგორც მოიქცეოდა API კლიენტსს მიერ Authorization თავსართის გადმოუცემლობის შემთხვევაში.
აუცილებელია გადახდის ინიციირების ისეთი დავალების მიღების შემდეგ, რომელშიც Authorization სათაურში გადმოცემულია ამ თავით მხარდაჭერილი ტოკენი, მაგრამ მითითებული არ არის გადამრიცხავის ანგარიში, ამსმპ-მა ტოკენი ჩათვალოს სმმ-ის ავთენტიფიკაციის საკმარის მტკიცებულებად სადებეტო ანგარიშების სიის API კლიენტისათვის დასაბრუნებლად თავი 5.7, "არასრულიად შევსებული API ტრანზაქციის შიგთავსის დაზუსტება ტრანზაქციის ავტორიზაციის პროცესში" მიხედვით განსაზღვრული მიზნებისათთვის.
შესაძლოა ამსმპ-მა, საკუთარი უსაფრთხოებისა და რისკების მართვის ჩარჩოს, ასევე მოქმედი კანონმდებლობის შესაბამისად მიიჩნიოს რომ ეს ტოკენი გამოადეგია ერთი-ერთთი შემდეგი მიზნისათვის:
საერთოდ არ მოითხოვოს სმმ-ის შემდგომი ავვთენტიფიკაცია (ჩათვალოს რომ წინა ავთენტიფიკაცია საკმარისია - მაგალითად, დაბალრისკიანი ტრანზაქციის შემთხვევაში)
მოითხოვოს მხოლოდ მეორე ფაქტორით ავთენტიფიკაცია, თავი 5.4.1, "ავთენტიფიკაციის დასაშვები ტიპები, რომელიც შეიძლება მოითხოვოს ამსმპ-მა" მიხედვით მხარდაჭერილი ნებისმიერი ავთენტიფიკაციის მეთოდით.
ამსმპ-მა თავი 5.4.7, "API ტრანზაქციის რესურსის ტოკენების მიღება და გამოყენება" შესაბამისად გაცემული ტოკენის გამოყენება არავითარ შემთხვევაში არ უნდა ჩაითვალოს გამოსადეგად ამ თავით განსაზღვრული მიზნებისათვის.

5.5.1startAuthorisationWithPsuIdentfication და სმმ-ის საიდენტიფიკაციო მონაცემების შეყვანა
იმ შემთხვევაში, როდესაც ავტორიზაციის რესურსის შესაქმნელად ამსმპ აბრუნებს startAuthorisationWithPsuIdentfication ტიპის ჰიპერბმულს, ან ავტორიზაციის პროცესში, startAuthorisation (ან მისი რომელიმე მოდიფიკაციის) გამოძახების პასუხად _links სექციაში ბრუნდება updatePsuIdentification, API კლიენტისათვის ეს მოასწავებს რომ ამსმპ მისგან ითხოვს მომხმარებლის საიდენტიფიკაციო მონაცემების შეყვანას.
აღნიშნულ ორ მიდგომას შორის განსხვავება ისაა, რომ startAuthorisationWithPsuIdentfication შემთხვევაში სმმ-ის საიდენტიფიკაციო მონაცემების გადაცემა ხდება ავტორიზაციის რესურსის შექმნის პროცესში, ხოლო მეორე შემთხვევაში ავტორიზაციის რესურსი უკვე შექმნილია, თუმცა საჭიროებს შევსებას ინფორმაციით.
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს აღნიშნული, როდესაც მიმდინარეობს გადამისამართების ტიპის ავტორიზაცია. ან როდესაც სხვა ტიპის ავტორიზაცია მიმდინარეობს და API კლიენტის მხრიდან Authorization სათაურში გადაცემულია ტოკენი, ის ხარვეზიანი არ არის და მისი საშუალებით ცალსახადაა შესაძლებელი სმმ-ის იდენტიფიკაცია (მათ შორის იმის დადგენა, სმმ პირადი პროფილის ფარგლებში მოქმედებს თუ ორგანიზაციულის).

5.5.2startAuthorisationWithAuthenticationMethodSelection და ავთენტიფიკაციის მეთოდის შერჩევა
იმ შემთხვევაში, როდესაც ავტორიზაციის რესურსის შესაქმნელად ამსმპ აბრუნებს startAuthorisationWithAuthenticationMethodSelection ტიპის ჰიპერბმულს, ან ავტორიზაციის პროცესში, startAuthorisation (ან მისი რომელიმე მოდიფიკაციის) გამოძახების პასუხად _links სექციაში ბრუნდება selectAuthenticationMethod, API კლიენტისათვის ეს მოასწავებს რომ ამსმპ მისგან ითხოვს მომხმარებლის ავთენტიფიკაციის მეთოდის არჩევას.
აღნიშნულ ორ მიდგომას შორის განსხვავება ისაა, რომ startAuthorisationWithAuthenticationMethodSelection შემთხვევაში ავთენტიფიკაციის მეთოდის გადაცემა ხდება ავტორიზაციის რესურსის შექმნის პროცესში, ხოლო მეორე შემთხვევაში ავტორიზაციის რესურსი უკვე შექმნილია, თუმცა საჭიროებს შევსებას ინფორმაციით.
აუცილებელია, ამსმპ-მა ბმულთან ერთად იმავე პასუხში დააბრუნოს არაცარიელი scaMethods მასივი და აუცილებელია, API კლიენტმა შესთავაზოს სმმ-ს ერთ-ერთი მეთოდის არჩევა.
იმის მიხედვით, რომელი მიდგომა იყო განხორციელებული, აუცილებელია მმპ-მა ამსმპ-ს არჩეული მეთოდი გადასცეს ან ავტორიზაციის რესურსის შექმნის ბმულზე, რაც startAuthorisationWithAuthenticationMethodSelection-ით მიიღო, ან ავტორიზაციის მეთოდის ასარჩევ ბმულზე რომელიც selectAuthenticationMethod -ით მიიღო. შესავალი პარამეტრები (HTTP მოთხოვნის ტანი) ორივე შემთხვევაში აღწერილია [oFA-PFSM]-ით.
მას შემდეგ, რაც ამსმპ მიიღებს ინფორმაციას ავთენტიფიკაციის მეთოდის შესახებ, მან პასუხში უნდა დააბრუნოს ASPSP-SCA-Approach თავსართი და ასევე სხვა საჭირო ინფორმაცია [oFA-PFSM] შესაბამისად (მათ შორის) ჰიპერბმულები და განაგრძოს ურთიერთობა API კლიენტთან, ავთენტიფიკაციის არჩეული მეთოდის შესაბამისად (იხ. თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში", თავი 5.4.3, "ჩაშენებული ტიპის ავთენტიფიკაცია (Embedded SCA Approach)", თავი 5.4.4, "განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)", თავი 5.4.5, "ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)").
თუ ამსმპ ითხოვს ჩაშენებულ ავთენტიფიკაციას, ანუ ASPSP-SCA-Approach=EMBEDDED, მაშინ აუცილებელია მან _links სექციაში დააბრუნოს authoriseTransaction ტიპის ჰიპერბმული და ასევე საჭიროებისამებრ სხვა ინფორმაციაც, იხ. თავი 5.5.3, "startAuthorisationWithTransactionAuthorisation და ტრანზაქციის ავტორიზაციის ინფორმაციის მიწოდება" დეტალებისთვის (მაგალითად, challenge ინფორმაცია, თუ არჩეულია შეკითხვა-პასუხის ტიპის ავთენტიფიკაციის მეთოდი).

იმ შემთხვევაში, როდესაც ავტორიზაციის რესურსის შექმნის პასუხად ან ავტორიზაციის პროცესში, startAuthorisation (ან მისი რომელიმე მოდიფიკაციის) გამოძახების პასუხად _links სექციაში ბრუნდება updateResourceByDebtorAccountResource, API კლიენტისათვის ეს მოასწავებს რომ ამსმპ მისგან ითხოვს სადებეტო ანგარიშისა და ვალუტის ინფორმაციის შეყვანას.
ასეთ შემთვევაში აუცილებელია პროცესი წარიმართოს თავი 5.7.4, "API ტრანზაქციის შიგთავსის დაზუსტება წინარე ავთენტიფიკაციის საფუძველზე" შესაბამისად.
ამსმპ-მა არავითარ შემთხვევაში არ უნდა მოითხოვოს აღნიშნული, როდესაც დაკმაყოფილებული არ არის რომელიმე წინაპირობა, რაც თავი 5.7.4, "API ტრანზაქციის შიგთავსის დაზუსტება წინარე ავთენტიფიკაციის საფუძველზე" მიხედვით არის მითითებული
5.7არასრულიად შევსებული API ტრანზაქციის შიგთავსის დაზუსტება ტრანზაქციის ავტორიზაციის პროცესში
აუცილებელია ამსმპ მხარს უჭერდეს მექანიზმებს, რომლის საშუალებითაც API კლიენტს შეეძლება დააზუსტოს არასრულიად შევსებული API ტრანზაქციის გარკვეული ატრიბუტები თუმცა მხოლოდ პირველი ავტორიზაციის პროცესში. დეტალები განისაზღვრება ამ თავის ქვე-თავებით.
შენიშვნა: ამ თავითა და მისი ქვეთავებით არ დგინდება რომელიმე ავთენტიფიკაციის მეთოდის სავალდებულობა. ქვე-თავები მოთოვნებს აწესებენ იმ დათქმით რომ ამსმპ ამა თუ იმ ავთენტიფიკაციის მეთოდს მხარს უჭერს ამ დოკუმენტის, რაიმე სხვა სტანდარტია, მარეგულირებელი კანონმდებლობის მოთოვნების დაკმაყოფილების, ან/და API კლიენტთან გაფორმებული ხელშეკრულების შესაბამისად (როგორც თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" თავით არის განსაზღვრული).
ერთადერთი ავთენტიფიკაციის მეთოდი, არასრულად შევსებული API ტრანზაქციის წინაპირობად არ აცხადებს, სულ, მცირე, სმმ-ის იდენტიფიკაციას, არის გადამისამართების ტიპის ავთენტიფიკაცია (იხ. თავი 5.7.1, "API ტრანზაქციის შიგთავსის დაზუსტება გადამისამართების ტიპის ავთენტიფიკაციისას"). შესაბამისად, ისეთ შემთხვევებში როდესაც ტრანზაქცია არასრულადაა შევსებული და API კლიენტს არ გადმოუცია Client-SCA-Approach-Preference თავსართი ან მისი საშუალებით ნებადართულად ხდის გადამისამართებას, უმჯობესია ამსმპ-მა მოახდინოს გადამისამართების ტიპის ავთენტიფიკაცია.
ყველა სხვა ავთენტიფიკაციის შემთხვევაში წინაპირობა არის სმმ-ის ცალსახა იდენტიფიკაციის შესაძლებლობა (ხოლო თავი 5.7.4, "API ტრანზაქციის შიგთავსის დაზუსტება წინარე ავთენტიფიკაციის საფუძველზე" შემთხვევაში ავთენტიფიკაციაც კი). შესაბამისად, თუ ამ თავის მოთხოვვნების შესაბამისად, გადამისამართება დაშვებული არ არის და ამავდროულად სმმ-ის ცალსახა იდენტიფიკაცია შეუძლებელია, აუცილებელია ამსმპ-მა ჯერ თავი 5.5.1, "startAuthorisationWithPsuIdentfication და სმმ-ის საიდენტიფიკაციო მონაცემების შეყვანა" მოითხოვოს სმმ-ის იდენტიფიკაცია.
თუ API კლიენტის მიერ გადმოცემულია Client-SCA-Approach-Preference თავსართი და მისი საშუალებით ნებადართული არაა გადამისამართება, მაგრამ ჩამონათვალში არსებულთაგან არც ერთი ავთენტიფიკაციის მეთოდი არაა ხელმისაწვდომი, აუცილებელია ამსმპ-მა მოახდინოს გადამისამართების ტიპის ავთენტიფიკაცია.
5.7.1API ტრანზაქციის შიგთავსის დაზუსტება გადამისამართების ტიპის ავთენტიფიკაციისას
როდესაც არასრულად შევსებული API ტრანზაქციის პირველი დადასტურება ხდება OAuth2 გადამისამართების ტიპის ავთენტიფიკაციის მეთოდით თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში" შესაბამისად, დაზუსტებას დაქვემდებარებული ველები განისაზღვრება შესაბამისი დოკუმენტაციით. მაგალითად:
ანგარიშები რომელზეც გამოიხატება ინფორმაციის გაზიარების თანხმობა (ამსმპ-ში გამოხატული თანხმობა) [GBA-oFA-IG-CONS] შესაბამისად;
სადებეტო ანგარიში და ვალუტაა საგადახდო დავალებაში, [GBA-oFA-IG-PIS] შესაბამისად.
ეს დოკუმენტი არ აწესებს რაიმე შეზღუდვას იმაზე, კონკრეტულად რისი დაზუსტებაა შესაძლებელი გადამისამართების ტიპის ავთენტიფიკაციისას და რისი არა.
აუცილებელია ამსმპ მხარს უჭერდეს ამ შესაძლებლობას ყოველგვარი წინაპირობის გარეშე
5.7.2API ტრანზაქციის შიგთავსის დაზუსტება განცალკევებული ტიპის ავთენტიფიკაციისას, მობილური აპლიკაციით
როდესაც არასრულად შევსებული API ტრანზაქციის პირველი დადასტურება ხდება განცალკევებული ავთენტიფიკაციის მეთოდით თავი 5.4.4, "განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)" შესაბამისად, დაზუსტებას დაქვემდებარებული ველები განისაზღვრება შესაბამისი დოკუმენტაციით. მაგალითად:
ანგარიშები რომელზეც გამოიხატება ინფორმაციის გაზიარების თანხმობა (ამსმპ-ში გამოხატული თანხმობა) [GBA-oFA-IG-CONS] შესაბამისად;
სადებეტო ანგარიში და ვალუტაა საგადახდო დავალებაში, [GBA-oFA-IG-PIS] შესაბამისად.
ეს დოკუმენტი არ აწესებს რაიმე შეზღუდვას იმაზე, კონკრეტულად რისი დაზუსტებაა შესაძლებელი განცალკევებული ტიპის ავთენტიფიკაციისას და რისი არა.
აუცილებელია ამსმპ მხარს უჭერდეს ამ შესაძლებლობას იმ შემთხვევაში, როდესაც დაკმაყოფილებულია ყველა შემდეგი პირობა:
შესაძლებელია სმმ-ის ცალსახა იდენტიფიკაცია თავი 5.2, "მომხმარებლის იდენტიფიკაცია" შესაბამისად (PSU_ID-თ, Authorization თავსართში გადმოცემული ტოკენით და სხვა)
API ტრანზაქციაში Authorization თავსართში გადაცემული ტოკენი მისაღები ან/და საკმარისი არაა სმმ-ის პირველი ფაქტორით ავთენტიფიკაციისათვის თავი 5.4.8, "მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში" შესაბამისად, ან ტოკენი საერთოდ არ ყოფილა გადაცემული
5.7.3API ტრანზაქციის შიგთავსის დაზუსტება ამსმპ-ის არხით ავთენტიფიკაციისას
როდესაც არასრულად შევსებული API ტრანზაქციის პირველი დადასტურება ხდება განცალკევებული ავთენტიფიკაციის მეთოდით თავი 5.4.5, "ამსმპ-ის არხით ავთენტიფიკაცია (ASPSP Channel SCA Approach)" შესაბამისად, პროცესი სრულად ემთხვევა თავი 5.7.2, "API ტრანზაქციის შიგთავსის დაზუსტება განცალკევებული ტიპის ავთენტიფიკაციისას, მობილური აპლიკაციით" შესაბამისად აღწერილს, იმ გამონაკლისით რომ ამსმპ არაა შეზღუდული მხოლოდ მობილური აპლიკაციით და მას შეუძლია ტრანზაქციის დეტალების დაზუსტება ნებისმიერ არხში მიიღოს, რაც სმმ-ისთვის ხელმისაწვდომია ამ ტიპის ავთენტიფიკაციისას: აუცილებელია ამსმპ მხარს უჭერდეს სულ მცირე ერთ ასეთ არხს.
5.7.4API ტრანზაქციის შიგთავსის დაზუსტება წინარე ავთენტიფიკაციის საფუძველზე
ამ თავით განსაზღვრული პროცედურა დასაშვებია მხოლოდ მაშინ, როდესაც დაკმაყოფილებულია ყველა შემდეგი პირობა:
API ტრანზაქცია არის გადახდის ინიციირება [GBA-oFA-IG-PIS] შესაბამისად
საგადახდო დავალებაში API კლიენტმა გამოტოვა მხოლოდ სადებეტო ანგარიში და ვალუტა
API ტრანზაქციაში Authorization თავსართში გადაცემული ტოკენი თავი 5.4.8, "მომხმარებლის წინარე ავთენტიფიკაციის გამოყენება იდენტიფიკაციისა და ავთენტიფიკაციის პროცესში" შესაბამისად და ამსმპ-ს უფლება აქვს, ამ ტოკენის წარდგენის ფაქტი ჩათვალოს, სულ მცირე, საკმარისი დონის ავთენტიფიკაციად საიმისოდ რომ API კლიენტთან გააზიაროს საგადახდო ანგარიშები, ნაშთითა და ვალუტით.
აუცილებელია ამსმპ-მა API კლიენტს ავტორიზაციის რესურსის შექმნის შემდეგ (არაცხადის შემთხვევაში - API ტრანზაქციის შექმნის შემდეგ) დაუბრუნა accounts ატრიბუტი, რომელშიც მითითებულია სმმ-ისთვის ხელმისაწვდომი ყველა ანგარიში, მათ შორის, არამარტო მისი პირადი ანგარიშები, არამედ კორპორაციული ანგარიშებიც, თუ ისინი ამ სმმ-ისთვის ამ ტიპის ტოკენით ავთენტიფიკაციისათვის ხელმისაწვდომია (მაგ. იმ შემთხვევაში, როდესაც ამსმპ-ს გააჩნია მომხმარებლების ერთიანი ბაზა ფიზიკური და იურიდიული პირებისათვის).

მას შემდეგ, რაც სმმ აირჩევს ანგარიშს და ვალუტას, აუცილებელია ამსმპ-მა შეავსოს გადახდის ინიციირების მოთხოვნის შესაბამისი ველები (როგორც წესი, debtorAccount და currency). ამის შემდეგ პროცესი შეიძლება გაგრძელდეს ორი შესაძლო გზით:
ავტორიზაციის პროცესი ამ ავტორიზაციის რესურსისათვის ჩაითვალოს დასრულებულად (თუ პრე-ავტორიზაცია საკმარისია ამ ტიპის ავტორიზაციისათვის)
განაგრძოს ავტორიზაციის პროცესი ამ ავტორიზაციის რესურსისათვის (მაგ. მოითხოვოს ჩაშენებული ავთენტიფიკაცია მეორე ფაქტორით, განცალკევებული ავთენტიფიკაცია, გადამისამართება და ა.შ.). ამსმპ-მა ეს დანაწესი არავითარ შემთხვევვაში არ უნდა ჩათვალოს სმმ-ისგან დამატებითი, არასაჭირო ავთენტიფიკაციის ან ავთენტიფიკაციის მოთხოვნის ნებართვად.
5.8მობილურ გარემოში (iOS, Android) ავთენტიფიკაციის მხარდაჭერა
5.8.1ამსმპ-ის ვალდებულებები მობილურ გარემოში OAuth2 გადამისამართების ტიპის ავთენტიფიკაციის მხარდასაჭერად
აუცილებელია, ამსმპ-მა საკუთარ მობილურ აპლიკაციაში, რომელსაც იგი ჩვეულებრივ სთავაზობს საკუთარ მომხმარებელს, მხარი დაუჭიროს თავი 5.4.2, "OAuth2-ის გამოყენება გადამისამართების ტიპის ავთენტიფიკაციის შემთხვევაში"-ით განსაზღვრულ თანხმობის გამოხატვას. მომხმარებელს არავითარ შემთხვევაში არ უნდა დასჭირდეს დამატებითი აპლიკაციის ჩამოტვირთვა აღნიშნული ფუნქციით სარგებლობისათვის.
აუცილებელია, ამსმპ-მა მობილურ აპლიკაციაში დაამატოს ყველა OAuth2 ავტორიზაციის ბოლოწერტილი (authorization_endpoint), რომელსაც დააბრუნებს scaOAuth ჰიპერბმულით (_links ატრიბუტიდან) მითითებულ მეტაინფორმაციაში, როგორც:
უნივერსალური ბმულები (Universal Links) iOS ოპერაციული სისტემისათვის
აპლიკაციის ბმულები (App Links) Android ოპერაციული სისტემისათვის
შენიშვნა: აზრის გარკვეულობისათვის, დოკუმენტში აღნიშნული მექანიზმები ჯამურად მოხსენიებული იქნება როგორც „აპლიკაციის მიერ მისაკუთრებული ბმულები“ (Application-claimed links).
აუცილებელია ბმულები დაცული იყოს https სქემით და ზოგადად აკმაყოფილებდეს ყველა მოთხოვნას რასაც ამ დოკუმენტითა და <oFA-PFSM>>-ით არ ის განსაზღვრული უყენებს OAuth2 ავტორიზაციის მიმართ (state პარამეტრი, PKCE და ა.შ.).
იმ შემთხვევაში, თუ მომხმარებელს დაინსტალირებული არ აქვს ამსმპ-ის მობილური აპლიკაცია, აუცილებელია პროცესი სრულფასოვნად ფუნქციონირებდეს მობილურ ბროუზერში. მათ შორის გათვალისწინებული იყოს მობილური ტელეფონის ეკრანის ზომის თავისებურებები.
აუცილებელია, საკუთარი მობილური აპლიკაციის შემუშავების პროცესში ამსმპ დარწმუნდეს რომ მისი მობილური აპლიკაცია იხსნება და თანხმობის გამოხატვა სრულფასოვნად მუშაობს, მათ შორის, იმ შემთხვევაშიც, როდესაც კლიენტი-აპლიკაცია მობილურ ბროუზერში მუშაობს და ავტორიზაციის ბოლოწერტილის ბმულს ხსნის.
აუცილებელია, საკუთარი მობილური აპლიკაციის შემუშავების პროცესში ამსმპ დარწმუნდეს რომ თუ პროცესის ინიცირების დასაწყისში Client-Redirect-URI და Client-Nok-Redirect-URI თავსართებით მიღებული ჰიპერბმულები ოპერაციულ სისტემაში რეგისტრირებულია როგორც „აპლიკაციის მიერ მისაკუთრებული ბმულები“, ავტორიზაციის პროცესის დასრულება გადამისამართებას გააკეთებს შესაბამის მობილურ აპლიკაციაში და არა ვებ-ბროუზერში.
5.8.2ამსმპ-ის ვალდებულებები მობილურ გარემოში განცალკევებული ავთენტიფიკაციის მხარდასაჭერად
აუცილებელია, ამსმპ-მა საკუთარ მობილურ აპლიკაციაში, რომელსაც იგი ჩვეულებრივ სთავაზობს საკუთარ მომხმარებელს, მხარი დაუჭიროს თავი 5.4.4, "განცალკევებული ავთენტიფიკაცია (Decoupled SCA Approach)"-ით განსაზღვრულ თანხმობის გამოხატვას. მომხმარებელს არავითარ შემთხვევაში არ უნდა დასჭირდეს დამატებითი აპლიკაციის ჩამოტვირთვა აღნიშნული ფუნქციით სარგებლობისათვის.
აღნიშნული მიზნის მისაღწევად აუცილებელია ამსმპ-ის მობილური აპლიკაცია სმმ-ს სთავაზობდეს გადაწოდებული შეტყობინებების (Push Notifications) არხის საშუალებით სმმ-ის განცალკევებული ავთენტიფიკაციის განხორციელებას, მათ შორის, არასრულად შევსებული API ტრანზაქციების შიგთავსის დაზუსტებას (იხ. თავი 5.7.2, "API ტრანზაქციის შიგთავსის დაზუსტება განცალკევებული ტიპის ავთენტიფიკაციისას, მობილური აპლიკაციით").
აუცილებელია ამსმპ-ს ჰქონდეს მექანიზმი, რომლის საშუალებითაც იგი გონივრულ ვადაში აღმოაჩენს მობილური აპლიკაციის დეინსტალაციისა და გადაწოდებული შეტყობინებების (Push Notifications) არხის გაუქმების ფაქტს და შესაბამისად, ამ შემთხვევაში API კლიენტებს აღარ შესთავაზებს შესაბამისი სმმ-ის განცალკევებულ ავთენტიფიკაციას.
თუ API კლიენტი API ტრანზაქციის შექმნისას გადმოსცემს Client-Redirect-URI ან/და Client-Nok-Redirect-URI თავსართებს, აუცილებელია ავთენტიფიკაციისა და ავტორიზაციის პროცესის დასრულების შემდეგ ამმსმპ-ის მობილურმა აპლიკაციამ მობილურ გარემოში გახსნას ეს ბმულები. აუცილებელია
აუცილებელია, საკუთარი მობილური აპლიკაციის შემუშავების პროცესში ამსმპ დარწმუნდეს რომ თუ პროცესის ინიცირების დასაწყისში Client-Redirect-URI და Client-Nok-Redirect-URI თავსართებით მიღებული ჰიპერბმულები ოპერაციულ სისტემაში რეგისტრირებულია როგორც „აპლიკაციის მიერ მისაკუთრებული ბმულები“, ავტორიზაციის პროცესის დასრულება გადამისამართებას გააკეთებს შესაბამის მობილურ აპლიკაციაში და არა ვებ-ბროუზერში.
5.8.3გამომძახებელ აპლიკაციებში ამსმპ-ის აპლიკაციის ინტეგრაცია (ინფორმაციული)
გამომძახებელი აპლიკაციის შემუშავებისას მწარმოებელი უნდა დარწმუნდეს რომ მისი მობილური აპლიკაცია მობილური პლატფორმის/ბროუზერის პლატფორმის სტანდარტების შესაბამისად ხსნის ამსმპ-ის აპლიკაციის მიერ მისაკუთრებულ ბმულებს, რომლებიც მას დაუბრუნდება OAuth2 მეტაინფორმაციით, როგორც ავტორიზაციის ბოლოწერტილი (authorization_endpoint).
გამომძახებელმა აპლიკაციამ თავადაც უნდა იზრუნოს, რათა დაარეგისტრიროს მისაკუთრებული ბმულები, კერძოდ ბმულები რომელსაც იგი გადასცემს ამსმპ-ს Client-Redirect-URI და Client-Nok-Redirect-URI თავსართებში. მწარმოებელმა უნდა გაითვალისწინოს, რომ თუკი აღნიშნულ თავსართებში ისეთი ჰიპერბმულებს გადასცემს, რომლებიც მისაკუთრებულ ბმულებად არაა რეგისტრირებულ მის აპლიკაციაში, ავტორიზაციის პროცესის დასრულების შემდეგ ჰიპერბმულები მობილურ ბროუზერებში გაიხსნება.
რეკომენდებულია, ამგვარი ინტეგრაციის სურვილის შემთხვევაში API კლიენტმა გადახდის ინიცირების და ანგარიშის ინფორმაციაზე წვდომის თანხმობის რეგისტრაციის ოპერაციებს გააყოლოს Client-SCA-Approach-Preference თავსართი [oFA-PFSM]-ის შესაბამისად.

აუცილებელია მხარდაჭერილი იყოს "გადახდისა" და "გადახდის ინიციირების" რესურსების სტატუსების ნოტიფიკაცია. უმჯობესია API რესურსები რომლებისთვისაც მხარდაჭერილია სტატუსის გადაწოდება -ით განსაზღვრული დანარჩენი რესურსების მხარდაჭერაც.
6.2API რესურსის სტატუსის გადაწოდების მხარდაჭერა
როდესაც ამსმპ მხარს უჭერდეს API რესურსის სტატუსის გადაწოდების მექანიზმს, აუცილებელია, იგი მას სთავაზობდეს მესამე მხარის პროვაიდერებს (იხ. თავი 3.2.1, "მესამე მხარის პროვაიდერების მხარდაჭერა"). შესაძლოა, ამსმპ მხარს უჭერდეს API რესურსის სტატუსის გადაწოდების მექანიზმს მესამე მხარის პროვაიდერებისათვის მხოლოდ სახელშეკრულებო ურთიერთობის ფარგლებში (იხ. თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის"). უმჯობესია, ამსმპ მხარს უჭერდეს API რესურსის სტატუსის გადაწოდების მექანიზმს იმ API კლიენტებისთვისაც, რომლებიც არ არიან მესამე მხარის პროვაიდერები (იხ. თავი 3.2.2, "საკუთარ ანგარიშზე პირდაპირი წვდომის მხარდაჭერა").
6.3API რესურსის სტატუსის გადაწოდების მოთხოვნა API კლიენტის მიერ
იმისათვის, რომ ამსმპ-მა API კლიენტს გადააწოდოს API რესურსის სტატუსი, აუცილებელია API კლიენტმა მოთხოვნის თავსართებში, რომელიც გადაეცემა თავი 6.1, "API რესურსები, რომლებისთვისაც მხარდაჭერილია სტატუსის გადაწოდება"-ით მითითებულ ბოლოწერტილებს, სხვა თავსართებთან და მოთხოვნის ტანთან (როგორც განსაზღვრულია შესაბამისი დოკუმენტაციით) ასევე გადასცეს ერთდროულად Client-Notification-URI და Client-Notification-Content-Preferred თავსართები, [oFA-PFSM]-ის 12.4 თავში მითითებული წესით, იმ ბოლოწერტილების გამოძახებისას, რომლებიც API რესურსები რომლებისთვისაც მხარდაჭერილია სტატუსის გადაწოდება-ით არის მითითებული. Client-Notification-URI-ს ფორმატირების წესი განისაზღვრება თავი 6.10, "API კლიენტის მიერ მისაღები შეტყობინებების URL-ების მოთხოვნები" შესაბამისად. Client-Notification-Content-Preferred-ის ფორმატი განისაზღვრება [oFA-PFSM]-ით (მხარდაჭერილია ერთი ან რამდენიმე მნიშვნელობა), დამატებითი განმარტებებისათვის იხ. რესურსის სტატუსის გადაწოდების სცენარები
თუ მოთხოვნაში Client-Notification-URI და Client-Notification-Content-Preferred თავსართებიდან მხოლოდ ერთია მითითებული, ამსმპ-მა არავითარ შემთხვევაში არ უნდა მიაქციოს ყურადღება მის არსებობას და მოიქცეს ისე, თითქოს არც ერთი თავსართი არ გადმოცემულა.

PROCESS
რესურსის სტატუსის თითოეული ცვლილება, რაც კი ამსმპ-ის სისტემაში აისახება (და შეიძლება დაბრუნდეს შესაბამისი სტატუსის გამოთხოვისას)
LAST
შეტყობინება გაიგზავნება მხოლოდ მაშინ, როდესაც რესურსი ამა თუ იმ სტატუსს ავტომატურ რეჟიმში მიაღწევს უშუალოდ ავტორიზაციის პროცესის მთლიანად დასრულების შედეგად. მაგალითად, API კლიენტთან შეტყობინება გაიგზავნება თანხმობის რესურსის ([GBA-oFA-IG-CONS] მიხედვით) სრული წარმატებული ავტორიზაცის შემდეგ. თუ შემდგომში მოხდება სტატუსის გაუქმება, API კლიენტთან შეტყობინება აღარ გაიგზავნება.
MAJOR
რესურსის საბოლოო სტატუსი, რომელსაც აღნიშნული რესურსი მიაღწევს ნაწილობრივი და სრული ავტორიზაციის შედეგად და ასევე ყველა შემდეგი სტატუსის ცვლილება. LAST-ისგან განსხვავებით, ამ შემთხვევაში API კლიენტთან შეტყობინება გაიგზავნება, მაგალითად, თანხმობის გაუქმების შემთხვევაშიც.
SCA სცენარის მხარდაჭერა აუცილებელია, რაც ნიშნავს რომ თუ API კლიენტი მოითხოვს SCA სტატუსის გადაწოდებას, აუცილებელია ამსმპ-მა დაუდასტუროს აღნიშნული (ASPSP-Notification-Content ატრიბუტში დაბრუნების გზით) და გაუგზავნოს შესაბამისი შეტყობინებები.
უმჯობესია ამსმპ-ს ჰქონდეს PROCESS სცენარის მხარდაჭერა.
თუ ამსმპ მხარს უჭერს PROCESS სცენარს, LAST და MAJOR სცენარების მხარდაჭერა არააუცილებელია.
თუ ამსმპ მხარს არ უჭერს PROCESS სცენარს, აუცილებელია LAST და MAJOR სცენარის მხარდაჭერა.
იმ შემთხვევაში, როდესაც ამსმპ მხარს არ უჭერს PROCESS სცენარს და API კლიენტი მას მოითხოვს (მიუთითებს Client-Notification-Content-Preferred თავსართში), აუცილებელია ამსმპ-მა დააბრუნოს SCA და MAJOR სტატუსები ერთდროულად(ASPSP-Notification-Content ატრიბუტში, [oFA-PFSM] -ით მითითებული ფორმით) და გაგზავნოს შესაბამისი შეტყობინებები, როდესაც აღნიშნული საჭირო გახდება.
6.4SCA სცენარი არაცხადი ავტორიზაციისას
იმ შემთხვევაში, თუ შეტყობინებისას განსაზღვრულია SCA სცენარი, აუცილებელია ამსმპ-მა გაგზავნოს შეტყობინებები იმისდა მიუხედავად, ავტორიზაცია განხორციელდა ავტორიზაციის რესურსის ცხადი თუ არაცხადი შექმნის გზით. აუცილებელია შესაბამის შეტყობინებაში გადაეწოდოს ავტორიზაციის რესურსის იდენტიფიკატორი (მათ შორის, არაცხადად შექმნილი იდენტიფიკატორი).
6.5რესურსის გაუქმებასთან დაკავშირებული საკითხები
ყველა რესურსს, რომელიც მოცემულია API რესურსები რომლებისთვისაც მხარდაჭერილია სტატუსის გადაწოდება-ში და სვეტში "გაუქმების სპეციალური რეჟიმი" მითითებული აქვს "არა", შესაბამისი რესურსის გაუქმების (HTTP DELETE) მოთხოვნა (როცა იგი განსაზღვრულია სტანდარტის შესაბამისი ჩანაწერით) ცალკე არ იღებს Client-Notification-URI და Client-Notification-Content-Preferred თავსართებს და აუცილებელია ამსმპ-მა აღნიშნულ თავსართებს ყურადღება არ მიაქციოს, თუ API კლიენტი მათ გადასცემს მოთხოვნაში.
როდესაც სვეტში "გაუქმების სპეციალური რეჟიმი" მითითებულია "დიახ", ეს ნიშნავს რომ API კლიენტმს უფლება აქვს, გაუქმების მოთხოვნაში გადმოსცეს Client-Notification-URI და Client-Notification-Content-Preferred. ეს ნიშნავს რომ ამსმპ-მა გაუქმების მოთხოვნასთან დაკავშირებული სტატუსები API კლიენტს ისე უნდა აცნობოს რომ არავითარ შემთხვევაში არ უნდა ჩაანაცვლოს რესურსის შექმნისას დაწესებული ნოტიფიკაციები და ამის ნაცვლად აუცილებელია ამსმპ-მა ეს აღიქვას როგორც დამატებით დავალებად სტატუსის გადაწოდებასთან დაკავშირებით. მაგალითად, თუ საგადახდო დავალების რესურსის შექმნისას გადმოცემული იყო PROCESS (რაც ნიშნავს რომ API კლიენტმა უნდა მიიღოს შესაბამისი გადახდის სტატუსის ყოველი ცვლილება) და შემდეგ გაუქმებისას Client-Notification-URI-ში მოვა განსხვავებული მისამართი და Client-Notification-Content-Preferred-ში მოვა რაიმე სხვა ჩამონათვალი, ამსმპ-მა ინფორმაცია ორ სხვადასხვა ბოლოწერტილზე უნდა გაგზავნოს, კონფიგურაციის შესაბამისად.
6.6რესურსის სტატუსის შეტყობინების შიგთავსი
აღნიშნული საკითხი რეგულირდება [oFA-PFSM]-ის 12.6 თავის შესაბამისად. ამ თავში მოცემულია დამატებითი მოთხოვნები.
როდესაც გადაეცემა ინფორმაცია ავთენტიფიკაციის რესურსების შესახებ (SCA სცენარი), აუცილებელია შევსებული იყოს scaStatus და debtorDecisionDateTime ატრიბუტები და authorisationId ან cancellationId იმის მიხედვით, რესურსის ავტორიზაცია ხდება თუ გაუქმების ავტორიზაცია (თუ გაუქმების ავტორიზაცია მხარდაჭერილია აღნიშნული რესურსისათვის, მაგალითად გადახდის ინიციირებისათვის). ასევე აუცილებელია შევსებული იქნას იმ რესურსის იდენტიფიკატორები.
აუცილებელია რესურსის იდენტიფიკატორები შეივსოს შემდეგი წესით (როგორც SCA ისე PROCESS და LAST სცენარებში):
paymentId - გადახდის რესურსის ან გადახდის რესურსის ინიციირების ინიციირების რესურსის სტატუსის შემთხვევაში
initiationId, რომელიც Max70Txt ტიპის უნდა იყოს - როდესაც რესურსის სტატუსის გადაწოდება ხდება ინიციირების მოთხოვნისას გადადებული და განმეორებადი გადახდებისათვის. აუცილებელია ამ დროს paymentId-ც იყოს შევსებული
consentId - თანხმობის რესურსის შემთხვევაში
subscriptionId გამოწერის რესურსის სტატუსის ან გამოწერის ელემენტის რესურსის სტატუსის შემთხვევაში
subscriptionEntryId გამოწერის ელემენტის რესურსის სტატუსის შემთხვევაში (ამ დროს აუცილებელია შევსებული იყოს subscriptionId-ც)
როდესაც გამოყენებულია PROCESS ან LAST სცენარი, გადაწოდებისას აუცილებელია შეივსოს რესურსის სტატუსის ველები იმგვარად, რომ API კლიენტს არ დასჭირდეს სტატუსის მოთხოვნა ამსმპ-დან (და, შესაბამისად, [oFA-PFSM]-ის 12.6 თავში მითითებული განმარტებით, ამსმპ-სათვის სავალდებულო არ გახდეს _links ელემენტში status-ის ტიპის ბმულის დაბრუნება), კერძოდ:
transactionStatus - გადახდის რესურსის ან ინიციირების რესურსის სტატუსის ცვლილების შემთხვევაში
consentStatus - თანხმობის რესურსის სტატუსის ცვლილების შემთხვევაში
subscriptionStatus - გამოწერის რესურსის სტატუსის ცვლილების შემთხვევაში
subscriptionEntryStatus - გამოწერის რესურსის ელემენტის სტატუსის ცვლილების შემთხვევაში
6.7გადაწოდება HTTP(S) პროტოკოლით
გამოძახება:
POST <Client-Notification-URL>
აუცილებელია შეტყობინებები და პასუხები ფორმატირებული იყოს [oFA-PFSM] დოკუმენტის 12.6 თავის შესაბამისად. დამატებითი მოთხოვნები რეგულირდება ამ დოკუმენტის თავი 6.6, "რესურსის სტატუსის შეტყობინების შიგთავსი" თავის შესაბამისად.
თუ შეტყობინება მიღებულია და დამუშავებულია წარმატებით, აუცილებელია შეტყობინების მიმღებმა პასუხად დააბრუნოს HTTTP სტატუს კოდი 200, როგორც ეს [oFA-PFSM] დოკუმენტის 12.6 თავის შესაბამისად არის განსაზღვრული. სხვა სტატუს კოდებს შემთხვევაში რეაგირება რეგულირდება თავი 6.7.1, "შეტყობინების გამეორების მექანიზმი" თავის შესაბამისად.
6.7.1შეტყობინების გამეორების მექანიზმი
აუცილებელია ამსმპ-მა განმეორებით გაგზავნოს შეტყობინება იმ შემთხვევაში, თუ შეტყობინება ვერ მიეწოდება API კლიენტს (მაგალითად, ქსელის შეცდომის ან API კლიენტის დროებითი მიუწვდომლობის გამო). აუცილებელია დროებით ხელმიუწვდომლობად ჩაითვალოს მხოლოდ ის შემთხვევა თუ Client-Notification-URL-ზე გაგზავნილი მოთხოვნა პასუხს არ დააბრუნებს 30 წამის განმავლობაში, ან დასრულდება შემდეგი სტატუს კოდებით:
408 (Request Timeout)
429 (Too Many Requests)
500 (Internal Server Error)
502 (Bad Gateway)
503 (Service Unavailable)
504 (Gateway Timeout).
ამსმპ-მა არავითარ შემთხვევაში არ უნდა ჩათვალოს დროებით ხელმიუწვდომლობაში სხვა სტატუს კოდები, მათ შორის 4xx კლასის შეცდომები, რომლებიც მიუთითებენ API კლიენტის მხრიდან არასათანადო მოთხოვნაზე.
აუცილებელია შეტყობინების გამეორებისას ამსმპ-მა გამოიყენოს ერთიდაიგივე x-request-id, რომელიც გამოყენებულია თავდაპირველ შეტყობინებაში, რათა API კლიენტმა შეძლოს დადგინდეს, რომ ეს არის გამეორებული შეტყობინება.
თუ სხვაგვარად არ არის შეთანხმებული API კლიენტსა და ამსმპ-ს შორის, აუცილებელია შეტყობინების გამეორება განხორციელდეს შემდეგი წესების დაცვით:
გამეორების მაქსიმალური რაოდენობა იყოს 5 (ხუთი) ცალი.
გამეორების ინტერვალი იყოს მზარდი, კოეფიციენტით 1,5 დაწყებული 5 (ხუთი) წუთიდან. ანუ პირველი გამეორება მოხდება 5 წუთის შემდეგ, მეორე - 7.5 წუთის შემდეგ, მესამე - 11.25 წუთის შემდეგ, მეოთხე - 16.875 წუთის შემდეგ და მეხუთე - 25.3125 წუთის შემდეგ.
თუ შეტყობინების მიწოდება ვერ მოხერხდა ყველა 5 (ხუთი) მცდელობის მიუხედავად, ამსმპ-მა უნდა შეწყვიტოს შეტყობინების გამეორება და შეინახოს აღნიშნული ინფორმაცია ჟურნალში, შემდგომი გამოკვლევის მიზნით.
მკვდარი წერილების რიგი დოკუმენტის ამ ვერსიით მხარდაჭერილი არ არის. შესაძლოა ამსმპ და API კლიენტი შეთანხმდნენ მკვდარი წერილების რიგის გამოყენებაზე, როგორც დამატებით მექანიზმზე შეტყობინებების მიწოდების წარუმატებლობის შემთხვევაში. აღნიშნული რეგულირდება ამსმპ-სა და API კლიენტს შორის არსებულ სახელშეკრულებო ურთიერთობით.
6.8გადაწოდება სხვა პროტოკოლებით
6.8.1შეტყობინებების სერიალიზაცია
აუცილებელია შეტყობინებები სერიალიზებული იყოს JSON ფორმატში. შეტყობინებების სტრუქტურა რეგულირდება თავი 6.6, "რესურსის სტატუსის შეტყობინების შიგთავსი" თავის შესაბამისად. შეტყობინებებზე ხელმოწერა ხორციელდება იგივე პრინციპით, რაც HTTP(S) პროტოკოლის შემთხვევაშია აღწერილი, შემდეგი დათქმებით:
სტანდარტული თავსართები (x-request-id, digest) გადაეცემა შესაბამისი პროტოკოლის მექანიზმების გამოყენებით (მაგალითად, Kafka Headers, AMQP Message Properties და ა.შ.).
თავსართი (request-target) კოდირებულია შემდეგი პრინციპით: POST Client-Notification-URL სადაც Client-Notification-URL არის შეტყობინების მისაღები URI, რომელიც გადმოსცა API კლიენტმა და ფორმატირებულია თავი 6.10, "API კლიენტის მიერ მისაღები შეტყობინებების URL-ების მოთხოვნები" თავის შესაბამისად.
6.8.2შეტყობინების გამეორების მექანიზმი
აუცილებელია ამსმპ-მა განმეორებით გაგზავნოს შეტყობინება იმ შემთხვევაში, თუ შეტყობინება ვერ მიეწოდება API კლიენტს (მაგალითად, ქსელის შეცდომის ან API კლიენტის დროებითი მიუწვდომლობის გამო). აუცილებელია შეტყობინების მიწოდების წარუმატებლობა დადგინდეს შესაბამისი პროტოკოლის მექანიზმების გამოყენებით (მაგალითად, Kafka Delivery Reports, AMQP Acknowledgements და ა.შ.). აუცილებელია მკვდარი წერილების რიგის რეალიზება და იგი უნდა მოხდეს შესაბამისი პროტოკოლის მექანიზმების გამოყენებით.
თუ სხვაგვარად არ არის შეთანხმებული API კლიენტსა და ამსმპ-ს შორის, აუცილებელია შეტყობინების გამეორება განხორციელდეს თავი 6.7.1, "შეტყობინების გამეორების მექანიზმი" თავის შესაბამისად აღწერილი პრინციპით.
6.9შეტყობინებზე ელექტრონული შტამპის დადება
აუცილებელია როგორც ამსმპ-მა, ისე API კლიენტმა გამოიყენოს ელექტრონული შტამპი შეტყობინებების ავთენტიფიცირებისა და მთლიანობის დასადასტურებლად. აუცილებელია ელექტრონული შტამპი დაიდოს როგორც მოთხოვნაზე, ისე პასუხზე, "შეტყობინებების" პროცესის დროს. აუცილებელია ელექტრონული შტამპი შეესაბამებოდეს თავი 4.3, "ელექტრონული შტამპის განხორციელება მოთხოვნასა და პასუხზე"-ით აღწერილ მოთხოვნებს. HTTP(S)-ისგან განსხვავებული პროტოკოლების შემთხვევაში აუცილებელია შტამპის დადება მოხდეს თავი 6.8.1, "შეტყობინებების სერიალიზაცია" თავის შესაბამისად.
6.10API კლიენტის მიერ მისაღები შეტყობინებების URL-ების მოთხოვნები
6.10.1HTTP(S) პროტოკოლის მხარდაჭერა
აუცილებელია ამსმპ-მა მხარი დაუჭიროს URL-ებს, რომლებიც API კლიენტის მიერ არის მიწოდებული და იყენებს HTTPS პროტოკოლს (მაგალითად, https://push.apiclient.example.com/receive). აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები, რომლებიც გამოიყენება შეტყობინებების მისაღებად, იყოს საჯაროდ ხელმისაწვდომი და მუდმივი. აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები იყენებდნენ HTTPS პროტოკოლს უსაფრთხო კომუნიკაციის უზრუნველსაყოფად. აუცილებელია API კლიენტმა უზრუნველყოს, რომ მისი URL-ები აკმაყოფილებდნენ თავი 3.7, "ზოგადი მოთხოვნები ჰიპერბმულების შემოწმების მიმართ"-ით აღწერილ მოთხოვნებს. HTTP პროტოკოლი არავითარ შემთხვევაში არ უნდა იყოს მხარდაჭერილი რეალურ გარემოში, თუმცა შესაძლოა იგი მხარდაჭერილი იყოს სატესტო (Sandbox) გარემოში.
6.10.2სხვა პროტოკოლების მხარდაჭერა
შესაძლოა გარდა HTTP(S) პროტოკოლისა, ამსმპ-მა მხარი დაუჭიროს სხვა პროტოკოლებსაც. მაგალითად - მაღალი დატვირთვის მქონდე API კლიენტების უკეთესი მხარდაჭერისათვის. თუ ამსმპ მხარს უჭერს სხვა პროტოკოლებს, აუცილებელია ამსმპ-მა უზრუნველყოს, რომ API კლიენტის მიერ მიწოდებული URL-ები ისე იყოს შედგენილი რომ მასში კოდირებული იყოს ყველა სათანადო პარამეტრი, რითაც უნიკალურად დადგინდება შეტყობინებების გასაგზავნი/მისაღები ადგილმდებარეობა. მაგალითად, ყველა სერვერის მისამართი (DNS ან IP) და შესაბამისი პორტი, ასევე რიგი (Queue) ან თემა (Topic) და ა.შ..

შესაძლოა URL-ები არ აკმაყოფილებდნენ თავი 3.7, "ზოგადი მოთხოვნები ჰიპერბმულების შემოწმების მიმართ" მოთხოვნებს. მაგალითად, ისინი მოწოდებული და მართულნი იყონ ამსმპ-ის მიერ. აუცილებელია URL-ები გაიწეროს თავი 3.8, "კონტრაქტი API კლიენტსა და ამსმპ-ს შორის" თავის შესაბამისად განსაზღვრული სახელშეკრულებო ურთიერთობის ფარგლებში. აუცილებელია URL-ით მითითებული მისამართები იყოს საჯაროდ ხელმისაწვდომი და მუდმივი. აუცილებელია გამოყენებული იყოს დაცული კომუნიკაციის მექანიზმები, რომლებიც უზრუნველყოფენ შეტყობინებების კონფიდენციალურობას, ავთენტიფიკაციას და მთლიანობას, არჩეული პროტოკოლის სტანდარტული შესაძლებლობების შესაბამისად, რათა API კლიენტს შეეძლოს დაეყრდნოს სტანდარტულ პროგრამულ ბიბლიოთეკებს.
